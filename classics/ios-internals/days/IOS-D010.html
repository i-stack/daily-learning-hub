Method Swizzling：方法交换、AOP 与安全边界

动态系统 · 2026-08-19 · Method Swizzling / 方法交换 / AOP / SEL 与 IMP / class_addMethod / +load / 消息派发 / 安全边界
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准

Method Swizzling 改写 method_t 中 SEL 到 IMP 的映射，在消息查找阶段完成切面织入。本课从 objc_msgSend 链路出发，解释继承场景下 class_addMethod 的隔离作用、多个 Hook 串成的调用链风险，以及它在 AOP 方案谱系中的位置与工程护栏。

01 背景与 API

要解决的问题

有一类需求横跨所有对象，却不该写进任何一处业务代码：页面曝光埋点、重复点击防护、网络层监控、内存泄漏观测、线上兜底防崩。共同特征是：你拿不到源码，也控制不了对象的创建，但仍想在方法执行前后插入逻辑。

Method Swizzling 给出的答案是：不改源码、不建子类、不改调用方，直接在运行时把「方法名 → 实现」这张表里的映射改掉。

主要 API

API 作用 备注
method_exchangeImplementations 交换两个 Method 的 IMP 最常用的入口
method_setImplementation / method_getImplementation 直接读写 IMP 适合保存原实现为函数指针
class_addMethod 只在本类添加方法条目 返回 NO 表示本类已有，是探测手段
class_replaceMethod 本类有则替换、无则添加 与 class_addMethod 配对使用
class_getInstanceMethod 取 Method 会沿继承链向上查找，这是万坑之源
class_getClassMethod 取类方法 Method 类方法存在元类上
method_getTypeEncoding 取类型编码 必须与原始签名一致
imp_implementationWithBlock 用 block 造 IMP 让 hook 写在 block 里
class_copyMethodList 遍历方法列表 调试与自检

最小可用形态

+ (void)load {
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        Method m1 = class_getInstanceMethod(self, @selector(viewWillAppear:));
        Method m2 = class_getInstanceMethod(self, @selector(xxx_viewWillAppear:));
        method_exchangeImplementations(m1, m2);
    });
}

- (void)xxx_viewWillAppear:(BOOL)animated {
    [self xxx_viewWillAppear:animated];   // 看似递归，实为调用原始实现
    [Tracker logPage:self];               // 切面逻辑
}

这段代码能跑，但它是错的——错在没处理继承。完整的正确写法见「03 底层原理」。

02 运行机制

一、方法的物理结构

Runtime 里一个方法就是 method_t 三元组：

struct method_t {
    SEL name;           // 选择器，本质是 uniquing 后的字符串地址
    const char *types;  // 类型编码，如 "v20@0:8B16"
    IMP imp;            // id (*)(id self, SEL _cmd, ...)
};

三个要点：

  1. SEL 是名字，不是实现。同名 SEL 全局唯一，跨类共享同一个值。
  2. IMP 是普通函数指针，前两个参数是隐式传入的 self 与 _cmd——这也是为什么交换后方法体里依然拿得到 self。
  3. swizzling 只改 imp 字段，name 名义不变。所以「viewWillAppear: 这个入口」永远有效，只是它指向的实现被换掉了。

二、消息发送链路

flowchart TD
    A["objc_msgSend(obj, SEL)"] --> B{"cache_t 命中?"}
    B -- 是 --> C["直接跳转 IMP"]
    B -- 否 --> D["本类 method_list 二分查找"]
    D -- 命中 --> E["回填 cache_t"]
    E --> C
    D -- 未命中 --> F{"存在 superclass?"}
    F -- 是 --> G["沿继承链向上重复查找"]
    G --> D
    F -- 否 --> H["消息转发三连"]
    H --> I["resolveInstanceMethod / forwardingTarget / forwardInvocation"]

Swizzling 生效在第 3 步「本类 method_list 查找」的结果上，完全不经过消息转发，因此是零转发开销的 hook。

三、method_exchangeImplementations 内部做了什么

简化的 objc4 源码逻辑：

void method_exchangeImplementations(Method m1, Method m2) {
    if (!m1 || !m2) return;
    mutex_locker_t lock(runtimeLock);   // 全局 runtime 锁，交换是原子的
    IMP imp1 = m1->imp(false);
    IMP imp2 = m2->imp(false);
    m1->setImp(imp2);
    m2->setImp(imp1);
    flushCaches(nil);                   // 清空全进程类缓存
    adjustCustomFlagsForMethodChange(...);
}

三个必须知道的推论：

  • 原子性：持 runtimeLock，不存在「交换到一半」的中间态；已在执行的调用也不会中断，它取到的旧 IMP 会跑完。
  • flushCaches(nil) 是 O(n) 全量清缓存。这是 swizzling 只能做一次、且必须在启动期做完的根本原因——热路径里反复 swizzle 会让全进程类缓存反复失效。
  • 它不校验签名。两个方法类型编码不一致也能换成功，后果在调用时才炸。

四、为什么 swizzled 方法里调用自己不是死循环

交换后，xxx_viewWillAppear: 这个 SEL 指向的 IMP 是原始实现。所以 [self xxx_viewWillAppear:animated] 执行的是原逻辑。

反之，如果在 swizzled 方法里写 [self viewWillAppear:animated]，那条 SEL 现在指向的是你自己的切面实现——真递归，直接爆栈。

不变式：hook 方法内部必须调用 swizzledSEL，且必须是无条件的第一行。

03 底层原理

一、核心命题：交换的是映射，不是代码

Swizzling 没有修改任何一行业务代码，它改的是「名字 → 实现」这张表。由此推出两条性质：

  • 对调用方完全透明：调用方写的还是 viewWillAppear:，编译期无感知。
  • 影响范围是全进程：同一时刻所有实例、包括系统框架内部的调用，全部走你的实现。

二、继承场景：唯一真正的硬核考点

class_getInstanceMethod 沿继承链向上查找。若子类未实现某方法，originalMethod 返回的是父类的 Method，此时直接 method_exchangeImplementations 会把父类的 IMP 改掉：

情况 直接 exchange 的后果
本类自己实现了方法 只影响本类，符合预期
本类未实现，继承自父类 父类实现被换掉 → 父类自身、所有兄弟子类、系统内部调用全部被污染
本类是类簇的公开父类 hook 根本落不到真实类上，看似成功实则无效

正确写法用 class_addMethod 做「探测 + 隔离」：

+ (void)load {
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        Class cls = [self class];
        SEL originalSel = @selector(viewWillAppear:);
        SEL swizzledSel = @selector(xxx_viewWillAppear:);
        Method originalMethod = class_getInstanceMethod(cls, originalSel);
        Method swizzledMethod = class_getInstanceMethod(cls, swizzledSel);

        // ① 只在本类加一条 originalSel → swizzledIMP
        BOOL didAdd = class_addMethod(cls, originalSel,
                                      method_getImplementation(swizzledMethod),
                                      method_getTypeEncoding(swizzledMethod));
        if (didAdd) {
            // ② 本类原本没有 → 把「继承自父类的实现」挂到 swizzledSel 名下
            class_replaceMethod(cls, swizzledSel,
                                method_getImplementation(originalMethod),
                                method_getTypeEncoding(originalMethod));
        } else {
            // ③ 本类自己有 → 安全交换
            method_exchangeImplementations(originalMethod, swizzledMethod);
        }
    });
}

一句话记法：class_addMethod 的作用是把继承来的共享实现隔离成本类私有条目，避免污染父类。

三、为什么必须在 +load，为什么还要 dispatch_once

  • +load 在 dyld 装载镜像、main() 之前执行，由 runtime 按函数指针直接调用，不走 objc_msgSend——因此不存在方法查找，也不存在「子类继承父类 load」。
  • 顺序：父类 → 子类 → 分类；分类之间顺序不确定，取决于 Build Phases 的编译顺序。
  • load 期间 runtime 持锁，天然串行线程安全。
  • 仍要 dispatch_once 的理由：二次 exchange 会把 IMP 换回去，hook 静默失效，且最难排查；once 是对「入口可能被重复调用」的幂等兜底。

对比 +initialize：懒加载、走消息派发、子类未实现时会因继承而多次触发父类实现，需要 if (self == [Xxx class]) 守卫。

四、两个容易忽略的底层事实

1. dirty memory 代价。 类数据分为只读的 class_ro_t 与可写的 class_rw_ext_t。首次修改方法列表会触发 extAllocIfNeeded 分配 rw_ext——也就是说 swizzling 会把类从 clean memory 搬进 dirty memory。少量类无感，批量 hook 上千个类时可在 VM Tracker 上量到。

2. 不能直接改结构体字段。 iOS 14 起 arm64 使用 relative method lists（method_t 内是 int32 相对偏移而非绝对指针）；arm64e 上 IMP 还带 PAC 指针签名。老代码里「按偏移手写 `imp`」的做法会签名校验失败或读错地址——必须走官方 API。

五、类方法要操作元类

hook 类方法时目标不是类本身，而是它的元类：class_getClassMethod 或 class_getInstanceMethod(object_getClass(cls), sel)。写错目标会静默 hook 到别处。

04 设计与取舍

一、放到 AOP 坐标系里

Swizzling 本质是运行时织入的切面，对应 AOP 的三个概念：

AOP 概念 在 Swizzling 中的对应
Join Point（连接点） 每一次 objc_msgSend 派发
Pointcut（切点） 被交换的那个 SEL
Advice（通知） swizzled 方法体（before / after / around）

它的特殊性在于：织入发生在运行时，且不留下任何源码痕迹。这既是它的价值，也是它的原罪。

二、与其他 hook 方案的取舍

方案 机制 适用面 代价与风险
Method Swizzling 改 method_t.imp OC 方法、Swift 的 @objc dynamic 全局生效、顺序依赖
Aspects 类 block hook | 原 SEL 指向 `_objc_msgForward`，在 `forwardInvocation:` 中分发 | 想用 block 写切面 | 走消息转发，慢 1~2 个数量级；与 RAC 等转发型 hook 互相覆盖
fishhook 重绑定 __la_symbol_ptr / __nl_symbol_ptr 跨镜像调用的 C 函数 对同镜像内调用无效，对 OC 方法完全无效
Category 重写同名方法 方法列表插入 禁止使用 原实现永久丢失、无法调 super、多 category 同名运行时静默、行为依赖编译顺序
继承 + override + super 编译期 你能控制对象创建的场景 管不了系统/第三方创建的对象
改源码 / 协议装饰器 编译期 自己的业务代码 需要改调用方，成本最高但最可控

三、Apple 的取向

Apple 提供了完整的运行时反射与改写能力（objc/runtime.h 公开 API），却始终没有提供官方的 hook 框架。这个取舍很清晰：

  • 换来了：极强的动态性，第三方 SDK 可以无侵入地做监控、埋点、热修、调试工具；整个 iOS 生态的 APM 能力建立在这套机制上。
  • 付出了：能力没有边界约束，风险完全由使用者承担——全局性、顺序不确定、静默失效、ABI 假设。Apple 只在文档里用「不要滥用」约束，无法在机制层面兜底。

架构层面的结论：能改源码就改源码。Swizzling 的正当用途只有一种——无侵入的横切关注点。用它承载业务逻辑，等于把控制流藏进 runtime，代码的可读性与可测性同时归零。

四、与相邻知识的连接

  • Category（Day 8）：category 在编译后把方法插入本类方法列表，是 swizzling 最常见的载体。
  • Associated Object（Day 9）：hook 后常常需要给宿主对象挂私有状态，二者成对出现。
  • Message Forwarding（Day 11）：Aspects 走的是转发路径，理解转发才能判断「为什么两个 hook 库会互相打断」。
  • KVO（Day 6）：KVO 动态生成 NSKVONotifying_Xxx 子类并重写 setter，与 swizzling 在同一块地盘上相互干扰。

05 工程实战

一、集中注册表：所有 hook 只走一个入口

@implementation HookRegistry
+ (void)swizzleClass:(Class)cls
             origin:(SEL)origin
          swizzled:(SEL)swizzled
            isClass:(BOOL)isClassMethod
{
    Class target = isClassMethod ? object_getClass(cls) : cls;
    Method m1 = class_getInstanceMethod(target, origin);
    Method m2 = class_getInstanceMethod(target, swizzled);
    if (!m1 || !m2) { [self reportFailure:cls sel:origin]; return; }
    if (strcmp(method_getTypeEncoding(m1), method_getTypeEncoding(m2)) != 0) {
        [self reportFailure:cls sel:origin];  // 签名不匹配，直接放弃并上报
        return;
    }
    BOOL didAdd = class_addMethod(target, origin,
                                  method_getImplementation(m2),
                                  method_getTypeEncoding(m2));
    if (didAdd) {
        class_replaceMethod(target, swizzled,
                            method_getImplementation(m1),
                            method_getTypeEncoding(m1));
    } else {
        method_exchangeImplementations(m1, m2);
    }
}
@end

统一入口带来四件事：统一 dispatch_once、统一前缀命名、签名校验、失败可上报。

二、工程护栏清单

  1. 只执行一次：+load + dispatch_once，并记录已 hook 的 SEL，重复注册直接拒绝。
  2. 可观测：记录原始 IMP 指针，暴露「当前 hook 清单」供调试页查看。
  3. 可回滚：保存原 IMP，提供 unswizzle。
  4. 可关闭：远程配置开关 + 灰度，出问题时不必发版。
  5. 切面要薄：不加锁、不发网络请求、不做同步 IO、不做耗时计算。
  6. 优先顺序：自己的类 > 可控第三方 > 系统类。hook 系统类是最后手段，且必须加白名单限定作用范围。
  7. 测试矩阵：继承场景 / 子类未实现 / 重复调用 swizzle / 两个 SDK 同时 hook / KVO 对象 / 类簇。

三、适用与禁止

适合：页面曝光与点击埋点、重复点击防护、网络层监控、 dealloc 泄漏观测、越界与 unrecognized selector 的线上兜底、Debug 期调试工具。

禁止：承载业务分支逻辑；hook drawRect: / layoutSubviews / cellForRowAtIndexPath: 等高频方法加耗时切面；用 category 重写同名方法来「替代」swizzling。

四、验证手段

目标 手段
确认 IMP 真的换了 swizzle 前后打印 method_getImplementation(m) 对比地址
反查 IMP 归属 (lldb) image lookup -a 0x10xxxxxx 定位符号
看方法列表全貌 class_copyMethodList 打印 SEL + IMP
看调用链是否完整 切面里打 os_signpost，Instruments → Points of Interest 可视化每一跳
量化开销 Time Profiler 对比开关两组
看内存代价 VM Tracker 对比 hook 前后 dirty size

五、一个真实故障

现象：部分页面曝光埋点丢失，只在接入某第三方统计 SDK 的版本出现。

证据链：

  1. 打印 method_getImplementation 发现 viewWillAppear: 的 IMP 确实指向我方切面；
  2. 切面里打 os_signpost，发现链路在某次调用后断开；
  3. image lookup -a 反查，确认第三方 hook 在我方之后执行；读其汇编，发现它对 self 做了类白名单判断，非白名单直接 return，不调用原实现。

根因：不是我方 bug，但依赖链的 hook 无法保证生效。

处置：改为不依赖 viewWillAppear: 链路，改用容器导航代理 + 显式生命周期回调；同时给 hook 增加「链路存活」自检上报。

教训：AOP 最恶劣的失败模式是 fails silently——链上任一环不调原实现，后面的切面全部消失，且不报错。

06 常见坑与反思

高频坑位表

坑 成因 症状 规避
污染父类 未用 class_addMethod 隔离，交换了继承来的 Method 兄弟子类与系统内部调用全被改 固定走「addMethod 探测」套路
真递归 hook 方法里调了 originalSEL 立刻爆栈 一律调用 swizzledSEL
静默失效 swizzle 被调用两次 → 换回原状 功能偶发失效，无报错 dispatch_once + 注册表去重
多 SDK 断链 链上某环不调原实现 后续切面全失效 链路自检 + 不依赖 hook 做关键埋点
类簇无效 hook NSString/NSArray 落到私有子类 看似成功，实际不生效 确认 object_getClass(obj) 的真实类；tagged pointer 无法 hook
KVO 干扰 NSKVONotifying_Xxx 动态子类重写 setter hook 打偏 用 object_getClass(obj) 取真实类
签名不匹配 swizzled 方法签名/类型编码不一致 读垃圾寄存器、栈破坏、随机崩溃 比对 method_getTypeEncoding，返回结构体的 sret 尤其危险
Swift 不生效 静态派发 / extension devirtualize OC 侧生效、Swift 侧不进切面（半生效） 需要 @objc dynamic，且写在主类体内而非 extension
分类顺序 多个分类 +load 顺序取决于编译顺序 行为在改编译顺序后突变 不依赖跨分类的 load 顺序
频繁 swizzle flushCaches(nil) 全量清缓存 启动变慢、cache miss 飙升 只在启动期一次性完成

三条判断原则

  1. 能改源码就不 swizzle。 用 runtime 改控制流，等于把架构决策藏在没有调用关系的地方。
  2. hook 的影响范围是进程级的。 你以为你在改「某个页面」，实际你在改「所有人的这个消息」。
  3. 必须能回答「如果 hook 没生效会怎样」。 如果答案是「功能静默丢失」，那这个设计本身就是错的——要么换方案，要么加自检。

08 掌握标准

一句话总结：Method Swizzling 改写的是 method_t 中 SEL 到 IMP 的映射，在消息查找阶段完成切面织入；继承场景下必须先用 class_addMethod 把继承来的共享实现隔离成本类私有条目，否则会污染父类。

掌握标准：

  • 能画全 objc_msgSend 链路，指出 swizzling 的作用点与 flushCaches 的代价；
  • 能手写 class_addMethod 隔离套路，并解释不这么写会污染谁；
  • 能说清 +load 的执行时机、线程模型与 dispatch_once 的必要性；
