Block：闭包、捕获与异步编程

内存管理 · 2026-08-12 · Block / 闭包 / 捕获 / __block / forwarding / 栈 Block / 堆 Block / 逃逸闭包 / 循环引用 / 异步编程
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准参考资料

Block 是「带捕获上下文的匿名函数」，本质是一个带 isa 的结构体——它就是一个 Objective-C 对象。本课从 Clang 编译出的三件套结构出发，讲清三种存储域的判定、捕获时到底复制了什么、__block 的 forwarding 指针如何让栈与堆指向同一份数据，以及 Block 真正难的地方：不是语法，而是逃逸之后的生命周期与执行队列契约。

01 背景与 API

要解决的问题

C 语言没有闭包。在 Block 出现之前，OC 的回调只有三条路：

方案 问题
函数指针 不能捕获上下文，要把所有状态塞进 void *context
delegate 协议 一个回调就要声明一个协议，代码远离调用点
NSInvocation 冗长、慢、无编译期检查

GCD 的出现让「把一段代码提交到队列」成为主流范式，语言层面必须有一个可以传递、可以捕获上下文、能当对象存起来的代码单元。Block 由此诞生。

Block 是什么

带有自动变量（局部变量）的匿名函数。

三个关键词：匿名（没有名字）、函数（可执行）、带自动变量（能捕获定义处的上下文）。最后一点是它与函数指针的根本区别。

基本语法

// 声明
返回值 (^名称)(参数列表)
void (^completion)(NSData *, NSError *);

// 定义
void (^log)(NSString *) = ^(NSString *msg) {
    NSLog(@"%@", msg);
};

// typedef（工程里一律这么用）
typedef void (^Completion)(NSData *data, NSError *error);

Swift 对应写法：

let log: (String) -> Void = { msg in print(msg) }
typealias Completion = (Data?, Error?) -> Void

三种 Block 类型

类型 存储域 产生条件 特点
__NSGlobalBlock__ 数据段（.data） 不捕获任何自动变量 编译期确定，永不释放，无循环引用风险
__NSStackBlock__ 栈 捕获了自动变量 出作用域即失效；栈上 Block 对捕获对象是弱引用语义
__NSMallocBlock__ 堆 对栈 Block 执行了 copy 由引用计数管理，会 retain 捕获的对象 
void (^a)(void) = ^{ NSLog(@"hi"); };          // Global（没捕获）
int x = 10;
void (^b)(void) = ^{ NSLog(@"%d", x); };       // ARC 下赋值给 __strong 变量 → Malloc
NSLog(@"%@", ^{ NSLog(@"%d", x); });           // 未 copy → Stack（MRC）/ ARC 下也常被优化

__block 说明符

Block 内部默认不能修改外部局部变量：

int count = 0;
void (^inc)(void) = ^{ count++; };   // ❌ 编译错误：Variable is not assignable

__block int count = 0;
void (^inc)(void) = ^{ count++; };   // ✅

Swift 的 capture list 与 @escaping

func load(completion: @escaping (Result) -> Void) { ... }

load { [weak self] result in
    guard let self = self else { return }
    self.update(result)
}
概念 Swift OC Block
捕获列表 [weak self] / [unowned self] __weak typeof(self) weakSelf = self;
逃逸标注 @escaping（编译期强制） 无，靠约定与文档
修改外部变量 直接可改（闭包捕获的是引用语义） 需要 __block

02 运行机制

一、Block 的本质：一个结构体

clang -rewrite-objc 后，一个 Block 会被翻译成三个东西：

flowchart TD
    A["源码 ^{ printf(x); }"] --> B["__main_block_impl_0 实例"]
    A --> C["__main_block_func_0 函数"]
    A --> D["__main_block_desc_0 描述"]
    B --> B1["isa → _NSConcreteStackBlock / MallocBlock"]
    B --> B2["FuncPtr → __main_block_func_0"]
    B --> B3["Desc → __main_block_desc_0"]
    B --> B4["捕获的变量（值副本）"]
    D --> D1["reserved / Block_size"]
    D --> D2["copy 辅助函数 __main_block_copy_0"]
    D --> D3["dispose 辅助函数 __main_block_dispose_0"]

struct __block_impl {
    void  *isa;          // 指向 _NSConcreteXxxBlock
    int    Flags;        // 标志位（含引用计数、是否堆上）
    int    Reserved;
    void  *FuncPtr;      // 执行体函数指针
};

struct __main_block_impl_0 {
    struct __block_impl impl;          // ① isa + FuncPtr
    struct __main_block_desc_0 *Desc;  // ② 描述（含 copy/dispose）
    int x;                             // ③ 捕获的变量：值副本
};

static void __main_block_func_0(struct __main_block_impl_0 *__cself) {
    int x = __cself->x;   // 通过 cself 访问捕获值
    printf("%d", x);
}

结论：Block 的第一个成员是 isa，因此它是一个真正的 Objective-C 对象，可以 retain / release / 放进 NSArray。

二、捕获到底复制了什么

值捕获。 编译期会在 __main_block_impl_0 里加一个同类型的成员，把变量当前的值拷进去。

关键推论：

  • 捕获的是值，所以 Block 内修改不了外部变量（改的是结构体成员，且是 const）；
  • 捕获的是指针变量时（如 self、NSString *），复制的是指针本身（地址），不是对象。因此对象引用计数 +1（堆 Block 会 retain）。
局部变量 int x = 10      →  复制 10
局部变量 NSString *s     →  复制指针地址（堆 Block 会 retain 该对象）
局部变量 self           →  复制 self 指针（堆 Block 会 retain self）★循环引用根源

三、栈 → 堆：什么时候发生 copy

栈 Block 出作用域就失效。要把它存起来，必须 copy 到堆。ARC 下编译器会自动插入 objc_retainBlock（等价于 Block_copy）：

触发场景 ARC 下是否自动 copy
赋值给 __strong / copy 属性 ✅
作为函数/方法返回值 ✅
作为参数传给 GCD（dispatch_async） ✅（GCD 内部 copy）
加入 NSArray / NSDictionary ✅（copy on add）
仅作为函数参数传入并同步调用 ❌（仍是栈，这也是非逃逸闭包更快的原因）
赋值给 __weak 变量 ❌

copy 时发生了两件事：

  1. 把整个 Block 结构体 memcpy 到堆；
  2. 调用 desc 里的 __main_block_copy_0 → _Block_object_assign，按捕获变量的类型分别处理：
捕获类型 常量 动作
对象 BLOCK_FIELD_IS_OBJECT objc_retain
另一个 Block BLOCK_FIELD_IS_BLOCK Block_copy
__block 变量 BLOCK_FIELD_IS_BYREF _Block_byref_copy（复制到堆）

四、__block 的实现与 forwarding 指针

__block int count 会被编译成一个 __Block_byref 结构体：

struct __Block_byref_count_0 {
    void  *isa;
    struct __Block_byref_count_0 *forwarding;   // ★ 关键
    int    flags;
    int    size;
    int    count;                               // 真正的变量
};

为什么需要 forwarding？

copy 前：
  栈上 byref.forwarding ──→ 栈上 byref 自己
  Block（栈）──→ byref（栈）

copy 后：
  栈上 byref.forwarding ──→ 堆上 byref   ← 改指向
  堆上 byref.forwarding ──→ 堆上 byref 自己
  Block（堆）──→ byref（堆）

复制后，栈上和堆上同时存在 __Block_byref 结构体，但两者的 forwarding 都指向堆上那一份。因此无论从栈还是从堆访问 count，走的都是同一份数据。

这就是为什么 __block 变量在 Block 内外都能被正确修改——它不是「引用传递」，而是「多份结构体 + 一个统一的转发指针」。

Block 内所有对 __block 变量的读写都被编译成 count->forwarding->count。

五、一次完整的 Block 生命周期

阶段 发生什么
定义 编译期生成 impl / func / desc 三件套，isa 指向 StackBlock
捕获 复制自动变量的值（对象则复制指针）
copy memcpy 到堆，isa 改为 _NSConcreteMallocBlock，调 __block_copy retain 捕获对象
调用 FuncPtr(block, ...)，通过 __cself 访问捕获值
释放 引用计数归零 → __block_dispose → _Block_object_dispose release 捕获对象，释放 __block 变量

03 底层原理

一、根本命题：把「代码 + 上下文」变成一等公民

Block 的设计目标是让一段代码可以像对象一样传递，同时带走它需要的上下文。

它选择了最朴素的实现：结构体 + 函数指针，再加上 isa 让它能接入 OC 的内存管理体系。这个选择带来三个直接后果：

  1. Block 是对象 → 可以存进数组、当属性、被 GCD 持有；
  2. 捕获是编译期展开的 → 没有运行时的变量查找开销，性能接近函数调用；
  3. 捕获的对象由 Block 自己 retain → 循环引用就此埋下。

二、为什么 Block 内默认不能改外部变量

这是编译期的刻意限制，不是技术不能：捕获进结构体的是 const 成员。

理由是语义清晰：Block 可能在定义处很久之后、在另一个线程执行。如果允许直接写外部栈变量，那个栈帧早就不存在了，写操作无处可去。

所以必须显式写 __block，把变量从栈搬到堆（通过 byref 结构体），让它有独立于栈帧的生命周期。__block 的本质是「把变量提升为堆对象」，而不只是「允许修改」。

三、栈 Block 不 retain 捕获对象

这是一个常被忽略但很重要的细节：

  • 栈 Block：对捕获的对象不 retain（因为栈 Block 的生命周期短于或等于作用域，编译器认为没必要）；
  • 堆 Block：copy 时会 retain。

所以「Block 会 retain self 造成循环引用」这句话，准确的表述是「被 copy 到堆的 Block 会 retain self」。

下面这段在 ARC 下不会产生循环引用：

- (void)run {
    [UIView animateWithDuration:0.3 animations:^{ 
        self.view.alpha = 0;   // 传给方法后立即同步执行，编译器不 copy
    }];
}

而这段会：

self.handler = ^{ [self doSomething]; };   // 赋值给属性 → copy 到堆 → retain self

判断标准不是「有没有写 self」，而是「Block 逃逸了没有」。

四、Swift 为什么引入 @escaping

Swift 把上面这条隐含规则变成编译期契约：

非逃逸（默认） @escaping
生命周期 函数返回前一定执行完 可存储、可异步调用
self 捕获 不需要显式 self. 必须显式写 self. 或 capture list
编译器优化 可省略 retain、可内联 必须 retain
循环引用风险 无 有

@escaping 关键字的真正价值是：它逼你在写代码的那一刻回答「这个闭包会不会被存起来」，而这个答案直接决定了要不要 [weak self]。OC 没有这个标注，所以 OC 的 Block 循环引用更多。

五、Block 与 GCD

GCD 会 Block_copy 传给它的 Block（因为要跨队列、可能延迟执行），所以：

dispatch_after(dispatch_time(DISPATCH_TIME_NOW, 5 * NSEC_PER_SEC),
               dispatch_get_main_queue(), ^{
    [self refresh];     // ✅ 会被 copy 并 retain self，5 秒内 self 不会释放
});

这既是 GCD 好用的原因，也是延迟任务必然延长对象寿命的原因。

六、Block 的循环引用链条

self ─strong→ handler(Block) ─strong→ self

破解（详见 Day 2、Day 12）：

__weak typeof(self) weakSelf = self;
self.handler = ^{ 
    __strong typeof(weakSelf) strongSelf = weakSelf;   // weak-strong dance
    if (!strongSelf) return;
    [strongSelf doSomething];
};

注意：捕获 self->_ivar 也会捕获 self。 ^{ _name = @"x"; } 里 _name 会被编译成 self->_name，隐式捕获 self。Swift 对此有显式警告，OC 没有。

04 设计与取舍

一、Apple 为什么做 Block

约束：GCD 需要一段可传递、可延迟执行、能带走上下文的代码。

候选 问题
函数指针 + context 手工打包上下文，类型不安全
delegate 协议 太重，代码远离调用点
NSInvocation 慢、冗长、无编译期检查
Block（结构体 + 函数指针 + isa） 语法就近、能捕获、是对象、性能接近函数调用 → 被选中

换来什么：

  • 代码就近：回调写在调用点旁边，可读性提升巨大；
  • 零成本捕获：捕获是编译期展开的结构体成员，运行时无查找开销；
  • 与 GCD 天然契合：Block 能直接被队列持有和调度；
  • 是对象：可存储、可传递、可放容器。

付出什么：

  • 循环引用：捕获 self + Block 逃逸 = 泄漏，必须由人处理；
  • 存储域心智负担：栈/堆/全局三态，copy 时机不直观（__block 与 MRC 下尤为明显）；
  • 执行上下文隐含：Block 不承诺线程，回调在哪跑取决于调用方；
  • 调试困难：栈帧里看到的是 __main_block_func_0，堆栈可读性差。

二、Apple 的补救

问题 措施
MRC 下要手写 Block_copy ARC 自动在赋值给 strong/copy 属性、返回值、入参给 GCD 时 copy
Block 属性易写成 assign 建议一律 copy（ARC 下 strong 亦会 copy，但语义用 copy 更明确）
循环引用 __weak + weak-strong dance；Swift 的 @escaping 编译期提醒
延迟任务不可控 DispatchWorkItem 可取消；Swift Concurrency 的 Task 结构化取消
Block 类型写起来啰嗦 typedef / typealias

三、方案选型

场景 推荐 理由
一次性异步回调 Block / 闭包 代码就近
多事件、有状态、需复用 delegate 协议 Block 无法表达「多个回调 + 生命周期」
一对多广播 Notification（Day 13） Block 是一对一
需要取消 + 结构化并发 Swift Task Block 无内置取消
高频同步调用（如排序比较） 非逃逸闭包 / 函数指针 不逃逸 → 不 copy → 更快

四、架构定位

Block 是一等公民，但「谁持有它、在哪执行、能否取消」必须是显式契约。 设计一个接受 Block 的 API 时，必须在签名或文档里回答：

  • 这个 Block 会逃逸吗（存起来还是同步调用）？
  • 在哪个队列回调？
  • 能否取消？取消后 Block 还会执行吗？
  • Block 会把 self 的寿命延长多久？

五、与相邻知识的连接

  • ARC（Day 2）：weak-strong dance 与循环引用破解的基础。
  • GCD（Day 14）：GCD 会 copy Block，延迟任务必然延长对象寿命。
  • NSProxy（Day 12）：同样是处理回调生命周期的工具，侧重打断系统 API 的强引用。
  • Method Swizzling（Day 10）：AOP 的另一条路，Block-based hook（如 Aspects）用 Block 作为切面实现体。

05 工程实战

一、为回调写下三个契约

任何接受 Block 的 API，签名旁边就要写清楚：

/// - Parameter queue: 回调执行的队列（默认 main）
/// - Returns: 取消令牌，cancel 后 completion **不会**被调用
@discardableResult
func load(_ id: String,
          queue: DispatchQueue = .main,
          completion: @escaping (Result<Data, Error>) -> Void) -> Cancellable
契约 不写清楚的后果
执行队列 调用方在回调里直接更新 UI → 偶发崩溃/闪烁
取消语义 页面退出后回调仍执行，访问已释放资源
逃逸与否 泄漏或过度 weak

二、验证 owner → closure → owner 链

写每个闭包前，先回答三个问题：

① 这个闭包被谁持有？        self.handler / GCD 队列 / 网络层 / 立即调用
② 闭包捕获了谁？            self / self 的 ivar / 局部变量
③ 是否存在环？              ① 里的持有者最终是否又被 self 持有

只有 ①是 self 持有 且 ②捕获 self 时才构成环：

场景 是否成环 处理
self.handler = { self.x } ✅ 成环 [weak self]
dispatch_async(主队列) { self.x } ❌ 队列不被 self 持有 无需 weak（但会延长 self 寿命）
URLSession.dataTask { self.x } ❌ session 不被 self 持有 无需 weak
self.timer = Timer(...){ self.x } ✅ 成环 [weak self] + invalidate
UIView.animate { self.view.alpha } ❌ 同步执行不逃逸 无需 weak

三、不要机械使用 [weak self]

这是本课最重要的工程判断：weak 会把「对象活得不够久」变成「工作静默丢失」。

// ❌ 危险：上传完成后的落库操作可能永远不执行
upload(data) { [weak self] result in
    self?.saveToDatabase(result)   // self 提前释放 → 数据丢失，且无任何报错
}

正确做法是给工作本身一个所有者，而不是靠 self 存活：

// ✅ 由 UploadManager（长生命周期）持有任务，与 VC 生命周期解绑
UploadManager.shared.upload(data) { result in
    Database.shared.save(result)   // 不依赖 VC
}

判断原则：

场景 用 strong 还是 weak
更新 UI（对象没了就不需要更新） [weak self]
必须完成的副作用（写库、上报、清理） 不用 weak，但要换一个合适的所有者
网络请求回调（结果要落库） 让网络层/ViewModel 持有，不靠 VC

四、闭包不保证回调线程

// ❌ 假设回调在主线程
api.fetch { data in
    self.label.text = data.title    // 崩溃：回调可能在后台线程
}

// ✅ 显式切队列
api.fetch { [weak self] data in
    DispatchQueue.main.async { self?.label.text = data.title }
}

网络库、系统回调（NotificationCenter、KVO、相册/定位回调）都不承诺线程。要么 API 层统一 queue 参数，要么调用方显式切换。

五、取消语义

手段 适用
DispatchWorkItem.cancel() 延迟任务（但已经开始执行的无法中断）
Operation.cancel() 有状态、可检查 isCancelled 的任务
URLSessionTask.cancel() 网络请求
Swift Task.cancel() 结构化并发，支持协作式取消

注意：DispatchWorkItem.cancel() 不能中断已在执行的 Block，只能阻止尚未开始的执行。Block 内部需要自己检查 item.isCancelled。

六、验证手段

手段 验证什么
deinit 日志 对象是否真的释放
Memory Graph Debugger 谁持有了 Block、Block 又持有了谁
XCTest + weak var 断言闭包释放后对象释放
po [block class] / isa 打印 确认是 Global / Stack / Malloc
Instruments Allocations Block 数量是否持续增长

06 常见坑与反思

高频坑位表

坑 成因 症状 规避
逃逸闭包捕获 self 堆 Block retain self 循环引用，对象不释放 [weak self] + guard let
隐式捕获 self Block 里写 _ivar（编译成 self->_ivar） 以为没捕获 self 却泄漏 一律写 self.，或用属性访问
过度使用 [weak self] 关键工作依赖 self 存活 静默丢失副作用（写库失败、上报丢失） 换个合适的所有者，而不是加 weak
假设回调在主线程 Block 不承诺线程 偶发 UI 崩溃 API 显式声明队列，调用方切队列
延迟任务无法取消 dispatch_after 没有句柄 页面退出后仍执行 DispatchWorkItem / Task
MRC 下 __block 不 retain MRC 与 ARC 语义不同 旧代码迁移后出现悬垂 迁移时用 __weak 替代 __block 做弱引用
Block 属性用 assign 栈 Block 未 copy 野指针崩溃 属性一律 copy
循环变量捕获 for 里用同一个变量名 所有 Block 看到同一个值 Swift 闭包每次迭代独立捕获（Swift 5+ 已修正）
dispatch_sync 到当前队列 同步等待自己 死锁 检查 Thread.isMainThread，改用 async
Block 里改外部变量失败 忘了 __block 编译错误 / 值不变 显式 __block
Block 内 self 已被释放（MRC） 栈 Block 不强引用 崩溃 copy 到堆
把 Block 当 delegate 用 一对多语义 只能有一个回调 需要多播用 delegate 或 Notification
逃逸闭包未标注 @escaping Swift 编译错误 编译失败 存起来就标 @escaping

三条反思

  1. 判断循环引用的标准是「逃逸」，不是「写了 self」。 同步执行、不被存储的 Block 捕获 self 完全安全。机械地给所有闭包加 `[weak self]`，等于用「静默失败」换「可能泄漏」——前者更难排查。先画出 owner → closure → owner 链，再决定。
  2. __block 的语义是「把变量提升到堆」，不是「允许修改」。 理解 forwarding 指针后你会明白：Block 里外访问的是同一个堆上的 byref 结构体。这也解释了为什么 __block 变量在 Block 执行完后仍然可读——它已经不在栈上了。
  3. 闭包的难点从来不是语法，而是契约。 「在哪个线程回调」「能不能取消」「会延长谁的生命」——这三件事不写清楚，代码在单人开发时能跑，一旦多人协作或场景变复杂，就会以偶发崩溃和静默丢数据的形式暴露出来。

08 掌握标准

一句话总结：Block 是带 isa 的结构体（因此是对象），编译期展开为 impl / func / desc 三件套，捕获的是自动变量的值副本；栈 Block 不 retain 捕获对象，被 copy 到堆后才 retain——所以循环引用的判断标准是「逃逸了没有」，而不是「写没写 self」；__block 通过 __Block_byref + forwarding 指针把变量提升到堆，让 Block 内外访问同一份数据。

掌握标准：

  • 60 分：能说清 Block 三种类型及产生条件；能写出 typedef 与 capture list；能识别 self.handler = ^{ self.x } 这类循环引用并用 [weak self] 破解。
  • 80 分：能画出 Block 的编译结构并解释捕获机制；能讲清 forwarding 指针的作用与栈→堆复制后两份 byref 的指向；能列出 ARC 下自动 copy 的场景；能论证「什么时候不该用 weak self」并给出替代方案。
  • 100 分：能从 isa 推导出「Block 是对象」的全部后果；能对比 Block 与 delegate / Notification / Task 的选型边界；能为任意回调 API 定义执行队列、取消语义、逃逸性三契约；能指出「过度 weak 导致副作用静默丢失」这类隐蔽缺陷，并把所有权从 VC 迁移到合适的长生命周期对象。
