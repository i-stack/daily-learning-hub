NSProxy：消息代理与弱代理设计

动态系统 · 2026-08-21 · NSProxy / 消息代理 / 弱代理 / forwardInvocation / methodSignatureForSelector / NSTimer 循环引用 / 多播代理 / introspection
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准参考资料

NSProxy 是一个几乎不实现任何方法的抽象基类，消息进来直接落入转发流程，因此天生适合做代理。本课讲清它与 NSObject 子类做代理的本质差异、forwardInvocation 的必答接口与 target 消失后的返回值语义，并用它打断 NSTimer / CADisplayLink 的强引用环——同时指出一个常被误解的事实：弱代理只是让宿主有机会执行 deinit，Timer 仍然需要 invalidate。

01 背景与 API

要解决的问题

两个真实痛点：

痛点一：NSTimer / CADisplayLink 的循环引用。

RunLoop ──strong──> NSTimer ──strong──> target(VC) ──strong──> NSTimer

NSTimer 强持有 target，而 VC 通常又要持有 timer 才能 invalidate。把 delegate 改成 weak 没用——因为强引用来自 timer 那一侧，改 VC 的属性修饰符合毫无影响。

痛点二：需要一个「透明中间人」。

希望某个对象在不改变类型、不实现协议方法的前提下：把消息转给多个目标、做懒加载占位、或在目标不存在时安全静默。

NSProxy 同时解决这两件事。

NSProxy 是什么

@interface NSProxy <NSObject> {
    Class isa;
}
@end

-| 关键事实 | 说明 | | --- | --- | | 抽象基类 | 不能直接实例化使用 | | 遵循 <NSObject> 协议，但不继承 NSObject 类 | 因此没有 NSObject 自带的那几百个方法实现 | | 只有一个 ivar：isa | 结构体极简 | | -isProxy 返回 YES | 唯一能可靠识别代理的方式 |

必须实现的方法

方法 要求
-methodSignatureForSelector: 必须实现，基类实现会直接抛异常
-forwardInvocation: 必须实现，基类实现会直接抛异常

这两个方法在 NSProxy 里的默认实现调用 _NSRequestConcreteImplementation —— 也就是说，忘记实现它们的后果是崩溃，而不是「转发失败」。

与 NSObject 子类做代理的差别

维度 NSProxy 子类 NSObject 子类
自带方法数量 极少 几百个（description、isEqual:、valueForKey:、KVC、KVO…）
消息是否被自带方法截获 几乎不会 会（如 valueForKey: 被 NSObject 接住）
转发起点 几乎全部消息都进转发 只有 NSObject 没有的消息才进转发
适用场景 纯代理、多播、弱代理 需要 NSObject 全套能力的场合

最小可用实现

@interface WeakProxy : NSProxy
@property (nonatomic, weak, readonly) id target;
- (instancetype)initWithTarget:(id)target;
@end

02 运行机制

一、消息如何穿过 proxy

flowchart TD
    A["向 proxy 发消息"] --> B["isa → WeakProxy 类"]
    B --> C{"本类有实现?"}
    C -- "有（如 isProxy / dealloc）" --> C1["直接执行"]
    C -- 无 --> D["进入转发流程"]
    D --> E["methodSignatureForSelector:"]
    E -- "target 存在" --> F["向 target 取签名"]
    E -- "target 已释放" --> G{"有缓存签名?"}
    G -- 有 --> H["使用缓存签名"]
    G -- 无 --> I["返回 nil → doesNotRecognizeSelector: 崩溃"]
    F --> J["构造 NSInvocation"]
    H --> J
    J --> K["forwardInvocation:"]
    K --> L{"target 是否存活?"}
    L -- 是 --> M["invokeWithTarget: 真正执行"]
    L -- 否 --> N["不执行，把返回值清零后返回"]

二、三个必须自己接管的 introspection 方法

这是 NSProxy 最容易踩的坑：它自己实现了 -respondsToSelector:、-isKindOfClass:、-conformsToProtocol:，而这些实现都不会走转发。

方法 默认行为 后果
respondsToSelector: 只检查 proxy 自身 明明能转发的方法，返回 NO
isKindOfClass: 检查 proxy 的 isa 继承链 proxy isKindOfClass:[Target class] 返回 NO
conformsToProtocol: 检查 proxy 自身 返回 NO

因此一个可用的 proxy 必须显式重写它们：

- (BOOL)respondsToSelector:(SEL)aSelector {
    return [_target respondsToSelector:aSelector];
}

- (BOOL)isKindOfClass:(Class)aClass {
    return [_target isKindOfClass:aClass];
}

- (BOOL)conformsToProtocol:(Protocol *)aProtocol {
    return [_target conformsToProtocol:aProtocol];
}

- (BOOL)isProxy { return YES; }

三、target 消失后的签名问题

这是弱代理最容易被忽略的致命细节：

forwardInvocation: 之前必须先有 NSMethodSignature，而签名通常来自 target。 当 target 已经被释放：[_target methodSignatureForSelector:] = [nil ...] = nil → runtime 直接调 doesNotRecognizeSelector: 崩溃。

注意顺序：崩溃发生在构造 NSInvocation 之前，所以你在 forwardInvocation: 里写的任何防护代码都来不及执行。

三种解法：

解法 做法 评价
缓存签名（推荐） 第一次转发时把 SEL → NSMethodSignature 存进字典 可靠，代价是一点内存
哑签名兜底 target 为 nil 时返回 [NSMethodSignature signatureWithObjCTypes:"v@:"] 危险：签名与实际不符会栈破坏（见 Day 11）
提前 invalidate 在宿主 deinit 里停掉 timer，杜绝 nil 转发 治本，应与上一条同时做

四、返回值的内存语义必须明确

target 已释放时，forwardInvocation: 里不调用 invoke，此时 NSInvocation 的返回值缓冲区是未初始化的内存。调用方（ARC）会把它当作有效对象读取并 retain —— 结果是崩溃或野指针。

必须显式清零：

- (void)forwardInvocation:(NSInvocation *)invocation {
    if (_target == nil) {
        // 按返回值长度清零，对所有类型（对象/标量/大结构体）都安全
        NSUInteger length = invocation.methodSignature.methodReturnLength;
        if (length > 0) {
            void *zero = calloc(1, length);
            [invocation setReturnValue:zero];
            free(zero);
        }
        return;
    }
    [invocation invokeWithTarget:_target];
}

常见写法 void *null = NULL; [invocation setReturnValue:&null]; 对对象返回值能工作，但对 CGRect 这类大结构体会读到 &null 之后的栈内存。用 methodReturnLength + calloc 才是通用正确解。

五、弱代理打破了哪条边

打破前（有环）
  RunLoop ─strong→ Timer ─strong→ VC ─strong→ Timer

打破后（无环）
  RunLoop ─strong→ Timer ─strong→ Proxy ─weak→ VC ─strong→ Timer
                                    ↑
                              这条边是 weak，环断了

结论：VC 的引用计数现在可以归零，deinit 终于有机会执行。 这才是弱代理真正的价值——不是「自动停掉 timer」，而是「让 deinit 里的 invalidate 能跑到」。

03 底层原理

一、根本命题：一个几乎不实现任何方法的类

NSProxy 的设计意图非常极端：它存在的唯一目的就是「什么都不实现」。

NSObject 实现了数百个方法（description、isEqual:、hash、valueForKey:、performSelector:、KVC 全家桶……）。如果你用 NSObject 子类做代理，这些消息会被截获，根本走不到你的 forwardInvocation:。

NSProxy 只保留 NSObject 协议要求的极少数方法（isEqual:、hash、class、superclass、isKindOfClass:、respondsToSelector:、isProxy 等），其余全部落空 → 消息几乎必然进入转发。

这就是它适合做代理的原因：它是一个纯粹的转发入口，而不是一个有默认行为的对象。

二、isa 仍然存在

@interface NSProxy <NSObject> {
    Class isa;
}

NSProxy 的第一个字段就是 isa，所以它仍然参与 objc_msgSend 的正常查找流程。代理对象不是绕过 runtime 的特殊存在，只是「查找必然失败 → 必然进入转发」的一个普通对象。

用 object_getClass(proxy) 能拿到真实的 proxy 类；[proxy class] 若你没转发，会返回 proxy 自己的类（与 KVO 隐瞒身份的写法相反）。

三、为什么 respondsToSelector: 不转发

这是设计选择而非遗漏：

  • 如果 respondsToSelector: 走转发，那么「询问能力」这个动作本身就会变成「执行动作」，语义被破坏；
  • runtime 的默认实现（class_respondsToSelector）只查方法列表，不触发转发——NSObject 与 NSProxy 都遵守这个规则。

代价就是：代理必须自己把 introspection 方法转发一遍，否则整个类型系统对它是失效的。这直接导致「NSProxy 无法完全冒充 target」这一根本限制。

四、Timer 的真实引用关系

谁持有谁？
  RunLoop  ──strong──>  NSTimer        （scheduledTimer 会被 RunLoop 持有）
  NSTimer  ──strong──>  target          （文档明确：timer 强持有 target）
  VC       ──strong──>  NSTimer         （为了 invalidate，通常自己存一份）

只要 VC 持有 timer、timer 持有 VC，环就成立。把 VC 的 timer 属性改成 weak 没有用——因为 RunLoop → Timer 这条边保证了 timer 活着，VC 仍被强持有。

唯一有效的切入点是把 Timer → target 这条边变弱，而这正是 proxy 做的事。

五、Swift 中的等价写法

Swift 里没有 NSProxy，但可以用同样的思路：

final class WeakProxy: NSObject {
    weak var target: NSObjectProtocol?
}

或者更简单——iOS 10+ 的 block 型 Timer API + [weak self]：

timer = Timer.scheduledTimer(withTimeInterval: 1, repeats: true) { [weak self] _ in
    self?.tick()
}
// deinit 里仍然要 invalidate
deinit { timer?.invalidate() }

这条路径优先于 NSProxy：不需要处理签名、不需要转发、类型安全。

04 设计与取舍

一、Apple 为什么提供 NSProxy

约束：需要一个「没有默认行为的对象」来承载纯转发的语义。

候选方案 问题
用 NSObject 子类 几百个自带方法会截获消息，转发不纯粹
用 id + 手写转发 没有统一的基类契约
抽象出 NSProxy 只有 isa 和转发契约，语义最干净 → 被选中

换来什么：

  • 透明的中间人：不需要改协议、不需要改 target 的类型；
  • 可以打断第三方/系统 API 的强引用（timer、displayLink）；
  • 天然支持多播（一个 proxy 转发给多个目标）；
  • 支持懒加载占位与 Mock 测试。

付出什么：

  • 类型系统失效：isKindOfClass:、conformsToProtocol:、respondsToSelector: 必须手动转发；
  • 签名契约转移到运行时：必须自己提供 NSMethodSignature，写错就是栈破坏；
  • target 消失语义模糊：返回什么？静默？崩溃？必须由你定义；
  • 性能：每次调用都走完整的 NSInvocation 转发（Day 11）；
  • 可调试性：调试器里看到的是 proxy，po 出来的类名具有误导性。

二、方案选择

需求 推荐方案 理由
打断 Timer 循环引用 Timer block API + [weak self]（iOS 10+） 类型安全、无签名问题
需要支持 iOS 9 及以下 weak proxy + deinit 中 invalidate 兼容旧系统
多播代理 NSProxy 或 NSHashTable + 显式遍历 前者透明，后者类型安全
懒加载占位 NSProxy 典型场景
单元测试 Mock 专门的 mock 框架 比手写 proxy 可靠
代理给单一目标 组合（持有对象 + 显式转发方法） 最清晰，能用编译期检查

判断原则：`NSProxy` 是「当你无法修改调用方、又必须插入一个中间人」时的最后手段。能显式写代码转发，就不要用运行时转发。

三、架构定位

代理是基础设施层的工具，不应出现在业务代码里：

  • 收敛在一个 WeakProxy 类里，全项目共用；
  • 任何需要传 proxy 给外部 API 的地方，都要先确认该 API 不会对 target 做类型断言；
  • 代理不能替代正确的生命周期管理：它只是把「无法释放」变成「可以释放」，真正的清理逻辑仍在 deinit 里。

四、与相邻知识的连接

  • Message Forwarding（Day 11）：NSProxy 完全依赖三阶段转发，且跳过了阶段一（动态解析由 proxy 类自己决定）。
  • ARC（Day 2）：弱代理是为打破引用环而生，核心是 weak 的那条边。
  • Runtime（Day 4）：isa 仍然存在，转发入口仍是 _objc_msgForward。
  • KVO（Day 6）：KVO 不能观察 proxy（真实类不匹配），这是常见的静默失效场景。

05 工程实战

一、一个生产可用的 WeakProxy

@interface WeakProxy : NSProxy
+ (instancetype)proxyWithTarget:(id)target;
@end

@implementation WeakProxy {
    __weak id _target;
    NSMutableDictionary<NSString *, NSMethodSignature *> *_sigCache;
}

+ (instancetype)proxyWithTarget:(id)target {
    WeakProxy *p = [WeakProxy alloc];   // NSProxy 没有 init，不要调 [super init]
    p->_target = target;
    p->_sigCache = [NSMutableDictionary new];
    return p;
}

- (NSMethodSignature *)methodSignatureForSelector:(SEL)sel {
    NSString *key = NSStringFromSelector(sel);
    NSMethodSignature *sig = _sigCache[key];
    if (!sig && _target) {
        sig = [_target methodSignatureForSelector:sel];
        if (sig) _sigCache[key] = sig;      // 缓存，供 target 释放后使用
    }
    return sig;
}

- (void)forwardInvocation:(NSInvocation *)invocation {
    id target = _target;
    if (target) {
        [invocation invokeWithTarget:target];
        return;
    }
    NSUInteger length = invocation.methodSignature.methodReturnLength;
    if (length > 0) {                       // target 已释放：清零返回值
        void *zero = calloc(1, length);
        [invocation setReturnValue:zero];
        free(zero);
    }
}

// introspection 必须手动转发
- (BOOL)respondsToSelector:(SEL)aSelector {
    return [_target respondsToSelector:aSelector];
}
- (BOOL)isKindOfClass:(Class)aClass { return [_target isKindOfClass:aClass]; }
- (BOOL)conformsToProtocol:(Protocol *)p { return [_target conformsToProtocol:p]; }
- (BOOL)isProxy { return YES; }
@end

用法：

self.timer = [NSTimer scheduledTimerWithTimeInterval:1
                                              target:[WeakProxy proxyWithTarget:self]
                                            selector:@selector(tick)
                                            userInfo:nil
                                             repeats:YES];

- (void)dealloc {
    [_timer invalidate];     // 关键：proxy 让 dealloc 能执行，这里才能真正停掉 timer
}

二、多播代理

- (NSMethodSignature *)methodSignatureForSelector:(SEL)sel {
    for (id t in self.targets) {
        NSMethodSignature *sig = [t methodSignatureForSelector:sel];
        if (sig) return sig;
    }
    return nil;
}

- (void)forwardInvocation:(NSInvocation *)invocation {
    for (id t in self.targets) {
        if ([t respondsToSelector:invocation.selector]) {
            [invocation invokeWithTarget:t];   // 同一 invocation 可重复 invoke
        }
    }
}

约定：多播时只有最后一个目标的返回值有意义，需要在文档中明确，或约定被转发的方法一律返回 void。

三、必须验证的四类行为

写单元测试覆盖代理的边界，不要靠「看起来能跑」：

用例 断言
target 存活 转发后 target 真的收到消息（用 spy 记录）
target 释放 target 置 nil 后，proxy 仍能接收消息且不崩溃
返回值语义 target 为 nil 时，返回值是 0 / nil 而非垃圾值；对象返回值不会让 ARC crash
introspection respondsToSelector: / isKindOfClass: / conformsToProtocol: 与 target 一致
isProxy 返回 YES，外部可据此识别代理 
func testTargetReleased() {
    var spy: Spy? = Spy()
    let proxy = WeakProxy(target: spy!)
    (proxy as AnyObject).perform?(NSSelectorFromString("tick"))
    XCTAssertTrue(spy!.called)

    spy = nil                       // 释放 target
    XCTAssertNoThrow(               // 关键：不能崩溃
        (proxy as AnyObject).perform?(NSSelectorFromString("tick"))
    )
}

四、调试技巧

  • po proxy 显示的是 proxy 类，要看真实 target 用 po [proxy target]；
  • 用 object_getClass(proxy) 确认实例没有被 KVO 改写 isa；
  • 在 forwardInvocation: 打断点，能看清每次转发的 SEL；
  • 若发现消息没进来，优先检查 methodSignatureForSelector: 是否返回了 nil。

五、工程护栏

  1. 全项目只有一个 WeakProxy 实现，不要各处复制粘贴。
  2. 绝不把 proxy 传给会做类型断言的 API（KVO、需要真实类的 delegate 回调、NSNotification 的 object 参数）。
  3. deinit 里仍然要 invalidate——proxy 不是「自动清理」。
  4. 高频调用路径不用 proxy：每次都是一次完整的 NSInvocation 转发。
  5. 多播代理约定返回 void，避免返回值歧义。

06 常见坑与反思

高频坑位表

坑 成因 症状 规避
未实现 methodSignatureForSelector: 基类实现直接抛异常 调用即崩溃 必须实现
target 释放后返回 nil 签名 [nil methodSignature...] = nil 崩溃在构造 invocation 之前，防护代码来不及跑 缓存签名
返回值未清零 不 invoke 时缓冲区未初始化 野指针 / 随机崩溃 methodReturnLength + calloc
respondsToSelector: 返回 NO 默认不转发 能力判断全部失效 手动重写并转发
isKindOfClass: 返回 NO 检查的是 proxy 的 isa 链 类型判断失效、断言失败 手动重写并转发
以为 proxy 会自动停 timer RunLoop 仍持有 timer timer 继续 fire deinit 里 invalidate
把 proxy 当 target 传给 KVO 真实类不匹配 观察静默失效 不用 proxy 做 KVO target
proxy 自己没人持有 只被局部变量引用 消息无人接收 用属性强持有 proxy
多播返回值覆盖 多个 target 都写返回值 结果不确定 约定返回 void
[super init] NSProxy 没有可用的 init 编译/运行异常 只用 alloc 后自己初始化
高频路径使用 NSInvocation 开销 掉帧 热路径改用直接调用
调试误导 po 显示 proxy 类 排查方向跑偏 object_getClass + 查 target

三条反思

  1. target 消失后的返回语义必须明确定义。 「静默失败」和「崩溃」都是可接受的设计，但「未定义」不是。写 proxy 时第一件事就是回答：target 不在时，这次调用应该返回什么？
  2. 代理不能替代正确的生命周期管理。 弱代理只是把「VC 永远无法 dealloc」变成「VC 能 dealloc」，它没有替你清理 timer。如果你用了 proxy 却不在 deinit 里 invalidate，泄漏只是换了个形式：从「对象泄漏」变成「timer 空转 + 无效回调」。
  3. 能用编译期方案就别用运行时转发。 组合、显式协议、block API 都能解决同样的问题，而且有类型检查。NSProxy 的价值在于你无法修改调用方时才成立——把它当常规工具，等于主动放弃编译器能给你的保护。

  13. 什么条件下你会拒绝使用 NSProxy，改用组合、协议或 block API？

08 掌握标准

一句话总结：NSProxy 是一个只含 isa、几乎不实现任何方法的抽象基类，消息必然落入 methodSignatureForSelector: + forwardInvocation: 的转发流程，因此适合做透明的中间人；用它弱持有 target 可以打断 RunLoop → Timer → target 的强引用环——但真正停止 timer 仍然要在 deinit 里 invalidate，代理只是让 deinit 有机会执行。

掌握标准：

  • 60 分：能说清 NSProxy 与 NSObject 的本质差异；能实现 methodSignatureForSelector: 与 forwardInvocation:；能画出 Timer 循环引用链条并说明弱代理打破的是哪条边。
  • 80 分：能写出生产可用的 WeakProxy（含签名缓存、返回值清零、introspection 转发）；能定位「target 释放后崩溃」与「respondsToSelector: 失效」两类故障；能为代理写出覆盖四类边界行为的单元测试。
  • 100 分：能解释 NSProxy 为何不默认转发 introspection 方法；能论证「代理不替代生命周期管理」；能在 NSProxy / block API / 组合 / 协议之间做出有理据的选型；能指出把 proxy 用于 KVO、高频调用、类型断言 API 时的具体风险，并把它收敛在基础设施层。
