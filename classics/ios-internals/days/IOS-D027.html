IOS-D027

App 生命周期：进程、Scene、前后台与系统调度

系统生命周期 · 2026-09-20 · UIApplicationDelegate / UISceneDelegate / Scene / 后台执行 / Suspension / BGTaskScheduler
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准参考资料

将进程生命周期与多 Scene 的界面生命周期分开理解，建立前后台切换、挂起与后台任务的资源管理边界。

01 背景与 API

背景、API 与场景：用户切出 App、锁屏、分屏开多个窗口或系统因内存压力回收进程时，业务常要保存编辑状态、暂停动画和恢复任务。UIKit 中 UIApplicationDelegate 负责应用启动等进程级事件；采用 Scene 生命周期的 App 通过 UISceneDelegate 处理每个界面实例的连接、激活、进入后台和断开。iOS 13 起支持 Scene，但是否启用取决于 App 配置；不能假定所有 App 都会收到相同的回调组合。

02 运行机制

运行机制：一个进程可承载多个 Scene，各 Scene 可以分别处于前台活动、前台非活动或后台。Scene 连接时构建其 UI；变为活动时允许用户交互；失去活动状态时收敛实时工作；进入后台时保存可恢复状态并释放非必要资源。后台 Scene 可被系统断开，后台进程也可能被挂起或终止；终止前不保证一定回调，因此持久化不能只押在“退出时”。进程仍存活不代表所有 Scene 可见，一个 Scene 进入后台也不等于整个进程马上终止。后台继续执行必须走系统允许的策略，普通定时器不能保证挂起后运行。

03 底层原理

底层原理是所有权与调度边界：进程拥有共享服务和内存，Scene 拥有窗口、导航与界面状态，系统决定可见性、CPU 预算和恢复时机。前台获得更高交互优先级；后台应尽量少做工作，挂起后普通代码不继续执行。系统可以在资源紧张时回收已挂起进程，所以业务状态必须可持久化，网络请求与 UI 回写必须能识别 Scene 身份及生命周期。具体回调顺序应以当前 Scene 配置和设备实测为准，不把单次观察写成系统保证。

04 设计与取舍

Apple 的设计动机：Scene 将单进程与多窗口 UI 解耦，支持同一 App 中不同窗口独立显示、隐藏与恢复。App Delegate 仍是启动和进程级协调入口，Scene Delegate 则管理特定界面的状态。架构上，账户、持久化和共享网络服务归进程级依赖，窗口导航和未提交的编辑草稿归 Scene 级状态；后台任务使用 beginBackgroundTask、BackgroundTasks 框架或对应能力时要遵守各自有限时长和调度契约，不能把它们当永久保活手段。

05 工程实战

工程实战：一、在 App Delegate 与 Scene Delegate 关键回调中记录进程标识、Scene session 标识、时间和状态；二、将可恢复草稿在编辑过程及进入后台时增量保存，而不只依赖终止回调；三、Scene 失活时暂停动画、显示链路或不必要的高频采样；四、异步结果回写前检查目标 Scene 与模型身份，断开后取消 Scene 所属任务；五、在 iPad 多窗口、锁屏、任务切换、系统杀进程后重启等场景验证状态恢复；六、需要后台运行时按任务性质选择有限延续、后台 URLSession 或 BackgroundTasks，并记录过期和取消。

06 常见坑与反思

常见坑：把 applicationDidEnterBackground 当成每个窗口的唯一入口；认为 sceneDidDisconnect 就等于进程退出；在 willTerminate 才保存关键数据；假设后台定时器可持续运行；为保活滥用后台能力；Scene 已关闭却让网络回调改写全局“当前窗口”；把内存警告等同于必然终止。反思：当前项目的 UI 状态、共享服务和未提交草稿分别属于进程还是某个 Scene？

07 知识验收

  1. 进程生命周期与 Scene 生命周期有什么区别？为什么一个进程可能同时有多个状态不同的 Scene？
  2. 为什么不应只在终止回调里保存用户数据？
  3. sceneDidEnterBackground、sceneDidDisconnect 与进程被系统终止之间是什么关系？
  4. 如何防止已关闭 Scene 的异步结果回写到另一个窗口？
  5. 普通后台定时器为何不能被当成可靠调度机制？应如何选择后台执行策略？
  6. 面试题：从点击图标、创建 Scene、前后台切换到挂起与恢复，描述谁负责回调、谁拥有状态、哪些顺序不能假定。

08 掌握标准

一句话总结：进程管理共享资源，Scene 管理可独立变化的界面，后台运行由系统授予而非 App 自行保证。掌握标准：60 分能区分 App 与 Scene 回调；80 分能在多窗口和进程回收后恢复状态；100 分能设计具备明确所有权、取消边界和后台调度验证的生命周期架构。
