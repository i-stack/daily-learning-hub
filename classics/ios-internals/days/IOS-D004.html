IOS-D004

Runtime：Objective-C 动态能力的根基

动态系统 · 2026-08-13 · Runtime / objc_msgSend / isa / 元类 / cache_t / class_ro_t / Tagged Pointer / Type Encodings / objc4
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准参考资料

Runtime 把「调用哪个方法」从编译期推迟到运行期。本课从 objc_object / objc_class 的内存布局出发，打通 isa、元类、cache_t 与 objc_msgSend 的查找链路，说明 KVO、Category、Swizzling、字典转模型等上层能力共同的底层支点，并给出可复现的观察实验与工程护栏。

01 背景与 API

要解决的问题

C 语言的函数调用在编译期就已经绑定地址：编译器知道 `foo()` 跳到哪里。但 Objective-C 需要的是「运行时才知道该执行什么」——因为方法可以被分类添加、可以被 KVO 替换、可以被转发给别的对象的、甚至可以在运行时凭空生成。

Runtime（libobjc.A.dylib，苹果开源为 objc4）就是支撑这套动态性的运行时库。它不是可选组件，而是每一个 OC 方法调用都要经过的必经路径。

三个层次

层次 内容 例子
语言层 编译器把语法翻译成 runtime 调用 [obj foo] → objc_msgSend(obj, @selector(foo))
API 层 objc/runtime.h 暴露的 C 函数 class_addMethod、method_exchangeImplementations
实现层 汇编与 C 的查找逻辑 _objc_msgSend、lookUpImpOrForward、cache_t

核心类型

类型 定义 说明
id struct objc_object * 任何对象；没有 *
Class struct objc_class * 类对象
SEL struct objc_selector * 选择器，本质是 uniquing 后的字符串地址
IMP id (*)(id, SEL, ...) 方法实现指针
Method struct method_t * 方法对象（SEL + types + IMP）

常用 API 全景

类别 API
类与元类 object_getClass、class_getSuperclass、class_isMetaClass、objc_allocateClassPair / objc_registerClassPair、objc_getMetaClass
方法 class_getInstanceMethod、class_getClassMethod、class_addMethod、class_replaceMethod、method_getName、method_getImplementation、method_getTypeEncoding、method_setImplementation、method_exchangeImplementations、class_respondsToSelector
列表遍历 class_copyMethodList、class_copyIvarList、class_copyPropertyList、class_copyProtocolList、protocol_copyMethodDescriptionList
成员变量 object_setIvar、object_getIvar、ivar_getName、ivar_getTypeEncoding、class_getInstanceVariable
关联对象 objc_setAssociatedObject / objc_getAssociatedObject / objc_removeAssociatedObjects
选择器 sel_registerName、NSSelectorFromString、NSStringFromSelector
底层入口 objc_msgSend（需强转后调用）、objc_msgSendSuper、class_getMethodImplementation

现代 runtime（Objective-C 2.0，macOS 10.5 / iOS 起）中，分类可以加方法、类支持动态添加方法、ivar 布局可变（fragile ABI 已成历史）。iPhone 上只有 modern runtime。

一个最小例子

unsigned int count = 0;
Method *list = class_copyMethodList([Person class], &count);
for (unsigned int i = 0; i < count; i++) {
    NSLog(@"%@ %s", NSStringFromSelector(method_getName(list[i])),
          method_getTypeEncoding(list[i]));
}
free(list);   // copy 系列 API 必须手动 free

02 运行机制

一、对象的内存布局

每个 OC 对象（实例）的第一个字段就是 isa：

struct objc_object {
    isa_t isa;      // 不是简单的 Class 指针
};

类对象本身也是对象，它的 isa 指向元类：

struct objc_class : objc_object {
    Class superclass;
    cache_t cache;             // 方法缓存
    class_data_bits_t bits;    // 通过 FAST_DATA_MASK 取 class_rw_t
};

二、isa 的演进：从指针到位域

早期：isa 直接存 Class 地址。

arm64 之后：isa 是 non-pointer isa——一个 64 位整数，只有中间 33 位是真正的类地址：

bit 0     nonpointer        是否启用非指针 isa（1 = 是）
bit 1     has_assoc         是否有关联对象
bit 2     has_cxx_dtor      是否有 C++ 析构
bit 3..35 shiftcls          类地址（33 位）
bit 36..41 magic            校验位
bit 42    weakly_referenced 是否被 weak 指向
bit 43    deallocating      是否正在释放
bit 44    has_sidetable_rc  引用计数是否外挂到 SideTable
bit 45..63 extra_rc         引用计数（19 位）

取类必须做掩码：class = isa & ISA_MASK（arm64 上 0x0000000ffffffff8ULL）。

直接后果：老代码里 (Class)obj->isa 在 arm64 上是错的，必须用 object_getClass(obj)；arm64e 上 shiftcls 还带 ptrauth 签名。

三、Tagged Pointer：连对象都不分配

小对象（NSNumber、NSDate、短 NSString）的值直接编码在指针里，不分配堆内存：

NSNumber *n = @(42);
// 0xb0000000000002a2 —— 最高位为 1，值 42 就在指针里
  • arm64 上最高位（1<<63）为 1 表示 tagged pointer；
  • iOS 14 起苹果加了 objc_debug_taggedpointer_obfuscator 做异或混淆，所以启动时打印的地址每次运行都不同；
  • Tagged pointer 对象没有 isa、不走消息查找的完整流程，也没有引用计数——这直接影响 KVO 与方法交换能否生效。

四、类的数据：clean 与 dirty 的分离

class_data_bits_t  --(FAST_DATA_MASK)-->  class_rw_t
                                              ├── ro()  -> class_ro_t   （干净内存：类名、ivar 布局、原始方法列表）
                                              └── ext() -> class_rw_ext_t（脏内存：runtime 添加的方法/属性/协议）
  • clean memory（class_ro_t，read-only）：编译期产生，可被多个进程共享、可换出。
  • dirty memory（class_rw_ext_t）：只有在 runtime 修改过类（加方法、加分类、swizzle）时才分配。

这个分离是苹果优化内存的核心手段之一：绝大多数类的 rw_ext 从未被创建。

五、消息查找链路

flowchart TD
    A["objc_msgSend(receiver, sel, ...)"] --> B{"receiver 为 nil?"}
    B -- 是 --> B1["返回 nil / 0，安全结束"]
    B -- 否 --> C{"Tagged Pointer?"}
    C -- 是 --> C1["走 tagged 专用路径"]
    C -- 否 --> D["CacheLookup：cache_t 哈希查找"]
    D -- 命中 --> E["TailCallCachedImp：直接跳转 IMP"]
    D -- 未命中 --> F["__objc_msgSend_uncached"]
    F --> G["MethodTableLookup"]
    G --> H["lookUpImpOrForward 慢速查找"]
    H --> I["本类 method_list 二分查找"]
    I -- 命中 --> J["log_and_fill_cache 回填 cache_t"]
    J --> E
    I -- 未命中 --> K{"有 superclass?"}
    K -- 是 --> L["父类 cache + method_list"]
    L --> I
    K -- 否 --> M{"尝试过动态解析?"}
    M -- 否 --> N["resolveInstanceMethod: 后重试"]
    N --> I
    M -- 是 --> O["__objc_msgForward_impcache 进入转发"]

三个阶段各自的特点：

阶段 实现 成本
缓存查找 汇编 CacheLookup，哈希 + 线性探测 几条指令
慢速查找 C 函数 lookUpImpOrForward，二分查找 数十~数百纳秒，且只发生一次
转发 ___forwarding___ 慢 1~2 个数量级（见 Day 11）

关键事实：慢速查找的结果会回填 cache_t，所以同一个方法第二次调用就是缓存命中。这是 runtime 性能可接受的根本原因。

六、cache_t 与 method_list

  • cache_t：哈希表，bucket_t 存 sel + imp。占用超过容量的 3/4 时会扩容（翻倍）并清空旧桶。arm64 上用 _bucketsAndMaybeMask 一个 64 位字段同时编码桶数组地址与掩码。
  • method_list_t：按 SEL 排序的有序数组，查找用二分。iOS 14 起 arm64 使用 relative method lists——内部存 int32 相对偏移而非绝对指针，省内存但需要 runtime 做地址换算。

03 底层原理

一、根本命题：把绑定推迟到运行期

Runtime 只做一件事：把「SEL → IMP」这张表的查询，从编译期推迟到运行期。

一旦查询发生在运行期，就自然获得了这些能力：

能力 依赖的机制 对应课程
Category 添加方法 运行时往 class_rw_ext_t 插入 method Day 8
关联对象 运行时在外部表挂数据 Day 9
Method Swizzling 运行时改 method_t.imp Day 10
KVO 运行时换 isa Day 6
消息转发 查找失败后的兜底 Day 11
字典转模型 / 归档 遍历 ivar / property 列表 本课

换句话说：Day 6 到 Day 12 的所有内容，都建立在本课这一张表的可修改性上。

二、isa 走位与元类

flowchart TD
    subgraph 实例
        I["实例对象"]
    end
    subgraph 类
        C["类对象 Person"]
    end
    subgraph 元类
        M["元类 Person meta"]
        RM["根元类 NSObject meta"]
    end
    N["NSObject 类"]
    I -- isa --> C
    C -- isa --> M
    M -- isa --> RM
    RM -- isa --> RM
    C -- superclass --> N
    M -- superclass --> N
    N -- isa --> RM

三条必须记住的规则：

  1. 实例方法存在类里，类方法存在元类里（类方法本质是元类的实例方法）。
  2. 任何元类的 isa 都指向根元类，根元类的 isa 指向自己。
  3. 元类的 superclass 链最终指向 NSObject 类——这就是为什么「给 NSObject 加分类」能同时影响所有类方法。

验证：

Person *p = [Person new];
object_getClass(p);                     // Person（类）
object_getClass([p class]);             // Person meta（元类）
object_getClass(object_getClass([p class])); // NSObject meta（根元类）
class_isMetaClass(object_getClass([p class])); // YES

三、objc_msgSend 的实现要点

_objc_msgSend 是汇编实现的，入口在 objc-msg-arm64.s：

  1. 从 x0（receiver）取 isa → Class；
  2. 取 cache 的 buckets 与 mask，用 sel（x1）做哈希；
  3. 命中 → TailCallCachedImp 直接跳转，不回 C；
  4. 未命中 → 跳 __objc_msgSend_uncached → MethodTableLookup → 调 C 函数 _lookUpImpOrForward。

调试技巧：arm64 上 receiver 在 x0、SEL 在 x1，所以 objc_msgSend 符号断点里可以 po (id)$x0、p (SEL)$x1。

四、lookUpImpOrForward 慢速查找

lookUpImpOrForward(cls, sel, inst, behavior)
  1. 若类未 realize → realizeClassMaybeSwiftAndLeaveLocked
  2. 再查一次 cache（多线程下可能已被别的线程填好）
  3. 本类 method_list 二分查找（findMethodInSortedMethodList）
  4. 沿 superclass 链重复 2~3，直到 nil
  5. 命中 → log_and_fill_cache 回填 → 返回 IMP
  6. 未命中 → 若未尝试过 → _class_resolveMethod（动态解析）→ 回到第 2 步 retry
  7. 仍未命中 → 返回 _objc_msgForward_impcache（进入消息转发）

注意第 6 步的 retry：动态解析成功后会重新走一遍完整查找，这也是「resolveInstanceMethod: 只会被调用一次」的原因——第二次进来时方法已经在列表里了。

五、Type Encodings

每个方法的 types 字段描述其签名，runtime 与 NSInvocation 都靠它理解参数：

编码 类型 编码 类型
c char @ id / 对象
i int # Class
s short : SEL
l long * char *
q long long ^T T *
f float {name=...} 结构体
d double v void
B bool / _Bool ? 未知（函数指针）

例：- (void)setName:(NSString *)name 的编码是 v24@0:8@16 —— 返回 void、共 24 字节、self 在 0、_cmd 在 8、参数在 16。

六、Runtime 的启动

dyld 装载镜像时触发 _objc_init，注册三个回调：

回调 时机 干什么
map_2_images 镜像映射 注册类、注册分类、修正 selector 唯一性
load_images 镜像装载完 调用 +load
unmap_image 镜像卸载 清理

_objc_init 之前还有 sel_init（选择器表初始化）与 cache_init。所有类的注册、+load 的调用都发生在 main() 之前。

04 设计与取舍

一、Apple 的取舍

选择：把方法绑定从编译期挪到运行期。

换来什么：

  • 极强的表达能力：分类、KVO、Swizzling、转发、依赖注入、字典转模型、JSON 映射、Core Data 的 faulting、甚至 JSPatch 热修——全部建立在这一个决策上；
  • 向后兼容的 ABI 演进：类的内存布局可推迟到加载时确定；
  • 与 Smalltalk 一脉相承的「一切皆消息」的一致性。

付出什么：

  • 性能：每次调用多一次查表。缓存命中约几条指令，未命中要走 C 的慢速路径；
  • 编译期检查缺失：unrecognized selector sent to instance 是运行时崩溃，编译器帮不上忙；
  • 优化受阻：消息调用无法内联、无法做跨函数优化；
  • 体积：类名、SEL 字符串、类型编码都要进 Mach-O，无法被 strip；
  • 可分析性：调用关系藏在 runtime 里，静态分析工具看不到。

二、苹果的补救措施

问题 补救
查找慢 cache_t 哈希缓存 + 汇编快速路径
对象头开销 non-pointer isa（isa 里塞引用计数等）
小对象分配开销 Tagged Pointer（不分配堆内存）
类内存占用 clean / dirty 内存分离（class_ro_t / class_rw_ext_t）
方法列表体积 relative method lists（int32 偏移）
引用计数性能 extra_rc + SideTable 外挂

这些优化的共同思路是：保留动态性的语义，把常见路径的成本压到接近静态调用。

三、Swift 的反向选择

Swift 把默认派发方式改回了静态：

派发方式 场景
直接调用（静态） struct / final / private 方法
vtable 派发 class 的普通方法
witness table protocol 方法
消息派发 @objc dynamic / 继承 NSObject

结论：Swift 只有在需要 Cocoa 互操作时才回退到 runtime 消息派发。这也解释了为什么 KVO、Swizzling 在 Swift 里都需要显式标注 @objc dynamic（Day 6、Day 10）。

四、与相邻知识的连接

  • Category（Day 8）：分类在 map_images 阶段被插入到方法列表前面，+load 由 load_images 触发。
  • KVO（Day 6）：换 isa 之所以有效，正是因为查找按 receiver 的 isa 走。
  • Message Forwarding（Day 11）：本课链路的第 7 步就是它的入口。
  • Method Swizzling（Day 10）：改的就是慢速查找要查的那张表。

05 工程实战

一、观察实验：看清一个类

- (void)inspect:(id)obj {
    Class cls = object_getClass(obj);          // 真实类（KVO 后能看到动态子类）
    NSLog(@"isa=%@ super=%@ isMeta=%d", cls, class_getSuperclass(cls),
          class_isMetaClass(cls));

    // 继承链
    for (Class c = cls; c; c = class_getSuperclass(c)) {
        NSLog(@"chain: %@", c);
    }

    // 方法列表（copy 系列必须 free）
    unsigned n = 0;
    Method *ms = class_copyMethodList(cls, &n);
    for (unsigned i = 0; i < n; i++) {
        NSLog(@"  %@ %s -> %p", NSStringFromSelector(method_getName(ms[i])),
              method_getTypeEncoding(ms[i]), method_getImplementation(ms[i]));
    }
    free(ms);

    // ivar / property
    unsigned ic = 0; Ivar *ivs = class_copyIvarList(cls, &ic);
    for (unsigned i = 0; i < ic; i++) NSLog(@"  ivar %s %s",
        ivar_getName(ivs[i]), ivar_getTypeEncoding(ivs[i]));
    free(ivs);
}

二、符号断点观察一次真实查找

  1. 下 Symbolic Breakpoint：objc_msgSend；
  2. arm64 上打印：po (id)$x0（receiver）、p (SEL)$x1、p (char *)$x1；
  3. 单步到 TailCallCachedImp 可看到缓存命中；未命中会进入 __objc_msgSend_uncached。

由于 objc_msgSend 调用极频繁，建议先用条件断点限定 $x1 等于目标 SEL，否则调试器会被拖垮。

三、IMP 缓存：把动态调用压到最快

热路径（如列表滚动中反复调用同一方法）可以手动缓存 IMP：

SEL sel = @selector(rowHeight);
IMP imp = method_getImplementation(class_getInstanceMethod(cls, sel));
CGFloat (*fn)(id, SEL) = (CGFloat (*)(id, SEL))imp;   // arm64 上必须强转才能调
for (...) { CGFloat h = fn(model, sel); }

注意：arm64 上不能直接调 objc_msgSend 的 C 声明，必须强转成正确的函数签名，否则 ABI 不匹配会崩。

四、典型生产用途与风险

用途 做法 风险
字典转模型 遍历 property 列表 + KVC 赋值 类型不匹配、KVC 找不到 key 会崩
自动归档 / 序列化 遍历 ivar 逐个 encode 结构体成员需特殊处理
埋点与监控 见 Day 10 全局性
unrecognized selector 兜底 见 Day 11 吞掉编程错误
热修（JSPatch 类） 转发 + JS 引擎 审核风险，苹果明确限制

五、工程护栏

  1. 不依赖私有结构：objc_class、isa_t、cache_t 的字段布局没有 ABI 契约，系统升级即失效。只用于调试，不用于生产。
  2. 遍历列表要 free：class_copyMethodList / class_copyIvarList 返回的数组是 malloc 出来的。
  3. 不在热路径做反射：class_copyMethodList 会拷贝整个列表，成本远高于一次消息查找。
  4. 优先 object_getClass：不要碰 isa 字段（non-pointer isa）。
  5. 动态能力收敛在基础设施：业务代码里出现 objc_msgSend / method_exchangeImplementations，应视为需要评审的信号。

06 常见坑与反思

高频坑位表

坑 成因 症状 规避
(Class)obj->isa 拿到垃圾 arm64 是 non-pointer isa 类名乱码、崩溃 一律用 object_getClass
[obj class] 与真实类不符 KVO 重写了 -class 看不到 NSKVONotifying_（Day 6） 用 object_getClass
class_copyXXX 泄漏 copy 系列返回 malloc 数组 内存持续增长 配对 free
class_addMethod 返回 NO 当失败 返回 NO 表示「本类已有」 逻辑判断反了 理解语义：返回 NO 是探测结果
类/元类混淆 类方法在元类上 hook 类方法不生效 object_getClass(cls)
直接调 objc_msgSend arm64 ABI 要求强转 参数错乱、崩溃 强转成准确签名
Tagged Pointer 上做 KVO/Swizzle 它没有 isa、不走完整查找 静默失效 用 object_getClass 确认真实类
respondsToSelector: 与转发 默认实现不触发消息转发 误判对象「不支持」某方法 需要判断转发能力要显式重写
反射遍历进热路径 拷贝整个方法/属性列表 列表滚动掉帧 一次性缓存结果
NSSelectorFromString 拼错 字符串无编译期检查 运行时崩溃 优先用 @selector

三条反思

  1. 动态能力应收敛在基础设施边界。 业务代码里直接用 runtime 改行为，等于把控制流移出源码——可读性、可测性、静态分析能力同时归零。
  2. 私有实现与全局 Hook 缺乏稳定契约。 NSKVONotifying_、_NSSetXXXValueAndNotify、isa_t 位域都是逆向产物，可以拿来学习，不能拿来依赖。
  3. 「能」不等于「该」。 Runtime 能让你在运行时做任何事；判断标准应该是：如果一年后接手的人读这段代码，能不能在不跑起来的情况下知道会发生什么？

08 掌握标准

一句话总结：Runtime 把「SEL → IMP」的绑定从编译期推迟到运行期——对象经 isa 找到类，objc_msgSend 先查 cache_t 缓存，再沿类层级二分查找 method_list，失败后先做动态解析、最后进入消息转发；正因为这张表在运行期可读可写，KVO、Category、Swizzling、转发与字典转模型才成为可能。

掌握标准：

  • 60 分：能说清 id / Class / SEL / IMP 的定义与 objc_msgSend 的查找链路；知道元类存在的意义；能解释为什么 [obj class] 和 object_getClass(obj) 可能不同。
  • 80 分：能解释 non-pointer isa 的字段与 ISA_MASK 的必要性；能独立用 class_copyMethodList / 符号断点复现一次真实查找；能定位「方法找不到」与「hook 静默失效」两类故障；知道 class_copyXXX 必须 free。
  • 100 分：能讲清 clean / dirty 内存分离、relative method lists、Tagged Pointer 背后的取舍；能列举苹果为压低 runtime 成本所做的具体优化；能判断何时该用编译期方案替代动态能力，并把 runtime 使用收敛在基础设施边界内。
