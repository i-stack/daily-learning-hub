KVO：动态子类与观察机制

动态系统 · 2026-08-15 · KVO / 动态子类 / isa 混写 / NSKVONotifying / observationInfo / context / 集合代理 / 线程语义
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准

从 isa 混写与 NSKVONotifying 动态子类出发，打通 KVO 的注册、setter 改写、通知派发与生命周期边界，并给出可用于面试与排障的最小验证实验。

01 背景与 API

背景、API 与场景：需要在不修改被观察类源码的前提下，让多个观察者拿到属性变化的旧值与新值——典型对象正是 AVPlayerItem.status、WKWebView.estimatedProgress、UIView.bounds 这类源码不在自己手里的系统类。三条候选路径中，delegate 是一对一强契约，且要求被观察方写协议并持有代理；NotificationCenter 是一对多广播，但弱类型、要求被观察方主动 post，也不提供 old/new；只有 KVO 同时满足零侵入、定向一对多、系统代传旧值与新值。核心 API 三件套是 addObserver:forKeyPath:options:context: 注册、observeValueForKeyPath:ofObject:change:context: 统一回调、removeObserver:forKeyPath:context: 解绑。辅助入口包括 +automaticallyNotifiesObserversForKey:（关闭自动通知改为手动触发）、will/didChangeValueForKey:（手动包裹）、+keyPathsForValuesAffecting<Key>（依赖键）、mutableArrayValueForKey:（集合代理），Swift 侧是 iOS 11+ 的 observe(_:options:) 所返回的 NSKeyValueObservation token。options 四个位各有用途：New 给新值、Old 给旧值、Initial 在注册瞬间补发一次（只有 new，用于 UI 首帧填充）、Prior 在变化前额外回调一次（change 中 notificationIsPrior 为真，用于动画准备）。

02 运行机制

运行机制：调用 addObserver:forKeyPath:options:context: 时，系统为被观察对象的类动态创建一个子类 NSKVONotifying_XXX，重写被观察属性的 setter 以及 class、dealloc、_isKVOA，再用 object_setClass 把该实例的 isa 指向这个子类；子类只创建一次并全局复用，被改动的始终只是这一个实例。此后 p.name = x 仍编译为对 setName: 的调用，但经 isa 查表命中子类实现：先 willChangeValueForKey:，再调用 super 的 setter 真正赋值，最后在 didChangeValueForKey: 处取出观察者链表，逐个同步回调 observeValueForKeyPath:ofObject:change:context:。于是三个现象可以一次性解释：[p class] 仍返回 Person，是因为 -class 被重写以隐瞒身份；_name = x 不触发，是因为它绕过了全部方法派发；移除最后一个观察者后 isa 指回原类，但已注册的子类本身不会销毁。

03 底层原理

底层原理：KVO 建立在 ObjC 消息派发与 KVC 的键约定之上。objc_msgSend 按 receiver 的 isa 查找方法，因此只要换掉 isa，就能让同一句 p.name = x 命中另一份 setter 实现——这是消息机制留给 KVO 的天然后门，也正因如此，纯 Swift 属性必须标注 @objc dynamic 才能被观察，而 struct 因为没有 isa 根本无法支持 KVO。系统按 KVC 的 setter 命名约定定位并替换 setKey:，改写后的实现按属性类型分派到 Foundation 的私有通知函数（如 _NSSetObjectValueAndNotify、_NSSetIntValueAndNotify），其内部顺序是 willChange → 调用原类实现 → didChange → 遍历观察者同步回调；由于调用的是 super 的实现，开发者自己在原类里写的 setter 逻辑不会丢失。观察关系记录在 NSObject 的 observationInfo 所指向的观察信息表中，KVO 不持有 observer，因此既不产生循环引用，也不会在 observer 释放时自动解绑。集合属性必须经 mutableArrayValueForKey: 拿到 KVC 代理对象操作，由代理在插入前后发出 will/didChange:valuesAtIndexes:forKey:，回调中 kind 为 Insertion、Removal 或 Replacement，并带 indexes。通知没有队列语义，始终同步派发在属性被改变的那个线程。

04 设计与取舍

Apple 设计动机与架构：约束是「在不修改被观察类源码、不影响其他实例的前提下观察属性变化」，isa 混写是当时代价最小的解。换来的是：粒度细到单个实例，比类级 method swizzling 更安全，不会污染所有实例也不会与其他 Hook 打架；零侵入，可以观察 AVPlayerItem、WKWebView 等系统类；与 KVC、Bindings、Core Data 共用同一套键约定；old/new/kind/indexes 由系统代传。付出的是：调用方看不见谁在观察，隐式控制流难以推理；强制走 setter，逼着内部状态暴露成属性，团队里一句 _ivar = x 就能让通知静默失效；keyPath 是字符串，重构改名要到运行时才暴露；每次赋值都多一层消息转发、will/did 包裹与 change 字典构造，高频写入有实打实的开销；生命周期契约只能靠人守住。架构上 KVO 应收敛在基础设施边界，只做轻量通知（驱动 UI 刷新），不承担领域状态机与跨页面状态；Swift 侧有了编译期插桩的 @Observable 与类型安全的 Combine 之后，KVO 已退化为兼容 Cocoa 的过渡方案。

05 工程实战

工程实战：一、用最小实验证明动态子类确实存在，而不是停留在背诵结论。

- (void)dumpMethods:(Class)cls {
    unsigned int count = 0;
    Method *list = class_copyMethodList(cls, &count);
    for (unsigned int i = 0; i < count; i++) {
        NSLog(@"%@ -> %p", NSStringFromSelector(method_getName(list[i])),
              method_getImplementation(list[i]));
    }
    free(list);
}

Person *p = [Person new];
NSLog(@"%@", object_getClass(p));   // Person
[p addObserver:self forKeyPath:@"name"
      options:NSKeyValueObservingOptionNew context:MyCtx];
NSLog(@"%@", object_getClass(p));   // NSKVONotifying_Person
NSLog(@"%@", [p class]);            // Person（-class 被重写，隐瞒身份）
[self dumpMethods:object_getClass(p)];  // setName: / class / dealloc / _isKVOA

二、context 必须传且用静态地址，回调里先判 context 再分 keyPath，不是自己的交回父类。

static void * const MyCtx = (void *)&MyCtx;

- (void)observeValueForKeyPath:(NSString *)keyPath
                      ofObject:(id)object
                        change:(NSDictionary *)change
                       context:(void *)context {
    if (context != MyCtx) {   // 父类或框架注册的同名 keyPath，不能吞掉
        [super observeValueForKeyPath:keyPath ofObject:object
                              change:change context:context];
        return;
    }
    if ([keyPath isEqualToString:@"name"]) { /* 更新 UI */ }
}

// Swift：token 释放即自动解绑，这是目前最安全的写法
@objc dynamic var name: String = ""
let token = model.observe(\.name, options: [.initial, .new]) { _, change in ... }

三、观察集合内容变化时，直接 addObject: 不触发，必须经 KVC 代理对象。

[self.items addObject:x];                                  // 不触发：未走 setter
[[self mutableArrayValueForKey:@"items"] addObject:x];     // 触发：kind=Insertion + indexes

四、三条可验证断言：只给 p1 加观察，object_getClass(p2) 仍是 Person，证明只影响单个实例；在回调里打印 [NSThread currentThread]，配合后台队列赋值，验证通知线程等于改变线程；在 Person 内部加一个直接写 _name 的方法，验证回调不进来。五、生产规则：解绑必须绑定生命周期（dealloc、FBKVOController 或 Swift token），KVO 只同步 UI 或触发轻量刷新，不放网络请求与状态机。

06 常见坑与反思

常见坑与反思：直接给成员变量赋值不触发通知，而且这类失效不会抛错、只会静默不生效，是最难查的一类；observer 不被 retain，忘记 remove 会在 observer 释放后向悬垂指针发消息，重复 remove 或 context 不匹配则直接抛异常；通知同步派发在改变发生的线程，回调里直接改 UI 会出问题；对集合属性直接 addObject: 不触发；把 KVO 当命令总线会隐藏控制流，一旦出问题几乎无法从调用栈反推，因此不宜承载复杂领域状态；NSKVONotifying_ 前缀、_isKVOA、_NSSetXXXValueAndNotify 都是逆向得到的实现细节而非 API 契约，可以用来学习和调试，绝不能在生产代码里依赖。反思：这个观察关系的所有者是谁，它在什么时机被释放，如果改成显式事件或 @Observable，代码会不会更容易验证？

08 掌握标准

一句话总结：KVO 用 isa 混写把被观察实例指向系统动态生成的 NSKVONotifying_ 子类，在子类重写的 setter 中以 will/didChange 包裹原实现并同步派发通知，从而零侵入地观察任意对象的属性。掌握标准：60 分能说清从 addObserver 到 observeValueForKeyPath 的完整链路，并解释为什么必须用 object_getClass 才能看到动态子类；80 分能独立复现动态子类、验证回调线程与集合 KVO，并定位「改了值却不通知」与「observer 已释放仍回调」两类故障；100 分能讲明 Apple 选择 isa 混写而非类级 swizzling 的取舍，判断何时改用 @Observable 或 Combine，并给出把 KVO 收敛在基础设施边界的架构方案。
