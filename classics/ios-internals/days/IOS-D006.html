KVO：动态子类与观察机制

动态系统 · 2026-08-15 · KVO / 动态子类 / isa 混写 / NSKVONotifying / observationInfo / context / 集合代理 / 线程语义 / 依赖键 / @objc dynamic
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准参考资料

从 isa 混写与 NSKVONotifying 动态子类出发，打通 KVO 的注册、setter 改写、通知派发、依赖键与手动通知，并给出生命周期边界、线程语义与可用于面试和排障的最小验证实验。

01 背景与 API

要解决的问题

需要在不修改被观察类源码的前提下，让多个观察者拿到属性变化的旧值与新值。典型对象正是源码不在自己手里的系统类：AVPlayerItem.status、WKWebView.estimatedProgress、UIView.bounds、NSOperation.isFinished。

三条候选路径的取舍

方案 关系 类型安全 侵入被观察方 old/new 适用场景
Delegate 一对一强契约 强（协议） 要写协议 + 持有代理 需自己传 明确的双向协作
NotificationCenter 一对多广播 弱（字符串名 + userInfo 字典） 需主动 post 需自己传 全局事件广播
KVO 定向一对多 弱（字符串 keyPath） 零侵入 系统代传 观察任意对象的属性变化

只有 KVO 同时满足：零侵入、定向一对多、系统代传旧值与新值。代价是 keyPath 是字符串、控制流隐式。

核心 API

API 作用
addObserver:forKeyPath:options:context: 注册观察
observeValueForKeyPath:ofObject:change:context: 统一回调入口
removeObserver:forKeyPath:context: 解绑
removeObserver:forKeyPath: 解绑（不带 context，不推荐）
observationInfo / setObservationInfo: 读/写对象的观察信息表（调试用）

辅助入口

入口 用途
+automaticallyNotifiesObserversForKey: 返回 NO 关闭自动通知，改为手动触发
willChangeValueForKey: / didChangeValueForKey: 手动包裹赋值，成对调用
+keyPathsForValuesAffecting<Key> 声明依赖键，一个键变化时联动通知其他键
mutableArrayValueForKey: 取 KVC 集合代理对象，让集合内容变化可观察
observe(_:options:)（Swift，iOS 11+） 返回 NSKeyValueObservation token，token 释放即自动解绑

options 四个位

位 效果
NSKeyValueObservingOptionNew change 中带 NSKeyValueChangeNewKey
NSKeyValueObservingOptionOld change 中带 NSKeyValueChangeOldKey
NSKeyValueObservingOptionInitial 注册瞬间补发一次回调，change 中只有 new（用于 UI 首帧填充）
NSKeyValueObservingOptionPrior 变化前额外回调一次，change 中 NSKeyValueChangeNotificationIsPriorKey 为 YES（用于动画准备）

指定 Prior 时回调会变成两次：一次 prior（will 阶段）、一次正式（did 阶段）。

最小可用示例

static void * const MyCtx = (void *)&MyCtx;

[model addObserver:self
        forKeyPath:@"name"
           options:NSKeyValueObservingOptionNew | NSKeyValueObservingOptionOld
           context:MyCtx];

- (void)observeValueForKeyPath:(NSString *)keyPath
                      ofObject:(id)object
                        change:(NSDictionary *)change
                       context:(void *)context {
    if (context != MyCtx) {                       // 不是我的，交回父类
        [super observeValueForKeyPath:keyPath ofObject:object
                              change:change context:context];
        return;
    }
    id oldValue = change[NSKeyValueChangeOldKey];
    id newValue = change[NSKeyValueChangeNewKey];
}

02 运行机制

一、注册时发生了什么

调用 addObserver:forKeyPath:options:context: 后：

  1. 系统为被观察对象的类动态创建一个子类 NSKVONotifying_XXX；
  2. 在子类中重写被观察属性的 setter，以及 class、dealloc、_isKVOA；
  3. 用 object_setClass 把该实例的 isa 指向这个子类。

两个关键限定：子类只创建一次并全局复用（第二个同类实例注册时复用同一个子类）；被改动的始终只是调用 addObserver 的那一个实例，同类的其他实例不受影响。

二、子类重写了什么

方法 重写目的
setName: 等被观察 setter 包裹 will/didChange 并派发通知，内部仍调用 super 实现
class 返回原类，隐瞒动态子类身份
dealloc 清理该实例的观察信息
_isKVOA 供框架内部判断「这是 KVO 类」

注意子类不重写未被观察的属性 setter——只为真正被观察的 keyPath 生成实现。

三、赋值时发生了什么

p.name = x 仍编译为对 setName: 的调用，但经 isa 查表命中子类实现：

p.name = x
  → 子类 setName:（如 _NSSetObjectValueAndNotify）
      → willChangeValueForKey:@"name"
      → [super setName:x]        原类实现真正赋值，自定义逻辑不丢失
      → didChangeValueForKey:@"name"
          → 取出观察者链表，逐个同步回调 observeValueForKeyPath:...

由于调用的是 super 的实现，开发者自己在原类 setter 里写的业务逻辑不会丢失。change 字典就是在这里构造的，kind 为 NSKeyValueChangeSetting（1）。

四、解绑时发生了什么

移除最后一个观察者后，实例 isa 指回原类；但已注册的子类本身不会销毁（类一旦注册就无法安全卸载）。所以一个进程里给 Person 加过观察，NSKVONotifying_Person 会一直存在。

五、三个现象的一次性解释

现象 原因
[p class] 仍返回 Person -class 被重写以隐瞒身份；要看真实类必须用 object_getClass(p)
_name = x 不触发通知 直接写成员变量绕过全部方法派发，根本不进 setter
只给 p1 加观察，p2 不受影响 isa 混写是实例级的，改的是单个对象的 isa 指针

03 底层原理

一、底层支点：消息派发 + isa 可换

objc_msgSend 按 receiver 的 isa 查找方法实现。因此只要换掉 isa，同一句 p.name = x 就能命中另一份 setter 实现——这是消息机制留给 KVO 的天然后门。

由此推出三条硬约束：

  • 纯 Swift 属性必须标注 @objc dynamic，且类需继承 NSObject——否则走静态派发/vtable，isa 换不掉，观察不到。
  • struct / enum 根本无法支持 KVO——值类型没有 isa。
  • Swift 的 willSet / didSet 不是 KVO——它们是编译期插入的调用，只对该属性自己的写入生效，不产生通知。

二、系统如何定位并替换 setter

KVO 依赖 KVC 的键命名约定定位 setter。KVC 写入时的查找顺序：

set<Key>:  →  _set<Key>:  →  setIs<Key>:
   ↓ 都没找到
+accessInstanceVariablesDirectly == YES ?
   ↓
_<key>  →  _is<Key>  →  <key>  →  is<Key>

KVO 只替换方法形态的入口（通常是 set<Key>:），这也是「直接写成员变量不触发」的根源——它连方法都没进。

改写后的 setter 按属性类型分派到 Foundation 的私有通知函数：

属性类型 分派到的私有实现
对象 / id _NSSetObjectValueAndNotify
int / NSInteger _NSSetIntValueAndNotify
其他标量、结构体 对应的 _NSSetXXXValueAndNotify

NSKVONotifying_ 前缀、_isKVOA、_NSSetXXXValueAndNotify 都是逆向得到的实现细节，不是 API 契约。可用于学习与调试，绝不能在生产代码里依赖。

三、观察关系存在哪里

观察关系记录在 NSObject 的 observationInfo 所指向的观察信息表中（对外是 void *，内部结构私有，按 keyPath 组织观察者链表）。

KVO 不 retain observer，也不 retain observed object。 这带来两个直接后果：

  • 不会产生循环引用；
  • observer 释放时不会自动解绑 → 后续 didChange 向已释放对象发消息 → 悬垂指针崩溃。

四、手动通知

+ (BOOL)automaticallyNotifiesObserversForKey:(NSString *)key {
    if ([key isEqualToString:@"name"]) return NO;   // 关闭自动通知
    return [super automaticallyNotifiesObserversForKey:key];
}

- (void)setName:(NSString *)name {
    [self willChangeValueForKey:@"name"];
    _name = [name copy];        // 直接写 ivar 也没关系，通知由我手动发
    [self didChangeValueForKey:@"name"];
}

用途：批量写入时合并成一次通知、只在值真的变化时才通知（自动 KVO 即使赋相同值也会触发）。

必须成对调用，且嵌套不同 key 时配对顺序不能错。

五、依赖键

一个属性的值由其他属性推导而来时，用依赖键让它们联动：

// fullName 由 firstName + lastName 推导
+ (NSSet<NSString *> *)keyPathsForValuesAffectingFullName {
    return [NSSet setWithObjects:@"firstName", @"lastName", nil];
}

底层走 +keyPathsForValuesAffectingValueForKey: 的默认实现——它按 keyPathsForValuesAffecting<Key> 的命名约定去查找。Swift 侧对应：

@objc dynamic class func keyPathsForValuesAffectingFullName() -> Set<String> {
    ["firstName", "lastName"]
}

六、集合属性的观察

集合内容变化（增删替）不会走 setter，因此必须经 KVC 代理对象操作：

[self.items addObject:x];                               // 不触发：未走 setter
[[self mutableArrayValueForKey:@"items"] addObject:x];  // 触发

mutableArrayValueForKey: 返回 NSKeyValueMutableArray 代理，由代理在插入前后发出 will/didChange:valuesAtIndexes:forKey:。回调的 change 字典里：

key 值
NSKeyValueChangeKindKey Insertion(2) / Removal(3) / Replacement(4)
NSKeyValueChangeIndexesKey 变化的 NSIndexSet
NSKeyValueChangeNewKey / OldKey 仅 Replacement / Removal 时有意义

代理对象会优先调用 insertObject:in<Key>AtIndex: 等 KVC 集合访问器（若实现），否则回落到原始可变集合。

七、线程语义

通知没有队列语义，始终同步派发在「属性被改变的那个线程」。

  • 赋值语句在 didChange 处会同步阻塞直到所有观察者回调执行完毕；
  • 后台线程改属性 → 回调在后台线程 → 回调里直接改 UI 会出问题；
  • KVO 本身的 add / remove 也不是线程安全的，多线程并发注册/解绑同一 keyPath 需要外部串行化。

04 设计与取舍

一、Apple 的约束与选择

约束：在不修改被观察类源码、不影响其他实例的前提下观察属性变化。

方案对比：

候选方案 问题
类级 method swizzling 污染该类的所有实例，与其他 hook 打架
要求被观察方配合（delegate / 主动 post） 系统类改不了
isa 混写 + 动态子类 只影响单个实例，零侵入 → 被选中

isa 混写换来什么：

  • 粒度细到单个实例，比类级 swizzling 安全得多；
  • 零侵入，可以观察 AVPlayerItem、WKWebView 等系统类；
  • 与 KVC、Cocoa Bindings、Core Data 共用同一套键约定；
  • old / new / kind / indexes 由系统代传。

付出了什么：

  • 调用方看不见谁在观察，隐式控制流难以推理；
  • 强制走 setter：逼着内部状态暴露成属性，团队里一句 _ivar = x 就能让通知静默失效；
  • keyPath 是字符串，重构改名要到运行时才暴露；
  • 每次赋值都多一层消息查找、will/did 包裹与 change 字典构造，高频写入有实打实的开销；
  • 生命周期契约只能靠人守住。

二、架构定位

KVO 应收敛在基础设施边界：只做轻量通知（驱动 UI 刷新），不承担领域状态机与跨页面状态。判断标准：如果这个观察者回调里开始做「请求网络 + 修改多处状态 + 触发跳转」，就该换成显式事件或响应式管道。

三、Swift 时代的替代方案

方案 机制 类型安全 生命周期
KVO 运行时 isa 混写 弱（字符串 keyPath） 手动解绑，易漏
observe(_:options:) token KVO 的 Swift 封装 弱（KeyPath，比字符串好） token 释放即自动解绑
Combine Publisher 响应式管道 强 AnyCancellable 管理
@Observable（iOS 17+） 编译期插桩，无需 NSObject / @objc dynamic 强 自动追踪依赖

结论：Swift 侧有了编译期插桩的 @Observable 与类型安全的 Combine 之后，KVO 已退化为兼容 Cocoa 的过渡方案。新代码优先 @Observable / Combine；只有观察系统类（必须走 KVO）时才保留。

四、与相邻知识的连接

  • KVC（Day 5）：KVO 复用 KVC 的键命名约定与查找顺序，集合代理也来自 KVC。
  • Runtime（Day 4）：isa 混写、动态创建类对、方法重写，全是 runtime 能力。
  • Associated Object（Day 9）：FBKVOController 用关联对象存 block 表，这是 KVO 的安全封装范式。
  • Method Swizzling（Day 10）：同为「改实现」，但 swizzling 是类级、KVO 是实例级——这个对比是面试高频。

05 工程实战

一、用最小实验证明动态子类存在

不要停留在背诵结论，实测一遍：

- (void)dumpMethods:(Class)cls {
    unsigned int count = 0;
    Method *list = class_copyMethodList(cls, &count);
    for (unsigned int i = 0; i < count; i++) {
        NSLog(@"%@ -> %p", NSStringFromSelector(method_getName(list[i])),
              method_getImplementation(list[i]));
    }
    free(list);
}

Person *p = [Person new];
NSLog(@"%@", object_getClass(p));   // Person
[p addObserver:self forKeyPath:@"name"
      options:NSKeyValueObservingOptionNew context:MyCtx];
NSLog(@"%@", object_getClass(p));   // NSKVONotifying_Person
NSLog(@"%@", [p class]);            // Person（-class 被重写，隐瞒身份）
[self dumpMethods:object_getClass(p)];  // setName: / class / dealloc / _isKVOA

二、context 必须传，且用静态地址

static void * const MyCtx = (void *)&MyCtx;   // 地址唯一，且是编译期常量

- (void)observeValueForKeyPath:(NSString *)keyPath
                      ofObject:(id)object
                        change:(NSDictionary *)change
                       context:(void *)context {
    if (context != MyCtx) {   // 父类或框架注册的同名 keyPath，不能吞掉
        [super observeValueForKeyPath:keyPath ofObject:object
                              change:change context:context];
        return;
    }
    if ([keyPath isEqualToString:@"name"]) { /* 更新 UI */ }
}

传 NULL 的后果：父类/系统框架也观察了同名 keyPath 时，你无法区分是谁注册的，要么误处理、要么误吞掉父类的通知（吞掉后父类收不到，行为诡异且难查）。

三、Swift：token 自动解绑

@objc dynamic var name: String = ""

// token 释放（或所在对象 deinit）即自动解绑，目前最安全的写法
var token: NSKeyValueObservation?
token = model.observe(\.name, options: [.initial, .new]) { _, change in
    // 注意闭包里 weak self
}

四、生产级封装：FBKVOController 的思路

手写 removeObserver: 容易漏，业界通行做法是「统一观察者 + 自动解绑」：

  1. 内部持有一个共享的观察者对象（而不是让业务对象当 observer）；
  2. 用 NSMapTable（弱引用 key）维护 object → keyPath → block 的映射表；
  3. 在它的 observeValueForKeyPath: 里按 keyPath 查表，分发到对应 block；
  4. controller dealloc 时统一解绑所有观察关系。

收益：不可能忘记解绑、block 回调无需判断 context、业务代码不再需要实现统一回调入口。

五、三条可验证断言

断言 验证方法
只影响单个实例 只给 p1 加观察，object_getClass(p2) 仍是 Person
回调线程 = 改变线程 回调里打印 [NSThread currentThread]，配合后台队列赋值
直接写 ivar 不触发 在 Person 内部加一个直接写 _name 的方法，验证回调不进来

六、生产规则

  1. 解绑必须绑定生命周期：dealloc、FBKVOController、或 Swift token。
  2. 不要用 @try/@catch 包 removeObserver:：这是把崩溃换成静默泄漏，掩盖问题而非修复。
  3. KVO 只同步 UI 或触发轻量刷新，不放网络请求与状态机。
  4. 跨线程观察：回调里派发回主队列再改 UI；注册/解绑与赋值尽量在同一串行队列。
  5. 观察系统类前先确认它是 KVO-compliant——文档没写「KVO-compliant」的属性，行为不受保证（可能不走 setter、可能在私有线程改）。

06 常见坑与反思

高频坑位表

坑 成因 症状 规避
改了值却不通知 直接写成员变量 _ivar = x，绕过 setter 静默失效，不抛错，最难查 内部赋值也走 setter；或手动 will/didChange
observer 已释放仍回调 KVO 不 retain observer，未 remove 向悬垂指针发消息，EXC_BAD_ACCESS token / FBKVOController 自动解绑
重复 remove / context 不匹配 解绑参数与注册不一致 抛异常：Cannot remove an observer ... because it is not registered as an observer 注册与解绑参数严格一致，且只调一次
未实现回调方法 忘了写 observeValueForKeyPath: ...message was received but not handled 崩溃 统一封装，或使用 block 型方案
吞掉别人的通知 context 传 NULL 且不回传 super 父类/框架行为诡异 必传静态 context，非自己则交回 super
集合增删不触发 直接 addObject: 不走 setter 观察不到数组内容变化 用 mutableArrayValueForKey:
回调里改 UI 通知同步派发在改变线程 后台线程改 UI，偶发异常/渲染错乱 回调内派发回主队列
Swift 属性观察不到 未标 @objc dynamic 或类不继承 NSObject 静态派发，isa 换不掉 加 @objc dynamic；新代码改用 @Observable
依赖键不生效 方法名拼错（必须是 keyPathsForValuesAffecting<Key>） 联动通知不发出 拼对命名；Swift 需 @objc dynamic class func
依赖实现细节 用 NSKVONotifying_ 前缀 / _isKVOA 做判断 系统升级后行为变化 只用于调试

三条反思

  1. 这个观察关系的所有者是谁，它在什么时机被释放？ 答不上来，就该换成自动解绑方案。
  2. 如果改成显式事件或 @Observable，代码会不会更容易验证？ KVO 把控制流藏进了 runtime，出问题时几乎无法从调用栈反推——这是它最大的隐性成本。
  3. 你是在「观察状态」还是在「驱动流程」？ 后者用 KVO 是错配：通知没有顺序保证、没有队列语义、同步阻塞写入方，天生不适合当命令总线。

07 知识验收

  1. 为什么 [p class] 看不到 NSKVONotifying_ 子类，而 object_getClass(p) 能看到？子类还重写了哪些方法，各自目的是什么？
  2. 直接给成员变量赋值为什么不会触发 KVO？要让这种赋值也发出通知，应该怎么做？
  3. context 参数解决什么问题？传 NULL 会有哪些后果？
  4. KVO 通知在哪个线程派发？后台线程修改一个被 UI 观察的属性会发生什么？addObserver / removeObserver 本身线程安全吗？
  5. 观察 NSMutableArray 的元素增删时，直接 addObject: 为什么无效？正确写法是什么？回调的 change 字典里 kind 和 indexes 分别是什么？
  6. Apple 为什么选择动态子类加 isa 混写，而不是直接交换原类的 setter？它换来了什么、付出了什么？
  7. 如何关闭某个属性的自动通知？手写 will/didChange 时要注意什么？什么场景下需要这么做？
  8. fullName 由 firstName 与 lastName 推导而来，如何让修改后两者时也触发 fullName 的观察回调？底层是怎么查到这个依赖关系的？
  9. Swift 中 KVO 有哪些额外约束？@objc dynamic 各自解决什么问题？iOS 17 的 @Observable 与 KVO 在机制上有什么本质区别？
  10. FBKVOController（或类似封装）是如何做到「不会忘记解绑」的？它内部如何维护 object、keyPath 与 block 的关系？

08 掌握标准

一句话总结：KVO 用 isa 混写把被观察实例指向系统动态生成的 NSKVONotifying_ 子类，在子类重写的 setter 中以 will/didChange 包裹原实现并同步派发通知，从而零侵入地观察任意对象的属性。

掌握标准：

  • 60 分：能说清从 addObserver 到 observeValueForKeyPath 的完整链路，解释为什么必须用 object_getClass 才能看到动态子类，以及为什么直接写 ivar 不触发通知。
  • 80 分：能独立复现动态子类（class_copyMethodList 打印重写的方法）、验证回调线程与集合 KVO，定位「改了值却不通知」与「observer 已释放仍回调」两类故障；能写出正确的 context 用法与手动通知代码。
  • 100 分：能讲明 Apple 选择 isa 混写而非类级 swizzling 的取舍，解释依赖键与集合代理的底层机制，判断何时改用 @Observable / Combine，并给出把 KVO 收敛在基础设施边界的架构方案。
