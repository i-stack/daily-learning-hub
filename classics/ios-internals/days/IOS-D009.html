IOS-D009

Associated Object：不改变对象布局的扩展存储

动态系统 · 2026-08-18 · Associated Object / objc_setAssociatedObject / 关联策略 / AssociationsHashMap / Category 属性 / 静态地址 key / Tagged Pointer
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准参考资料

Category 不能添加实例变量，因为类的 ivar layout 在编译期就已固定。Associated Object 绕开了这个限制：runtime 在对象之外用一张全局哈希表维护「宿主 → key → 值」，代价是哈希查找、全局锁和一份无法被编译器检查的隐式状态。本课讲清三层表结构、五种关联策略、为什么 key 必须是稳定地址、为什么没有 weak 策略，以及它最危险的失效形式——关联对象持有宿主形成的永久泄漏。

01 背景与 API

要解决的问题

Category 不能添加实例变量（ivar）。

类的内存布局（class_ro_t 里的 ivarLayout）在编译期就已确定：每个实例的字节数、每个 ivar 的偏移都是固定的。运行时再往里塞一个 ivar，会让所有已存在的实例布局失效——这是不可能做的事。

于是出现一个矛盾的需求：

想在不改类源码、不改对象布局的前提下，给对象挂一份额外状态。

典型场景：

场景 例子
给系统类挂状态 给 UIView 挂一个业务 id、给 UIGestureRecognizer 挂闭包
在 Category 里实现「属性」 @property 在 Category 中只生成方法声明，需要存储
给协议扩展加存储 Swift extension 不支持存储属性
埋点 / AOP 的临时状态 记录某个对象是否已处理

API

// 设置
objc_setAssociatedObject(id object, const void *key, id value, objc_AssociationPolicy policy);
// 读取
id objc_getAssociatedObject(id object, const void *key);
// 移除该对象的**全部**关联（慎用）
void objc_removeAssociatedObjects(id object);

五种关联策略

策略 对应属性修饰符 语义
OBJC_ASSOCIATION_ASSIGN assign / unsafe_unretained 不持有，目标释放后成野指针
OBJC_ASSOCIATION_RETAIN_NONATOMIC strong, nonatomic 持有，不加锁
OBJC_ASSOCIATION_COPY_NONATOMIC copy, nonatomic 拷贝，不加锁
OBJC_ASSOCIATION_RETAIN strong, atomic 持有，setter 加锁
OBJC_ASSOCIATION_COPY copy, atomic 拷贝，setter 加锁

注意：没有 OBJC_ASSOCIATION_WEAK。 官方不提供弱关联（原因见 03 节）。

最小示例

static char kAssociatedKey;   // 用静态变量的地址作 key

- (void)setBadge:(NSString *)badge {
    objc_setAssociatedObject(self, &kAssociatedKey, badge,
                             OBJC_ASSOCIATION_COPY_NONATOMIC);
}

- (NSString *)badge {
    return objc_getAssociatedObject(self, &kAssociatedKey);
}

在 Category 里这样写，就得到了一个能用但不能自动合成 ivar 的「属性」。

02 运行机制

一、三层哈希结构

关联对象不存在对象里，存在 runtime 的一张全局表中：

flowchart TD
    A["AssociationsManager（自旋锁）"] --> B["AssociationsHashMap 全局唯一"]
    B --> C["key: DisguisedPtr 宿主对象地址"]
    C --> D["ObjectAssociationMap"]
    D --> E["key: const void* 你传入的 key"]
    E --> F["ObjcAssociation"]
    F --> G["policy + value"]

用 C++ 伪代码表示（objc4 objc-references.mm）：

// 第一层：宿主对象地址 → 该对象的关联表
DenseMap<DisguisedPtr<objc_object>, ObjectAssociationMap> AssociationsHashMap;
// 第二层：key → 关联值
DenseMap<const void *, ObjcAssociation> ObjectAssociationMap;
// 值
class ObjcAssociation { uintptr_t _policy; id _value; };

全局只有一张 AssociationsHashMap，由一个 AssociationsManager 用自旋锁保护。

二、set 的完整流程

objc_setAssociatedObject(object, key, value, policy)
  ↓
① acquireValue：按 policy 对 value 做 retain 或 copy
  ↓
② AssociationsManager 构造 → 加自旋锁（析构时解锁）
  ↓
③ 用 DisguisedPtr<object> 在 AssociationsHashMap 中查找
     - 找不到 → 插入空的 ObjectAssociationMap
     - 并设置 isa.has_assoc = 1（dealloc 时才知道要清理）
  ↓
④ 在 ObjectAssociationMap 中按 key 交换新旧值
  ↓
⑤ 释放旧值（按旧 policy 做 release）

注意顺序：先 retain 新值，再 release 旧值——与 objc_storeStrong（Day 2）同样的理由，避免自赋值时被提前释放。

三、get 的流程

objc_getAssociatedObject(object, key)
  ↓
加锁 → 两层哈希查找 → 取出 ObjcAssociation
  ↓
按 policy 决定返回方式（retain/copy 的会 retain + autorelease 后返回）

比一次 ivar 访问慢得多：加锁 + 两次哈希 + 可能的 retain/release。

四、什么时候被释放

关联对象不由 ARC 管理，而是由 runtime 在宿主 dealloc 时统一清理：

dealloc
  → _objc_rootDealloc → object_dispose → objc_destructInstance
        ① object_cxxDestruct        析构 ivar（ARC 插入的 release 在这里）
        ② _object_remove_assocations 移除全部关联对象   ★ 在这里
        ③ clearDeallocating          weak 置 nil、清 SideTable
  → free

关键推论：关联对象在 ivar 之后被释放。

这意味着——如果一个关联对象的 dealloc 里访问宿主的 ivar，那些 ivar 已经被释放了，是野指针。

五、objc_removeAssociatedObjects 为什么不该用

它会移除该对象所有的关联，包括别人的：

  • UIKit 内部、三方库、你自己不同模块设置的关联，全部被清掉；
  • 后果是难以定位的静默失效。

正确做法：用同一个 key 设为 nil，只移除自己那一份。

objc_setAssociatedObject(self, &kKey, nil, OBJC_ASSOCIATION_RETAIN_NONATOMIC);

03 底层原理

一、根本命题：把存储从「对象布局」搬到「外部索引」

传统的实例变量是布局的一部分：self + offset 直接访问，一条 ldr 指令。

关联对象换了一种思路：对象里只留一个标志位（isa.has_assoc），真正的数据放在全局表里，用「宿主地址 + key」索引。

维度 ivar Associated Object
位置 对象内存内部 runtime 全局哈希表
访问 编译期偏移，一条指令 加锁 + 两次哈希
何时确定 编译期 运行时任意时刻
能否在 Category 加 ❌ ✅
类型安全 编译期检查 无（id 进出）
能否 weak ✅ ❌

这就是「不改变对象布局」的全部含义：加一个关联对象，class_getInstanceSize 不变。

二、为什么 Category 不能加 ivar

class_ro_t（只读、编译期生成）里存着 ivar 列表与布局。类的实例大小 instance_size 在编译期固定，所有已创建的实例、所有子类都依赖这个布局。

运行期插入 ivar 意味着：

  • 已存在的实例需要重新分配内存（它们在其他地方被引用，无法迁移）；
  • 子类的偏移全部失效。

所以苹果选择不改布局，改索引。@property 写在 Category 里只会生成方法声明，不生成 ivar 与存取方法实现——存储必须由你自己用关联对象补上（详见 Day 8）。

三、key 必须是稳定的地址

第二层 map 的 key 是 const void *，比较用的是指针值（`ptr_hash`），不是字符串内容比较。

三种常见写法：

写法 是否可靠 说明
static char kKey; + &kKey ✅ 推荐 全 image 唯一，编译期确定
@selector(badge) ✅ 推荐 selector 由 dyld 全局 uniquing，地址稳定且唯一
_cmd（在 getter/setter 里） ✅ 等于 @selector(该方法的 SEL)
@"someKey" 字符串字面量 ⚠️ 能用但脆弱 依赖 linker 对字面量的去重；跨动态库、或用 stringWithFormat 生成时地址不同 → 取值失败

用字符串字面量「能跑」是因为同一个 Mach-O image 内的相同字面量通常被合并。但这是实现细节，不是契约。一旦有人把那段代码移到另一个 framework，或者在 Swift 侧用另一个字符串拼出来，就会静默取到 nil。

四、为什么没有 OBJC_ASSOCIATION_WEAK

weak 的实现依赖 weak_table_t：目标对象 dealloc 时 runtime 遍历所有指向它的 weak 变量并置 nil（Day 2）。

而关联值存在全局表里，value 字段是一个普通的 id。若支持 weak：

  • 需要在 weak_register_no_lock 时为「哈希表内部的一个槽位」注册 weak 引用；
  • 该槽位地址可能因哈希表扩容而移动，weak 表里存的地址就失效了。

因此苹果直接不提供。需要弱关联时，只能自己包装：

@interface WeakBox : NSObject
@property (nonatomic, weak, readonly) id target;
@end

// 存：把一个 WeakBox 用 RETAIN_NONATOMIC 关联上去
WeakBox *box = [WeakBox boxWithTarget:delegate];
objc_setAssociatedObject(self, &kKey, box, OBJC_ASSOCIATION_RETAIN_NONATOMIC);
// 取：
id target = [(WeakBox *)objc_getAssociatedObject(self, &kKey) target];

五、最危险的失效形式：关联对象持有宿主

宿主 obj ─(has_assoc)─→ 全局关联表 ─retain─→ value ─strong─→ obj

由于 value 强引用宿主，宿主的引用计数永远不会归零 → dealloc 不执行 → _object_remove_assocations 不会被调用 → 永久泄漏，且没有任何回收路径。

比 Day 2 讲的普通循环引用更隐蔽：在 Memory Graph 里，这条环经由 runtime 的全局表，不容易一眼看出。

典型触发：关联一个捕获了 self 的 Block。

objc_setAssociatedObject(self, &kKey, ^{ [self doSomething]; },  // ❌ 永久泄漏
                         OBJC_ASSOCIATION_COPY_NONATOMIC);

六、Tagged Pointer 不支持关联

isa.has_assoc 需要一个真正的 isa 结构。Tagged Pointer 对象（如 @(42)、短字符串）没有分配堆内存、没有 isa，因此无法记录这个标志位，不要对它们使用关联对象。

七、Swift 中的用法

Swift extension 不支持存储属性，关联对象是标准绕法：

private var key: UInt8 = 0

extension UIView {
    var badge: String? {
        get { objc_getAssociatedObject(self, &key) as? String }
        set { objc_setAssociatedObject(self, &key, newValue, .OBJC_ASSOCIATION_COPY_NONATOMIC) }
    }
}

注意 private var key: UInt8 = 0 的作用只是占一个稳定地址，值本身没有意义。

04 设计与取舍

一、Apple 为什么提供这个机制

约束：类的布局编译期固定，但扩展存储的需求真实存在（Category、系统类、AOP）。

候选方案 问题
允许 Category 加 ivar 破坏既有实例布局，不可行
子类化 系统类（如 NSString 的类簇、UIKit 私有子类）无法可靠子类化
自己维护全局字典 key 的生命周期、线程安全都要自己处理
runtime 统一维护关联表 与对象生命周期绑定、有策略语义 → 被选中

换来什么：

  • 不改源码、不改布局即可给对象挂状态；
  • 与对象生命周期绑定（宿主 dealloc 时自动清理）；
  • 带 retain/copy/assign 语义，接近属性；
  • 让 Category 能实现「属性」，Swift extension 能有存储能力。

付出什么：

  • 性能：加锁 + 两次哈希，比 ivar 慢一个数量级；
  • 全局锁竞争：所有对象的关联操作共用一把自旋锁；
  • 类型不安全：进出都是 id，写错类型只能运行时发现；
  • 可发现性差：状态藏在 Category 里，class_copyIvarList 看不到，读代码的人不知道它存在；
  • 无 weak 语义；
  • 调试困难：Memory Graph 上表现为「被 runtime 全局表持有」，看不出是谁设的。

二、方案选型

场景 推荐 理由
能改源码的类，需要新状态 直接加属性 类型安全、快、可发现
系统类 / 三方类，量小、低频访问 关联对象 无法改源码时的唯一选择
需要高频访问（列表 cell、drawRect） 绝不用关联对象 全局锁 + 哈希，会掉帧
需要一对多的附加数据 NSMapTable / 自己的字典 可控、可枚举、可调试
需要 weak 语义 包装类 + RETAIN_NONATOMIC 官方无 weak 策略
只是想给 Category 加方法 直接加方法，不需要存储就别用 最小惊讶

判断原则：关联对象是「不能改源码」时的兜底，不是「懒得建模」的借口。 如果这块状态是你自己模块的核心模型，应该建模成真实类型，而不是挂在别人身上。

三、架构定位

  • 集中管理：一个模块的所有关联 key 收敛到一个文件，避免散落；
  • key 命名带模块前缀，避免与他人冲突；
  • 关联的值不得持有宿主；
  • 需要清理时，用同 key 设 nil，不用 objc_removeAssociatedObjects。

四、与相邻知识的连接

  • Category（Day 8）：@property 在 Category 中不合成 ivar，关联对象是补上存储的标准手段。
  • ARC（Day 2）：关联对象的释放发生在 dealloc 第二步（ivar 之后、weak 置 nil 之前）。
  • Block（Day 3）：关联一个捕获 self 的 Block = 永久泄漏。
  • Method Swizzling（Day 10）：二者常一起用于 AOP，但也一起放大了「隐式行为」的风险。
  • KVO（Day 6）：KVO 会替换 isa；关联对象不动 isa（只置 has_assoc 位），两者可以共存，但调试时 object_getClass 的结果容易混淆。

05 工程实战

一、标准写法

// 1. key 用静态地址，命名带前缀
static const void *const kXYBadgeKey = &kXYBadgeKey;
// 或：static char kXYBadgeKey;  然后用 &kXYBadgeKey

@implementation UIView (XYBadge)

- (NSString *)xy_badge {
    return objc_getAssociatedObject(self, @selector(xy_badge));
}

- (void)setXy_badge:(NSString *)badge {
    objc_setAssociatedObject(self, @selector(xy_badge), badge,
                             OBJC_ASSOCIATION_COPY_NONATOMIC);
}

@end

三个要点：

  1. key 用 @selector(setter)——地址稳定、天然唯一、不用额外声明变量；
  2. 策略按需选：字符串/集合用 COPY，普通对象用 RETAIN，多线程读写用不带 NONATOMIC 的版本；
  3. 方法名加前缀（xy_）——Category 方法重名会静默覆盖，这是 Day 8 的坑。

二、需要 weak 关联时

@interface XYWeakBox : NSObject
@property (nonatomic, weak, readonly) id target;
+ (instancetype)boxWithTarget:(id)target;
@end

@implementation XYWeakBox
+ (instancetype)boxWithTarget:(id)target {
    XYWeakBox *box = [XYWeakBox new];
    box->_target = target;
    return box;
}
@end

// 使用
objc_setAssociatedObject(obj, &kKey, [XYWeakBox boxWithTarget:delegate],
                         OBJC_ASSOCIATION_RETAIN_NONATOMIC);
id target = [(XYWeakBox *)objc_getAssociatedObject(obj, &kKey) target];

注意：target 释放后，WeakBox 本身仍在关联表里（只是 target 变 nil）。要么容忍一个空壳，要么在读取后顺手清理。

三、清理：只清自己的

// ✅ 只移除自己那份
objc_setAssociatedObject(self, &kKey, nil, OBJC_ASSOCIATION_RETAIN_NONATOMIC);

// ❌ 会清掉 UIKit、三方库设的所有关联
objc_removeAssociatedObjects(self);

objc_removeAssociatedObjects 只适合测试代码或你自己独占的对象。

四、线程安全

层次 是否安全
关联表本身（插入/查找/移除） ✅ 有自旋锁
不带 NONATOMIC 的策略 ✅ setter 的「取旧值 → 设新值」是原子的
带 NONATOMIC 的策略 ❌ 并发读写仍可能出问题
值对象自身的内部状态 ❌ 与策略无关，需自己加锁

RETAIN / COPY（atomic）保证的是 setter 的原子性，不保证你「读到值之后再操作」这整段逻辑的原子性。需要复合操作时仍要自己加锁。

五、必须验证的行为

写单元测试或调试脚本覆盖：

用例 断言
基本读写 set 后 get 能取回；设 nil 后取回 nil
宿主释放时清理 用 weak var 观察：宿主释放后，关联值也释放
策略语义 COPY 策略取回的对象与原对象不是同一实例
key 唯一性 两个不同 key 互不覆盖
无泄漏 关联值不持有宿主时，宿主能正常 dealloc
Tagged Pointer 不对小对象使用（避免崩溃） 
func testAssociatedValueReleasedWithHost() {
    weak var weakValue: NSObject?
    autoreleasepool {
        let host = NSObject()
        let value = NSObject()
        weakValue = value
        objc_setAssociatedObject(host, &key, value, .OBJC_ASSOCIATION_RETAIN_NONATOMIC)
        XCTAssertNotNil(weakValue)
    }
    XCTAssertNil(weakValue, "宿主释放后关联值未释放")
}

六、调试技巧

  • Memory Graph 里关联对象挂在 runtime 的全局表下，看不到「谁设的」——所以 key 命名要能自解释；
  • 用 _objc_debug_assoc_info（lldb 私有命令）或直接在 objc_setAssociatedObject 打符号断点，能看到调用方；
  • 怀疑关联导致泄漏时，优先用符号断点列出所有 set 调用，检查有没有「值持有宿主」。

七、工程护栏

  1. 热路径禁用（cell 复用、drawRect:、布局计算）。
  2. 关联值不得持有宿主——这是硬约束，需要代码评审把关。
  3. key 集中声明并加模块前缀。
  4. 能用真实属性就不用关联对象；存量代码里每处关联对象都应能回答「为什么不能用属性」。
  5. 清理时只清自己的 key。

06 常见坑与反思

高频坑位表

坑 成因 症状 规避
用 ASSIGN 存会被释放的对象 不持有 悬垂指针，访问即崩溃 对象一律 RETAIN / COPY
关联值持有宿主 value 强引用 obj 永久泄漏（dealloc 永不执行） 硬约束：值不得持有宿主
用字符串字面量作 key 依赖 linker 去重 跨库/拼接时静默取到 nil 用静态地址或 @selector
误用 objc_removeAssociatedObjects 清掉所有人的关联 三方库静默失效 用同 key 设 nil
想要 weak 关联 官方无此策略 编译不过或强引用 WeakBox 包装
高性能路径使用 全局锁 + 哈希 掉帧 改真实属性
在关联值的 dealloc 里访问宿主 ivar 关联对象在 ivar 之后释放 野指针崩溃 不在其 dealloc 中回指宿主
对 Tagged Pointer 设关联 无 isa，无法置 has_assoc 未定义行为 只对堆对象使用
Category 方法名无前缀 重名覆盖 别人的实现被吞 统一加模块前缀
把核心状态挂在别人身上 图省事 可发现性差、难重构 核心状态建模成真实类型
atomic 误以为线程安全 只保证 setter 原子 复合操作仍竞态 自己加锁
与 KVO 混用看不清 isa KVO 替换 isa 调试误判 用 object_getClass 确认真实类

三条反思

  1. ASSIGN 是有毒的默认选择。 它看起来最「轻量」，实际上把「内存管理正确」变成了「你必须证明被关联对象一定活得比宿主久」。而这恰恰是使用关联对象的典型场景里最难证明的事。默认 RETAIN_NONATOMIC，只有当你能说出理由时才用别的。
  2. 隐式状态的代价在半年后支付。 关联对象让 Category 拥有了存储能力，代价是这块存储不在类的声明里、不在 ivar 列表里、不在 Memory Graph 的直觉位置。写的时候很爽，接手的人只能靠 grep objc_setAssociatedObject 才能知道这个类到底有什么状态。能建模成真实属性，就不要图省事。
  3. 「挂在别人身上」会放大生命周期错误。 普通循环引用至少还能在 Memory Graph 里看到一个环；关联对象的环经过 runtime 全局表，图上不明显，而且永远等不到 dealloc 去打破它。这条路上，weak 包装不是可选项，是必需项。

08 掌握标准

一句话总结：Category 不能加 ivar（类布局编译期固定），于是 runtime 在对象外部用「AssociationsHashMap（宿主地址）→ ObjectAssociationMap（key）→ ObjcAssociation（policy + value）」三层表挂在全局，并在宿主 dealloc 的第二步（_object_remove_associations，位于 ivar 析构之后）统一清理；代价是加锁 + 两次哈希的性能、无 weak 语义、以及「值持有宿主」时无法打破的永久泄漏。

掌握标准：

  • 60 分：能说清 Category 为何不能加 ivar；会用 objc_setAssociatedObject / get 配合静态地址 key；能列出五种策略并知道默认该选哪个。
  • 80 分：能画出三层表结构与 set 的完整流程；能解释关联对象在 dealloc 中的清理时机与顺序风险；能说明为何没有 weak 策略并给出 WeakBox 方案；能识别「值持有宿主」的永久泄漏。
  • 100 分：能从「对象布局编译期固定」推出关联对象存在的必然性；能论证 key 用字符串字面量的失效边界；能在 ivar / 子类化 / NSMapTable / 关联对象之间做出有理据的选型；能把「关联值不得持有宿主」落成评审硬约束，并解释隐式状态对长期可维护性的具体危害。
