IOS-D002

ARC：引用计数与对象生命周期

内存管理 · 2026-08-11 · ARC / 引用计数 / extra_rc / SideTable / weak 表 / dealloc / 循环引用 / objc_storeStrong / unowned
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准参考资料

ARC 不是垃圾回收，而是编译器在编译期插入 retain/release、runtime 在运行时维护计数表的一套协作机制。本课从 extra_rc 与 SideTable 的存储结构出发，打通对象从分配到 dealloc 的完整生命周期、weak 自动置 nil 的实现、以及 ARC 留下的唯一必须由人填的坑——循环引用，并给出所有权图与 Memory Graph 验证方法。

01 背景与 API

要解决的问题

手动内存管理（MRR）要求开发者自己写 retain / release / autorelease，漏一次就泄漏，多一次就野指针。ARC 的目标：让编译器替你写这些调用，同时保持释放时机的确定性。

ARC 不是 GC

这是面试第一个分水岭：

维度 ARC 垃圾回收（GC）
决策时机 编译期插入调用 运行时扫描
释放时机 确定（引用计数归零那一刻） 不确定（GC 触发时）
停顿 无全局停顿 可能有 Stop-The-World
循环引用 无法自动处理 可回收
开销位置 每次赋值多几条指令 周期性扫描

ARC = 编译期所有权分析 + 运行时引用计数表。没有扫描、没有追踪、没有循环检测。

所有权修饰符

Swift Objective-C 语义
strong（默认） __strong 持有，引用计数 +1
weak __weak 不持有，目标释放后自动置 nil
unowned __unsafe_unretained 不持有，目标释放后不置 nil（Swift 侧访问会崩）
unowned(unsafe) __unsafe_unretained 同上，明确放弃安全检查
— __autoreleasing 加入 autorelease pool（见 Day 7）

属性关键字对照：

关键字 用于 说明
strong 对象 默认
copy 有可变子类的类型（NSString / NSArray / Block） setter 里执行 copy
weak delegate、Outlet 自动置 nil
assign 标量（int / CGFloat / BOOL） 修饰对象会产生野指针
unsafe_unretained 对象（极少用） 不置 nil

编译期插入了什么

ARC 的全部魔法是 Clang 在编译期把赋值/作用域结束翻译成 runtime 函数调用：

源码写法 编译后调用
obj = newValue; objc_storeStrong(&obj, newValue)
局部变量出作用域 objc_storeStrong(&obj, nil)
读取 weak 变量 objc_loadWeakRetained(&weakObj)
__weak id w = obj; objc_initWeak(&w, obj)
从方法返回对象 objc_autoreleaseReturnValue(obj)
接收方法返回值 objc_retainAutoreleasedReturnValue(obj)

与 Core Foundation 的桥接

ARC 不管 CF 对象，跨框架时必须显式说明所有权转移：

写法 语义
__bridge 只转类型，不转移所有权（最常用）
__bridge_retained / CFBridgingRetain 转交所有权给 CF，需手动 CFRelease
__bridge_transfer / CFBridgingRelease 把所有权转回 ARC，ARC 负责释放

02 运行机制

一、引用计数存在哪里

对象自己不存完整的引用计数，而是两级存储：

flowchart TD
    A["对象 isa"] --> B{"nonpointer?"}
    B -- 否 --> C["SideTable 的 RefcountMap"]
    B -- 是 --> D["isa.extra_rc（19 位）"]
    D --> E{"extra_rc 溢出?"}
    E -- 否 --> F["计数就在 isa 里，无需加锁"]
    E -- 是 --> G["移一半到 SideTable，has_sidetable_rc=1"]
    G --> C
  • 一级：isa.extra_rc（arm64 下 19 位）。绝大多数对象的引用计数从未超过 19 位能表示的范围，因此常见路径完全不需要查表、不需要加锁，只是几条位运算指令。
  • 二级：SideTable。全局的分片哈希表（StripedMap，iOS 上 8 片、macOS 上 64 片），每片自带一把自旋锁，内含：
    • RefcountMap：对象地址 → 引用计数（外挂部分）；
    • weak_table_t：弱引用表。

分片的目的就是降低锁竞争——不同对象大概率落在不同片，可以并发加减计数。

二、一次 retain / release 的路径

objc_retain(obj)
  ├── Tagged Pointer?        → 直接返回（不分配堆内存的对象没有计数）
  ├── nonpointer isa?        → addc(isa, RC_ONE)，检测进位
  │       └── 溢出 → 移一半进 SideTable，置 has_sidetable_rc
  └── 否则                   → 加自旋锁，SideTable.refcnts 加一

objc_release(obj)
  ├── Tagged Pointer?        → 直接返回
  ├── nonpointer isa?        → subc(isa, RC_ONE)，检测下溢
  │       └── 下溢 → 从 SideTable 借回，仍为 0 则触发 dealloc
  └── 否则                   → 查表减一，为 0 则 dealloc

三、dealloc 内部做了什么

引用计数归零后进入 dealloc，真正干活的在 objc_destructInstance：

dealloc
  → _objc_rootDealloc
      → object_dispose
          → objc_destructInstance
              1. 有 C++ 成员？        → object_cxxDestruct（调 .cxx_destruct）
              2. 有关联对象？         → _object_remove_assocations
              3. clearDeallocating
                   - nonpointer isa  → clearDeallocating_slow
                   - weakly_referenced → weak_clear_no_lock：把 weak 表里
                                         所有指向它的 weak 变量**全部置 nil**
                   - has_sidetable_rc  → 从 SideTable 移除计数记录
          → free(obj)

关键事实：weak 变量置 nil 发生在 dealloc 过程中（析构之后、free 之前），由 weak_clear_no_lock 完成。 这就是为什么 weak-strong dance 里 strongSelf 一旦拿到，就保证在后续代码里不会被释放。

四、weak 表的结构

weak_table_t（全局，在 SideTable 里）
   └── weak_entries（哈希数组）
         └── weak_entry_t（按目标对象聚合）
               ├── referent：被指向的对象地址
               └── referrers：所有指向它的 weak 变量地址（动态数组/哈希）
  • 注册：objc_initWeak → storeWeak → weak_register_no_lock（插入 weak_entry_t.referrers）；
  • 清除：目标 dealloc 时 weak_clear_no_lock 遍历 referrers 全部写 0；
  • 读取：objc_loadWeakRetained 会 retain + autorelease 一次，保证你在使用期间对象不会被别人释放。

五、对象生命周期全景

阶段 发生什么
分配 alloc → calloc，isa 初始化（nonpointer，extra_rc = 1）
使用 每次 strong 赋值 objc_storeStrong：retain 新值 → 写入 → release 旧值
出作用域 编译器插入 objc_storeStrong(&obj, nil) → 计数减一
计数归零 dealloc → 析构 ivar → 移除关联对象 → weak 置 nil → free
悬垂 __unsafe_unretained / unowned 指针不会被置 nil，成野指针

03 底层原理

一、根本命题：把所有权变成类型系统的一部分

ARC 的核心创新不是「自动计数」，而是把所有权语义写进了类型：strong / weak / unowned 是类型修饰符，编译器据此决定在哪里插入 retain/release。

这带来一个直接结论：ARC 是确定性的。你读代码就能知道对象何时释放——不需要知道 GC 什么时候跑。这对 UI 开发极其重要：资源（文件句柄、纹理、音频缓冲）可以绑定在 dealloc 上及时释放。

二、objc_storeStrong 的顺序很关键

void objc_storeStrong(id *location, id obj) {
    id prev = *location;
    if (obj == prev) return;          // 自赋值保险
    objc_retain(obj);                 // ① 先 retain 新值
    *location = obj;                  // ② 再赋值
    objc_release(prev);               // ③ 最后 release 旧值
}

先 retain 后 release 是刻意的：如果反过来，当 newValue 和 oldValue 是同一个对象、且这是最后一个引用时，先 release 会直接把它送进 dealloc。

三、方法返回值优化（TLS 快速路径）

这是 ARC 最重要的性能优化，也是面试高频：

调用方                                  被调方
  |                                       |
  |  objc_retainAutoreleasedReturnValue   |  objc_autoreleaseReturnValue(obj)
  |                                       |    ↓
  |                                       |  检查调用方紧接着的指令（用返回地址 TLS 判定）
  |                                       |  如果是 objc_retainAutoreleasedReturnValue
  |  ← 直接拿到 +1 的对象，跳过 pool  →  |  则**不 autorelease**，直接返回（计数已 +1）

原理：objc_autoreleaseReturnValue 通过 Thread Local Storage 里存的调用方返回地址，判断下一个指令是不是 objc_retainAutoreleasedReturnValue。如果是，就跳过「放入 autorelease pool」这一步，直接返回，把计数交给调用方。

结果：常见的 [[Obj alloc] init] 完全不进 autorelease pool。

这个优化依赖「方法返回后立刻被 retain」这个模式。一旦你在中间插入别的操作，就会退化成真正的 autorelease。

四、循环引用：ARC 唯一无法自动处理的场景

引用计数判定存活的标准是「还有没有人指向我」。当两个对象互相指向，或一个对象指向自己时，计数永远不会归零。

四种最常见形态：

形态 链条 破解
对象互持 A.child = B / B.parent = A 一方改 weak（通常是子持父）
闭包捕获 self.closure = { self.doSomething() } [weak self] / [unowned self]
Timer / DisplayLink runloop → timer → target，target 又持有 timer weak proxy（Day 12）或 invalidate
通知 / KVO 未移除 通知中心持有观察者 deinit 移除 / token 自动解绑

ARC 不能消除循环引用，这是它相比 GC 最大的代价，也是所有内存泄漏的根因。

五、Swift 的 weak 与 unowned

维度 weak unowned
类型 必须是 Optional 可以是非 Optional
释放后 自动置 nil 不置 nil（保留野指针）
访问已释放对象 安全返回 nil 崩溃（runtime 会做 unowned retain 检查）
开销 需要维护 weak 表 无额外开销
语义表达 「可能不存在」 「必然比我活得久，这是你的契约」

选择原则：能用 weak 就用 weak；只有当你能在代码里证明「生命周期必然长于 self」时才用 unowned（典型例子：闭包捕获的 self.view 内部的子视图、Parent-Child 中闭包由 Child 持有）。

六、Tagged Pointer 与字面量

NSNumber *a = @(42);
NSString *b = @"hello";
// 它们不分配堆内存、没有引用计数，retain/release 对它们是 no-op

因此不要用「打印 retainCount」来判断内存行为——对 Tagged Pointer 和字面量，这个数字毫无意义（且 retainCount 本身就是不该依赖的 API）。

04 设计与取舍

一、Apple 为什么选 ARC 而不是 GC

约束：iOS 设备内存小、没有 swap、UI 必须保证帧率稳定。

候选 问题
追踪式 GC 需要 Stop-The-World 或并发扫描，帧率不可控；内存峰值更高
手动管理（MRR） 正确率低，泄漏与野指针频发
引用计数 + 编译期插桩 释放时机确定、无全局停顿 → 被选中

换来什么：

  • 释放时机确定：dealloc 就在最后一个引用消失的那一刻，资源能及时归还；
  • 无 Stop-The-World，帧率可预测；
  • 绝大多数内存问题在编译期被消除；
  • dealloc / deinit 成为可靠的资源释放钩子（RAII 风格）。

付出什么：

  • 循环引用必须人工处理——这是 iOS 端内存泄漏的第一大来源；
  • 每次赋值都有 retain/release 开销（虽然很小）；
  • weak 表、SideTable 占用额外内存并需要加锁；
  • 所有权成为开发者必须显式表达的语义，weak / unowned 选错就直接崩溃。

二、苹果的补救措施

成本 优化手段
计数存取要加锁 isa.extra_rc（19 位内联，无需查表加锁）
SideTable 锁竞争 StripedMap 分成 8/64 片
retain/release 指令开销 编译器消除冗余的 retain/release 对
返回值反复入池 TLS 快速路径（跳过 autorelease pool）
小对象分配开销 Tagged Pointer（根本不分配堆内存）
循环引用难排查 Memory Graph Debugger、Runtime 检查

三、架构定位

所有权必须是一个显式的设计决策，而不是事后补丁。 判断标准：

  • 每个对象都应该有明确的所有者（谁让它活着）；
  • 反向引用（子 → 父、view → controller、回调 → 宿主）默认用 weak；
  • 长生命周期容器（单例、缓存、通知中心）持有短生命周期对象时，必须明确「什么时候移除」。

四、与相邻知识的连接

  • AutoreleasePool（Day 7）：ARC 仍依赖 autorelease pool 处理返回值；TLS 优化决定了很多对象根本不入池。
  • Block（Day 3）：闭包捕获是循环引用的第二大来源，捕获语义与 __block 直接影响所有权。
  • Runtime（Day 4）：isa.extra_rc、weak_table_t、SideTable 全在 objc4 里。
  • NSProxy（Day 12）：弱代理是为打断 Timer 强引用环而生的。
  • Associated Object（Day 9）：关联对象的释放发生在 dealloc 的第二步。

05 工程实战

一、先画所有权图，再写代码

面对任何可能泄漏的关系，先画清楚「谁强持有谁」：

✅ 正确                              ❌ 循环
ViewController ─strong→ View        ViewController ─strong→ View
View ─weak→ delegate(VC)            View ─strong→ delegate(VC)  ✗

✅ 正确                              ❌ 循环
ViewController ─strong→ Timer       RunLoop ─strong→ Timer
Timer ─weak→ proxy ─weak→ VC        Timer ─strong→ VC ─strong→ Timer  ✗

规则：箭头只允许形成有向无环图。存在环的地方，把其中一条改成 weak，且优先改「生命周期更短的一方指向更长一方」的那条。

二、四类泄漏场景与标准修法

场景 泄漏链 修法
delegate view.delegate = self（属性是 strong） 属性声明为 weak
闭包 self.handler = { self.update() } [weak self] + guard let self
Timer RunLoop → timer → self，self 持 timer invalidate；或使用 iOS 10+ 的 block API + [weak self]；或用 weak proxy
通知/KVO 中心持有观察者 deinit 中移除；KVO 用 token 自动解绑
GCD 延迟 queue → block → self 尽早取消（DispatchWorkItem.cancel）或 [weak self]
缓存 单例缓存持有对象 用 NSCache（内存紧张时自动清理）并设 countLimit

三、用测试验证「真的释放了」

不要靠肉眼看，写成断言：

func testViewControllerReleases() throws {
    weak var weakVC: MyViewController?
    try autoreleasepool {
        let vc = MyViewController()
        weakVC = vc
        XCTAssertNotNil(weakVC)
    }
    XCTAssertNil(weakVC, "ViewController 未释放，存在循环引用")
}

要点：

  • 被测对象不能被测试函数里的强变量持有，否则断言永远为 nil 失败；
  • 涉及 autorelease 的对象要包在 autoreleasepool 里；
  • 交互测试中，VC 需要先走完 viewDidDisappear 等生命周期。

四、Memory Graph Debugger

  1. 运行 App，触发可疑场景后退出该页面；
  2. 点 Xcode 调试栏的 Debug Memory Graph（三个节点图标）；
  3. 左侧列表里仍然存在的本该释放的对象就是泄漏嫌疑；
  4. 选中对象，右侧显示引用关系，紫色的 ! 标记会被 Xcode 直接标为「循环引用」；
  5. 打开 Malloc Stack Logging，可以反查对象的分配调用栈。

五、deinit / dealloc 日志验证

deinit { print("\(type(of: self)) deinit") }

- (void)dealloc { NSLog(@"%@ dealloc", NSStringFromClass([self class])); }

Debug 期给关键 VC / ViewModel 加 deinit 日志，是最廉价、最可靠的泄漏检测手段。

六、其他检测手段

手段 适用场景
Memory Graph Debugger 定位谁在持有（最常用）
Instruments Leaks 长时间运行后的泄漏趋势
Instruments Allocations 内存增长、对象数量异常
Xcode Runtime Issues 运行时直接报循环引用
FBRetainCycleDetector 自动化检测（可集成到 Debug 构建）
deinit 日志 + 单元测试 回归防护

七、weak-strong dance 的正确写法

loadData { [weak self] result in
    guard let self = self else { return }   // 一旦拿到，后续一定存活
    self.updateUI(result)
    self.reload()
}

为什么需要第二行：只用 [weak self] 时，self?.a() 与 self?.b() 之间 self 可能被释放，导致前半段执行、后半段不执行的中间态。guard let 把它固定下来。

06 常见坑与反思

高频坑位表

坑 成因 症状 规避
delegate 用 strong 属性默认 strong VC 永不释放 delegate 一律 weak
闭包捕获 self 闭包被 self 间接持有 循环引用 [weak self] + guard let
unowned 假设失败 目标先于 self 释放 崩溃（不是返回 nil） 只在能证明生命周期时用
NSTimer 不 invalidate RunLoop 持有 timer VC 不释放、回调仍触发 viewWillDisappear 里 invalidate；或 block API
通知未移除 通知中心持有观察者 崩溃或重复响应 deinit 移除 / token
assign 修饰对象 不做 retain 野指针崩溃 对象用 strong/weak/copy
NSString 用 strong 外部传入 NSMutableString 后被改 值意外变化 有可变子类的一律 copy
Block 属性用 assign Block 在栈上 野指针 Block 属性必须 copy（ARC 下 strong 亦可，但语义用 copy 更明确）
过度使用 weak 需要对象活着时它已释放 功能静默失效 weak 只用于「允许不存在」的关系
deinit 里访问异步 self self 正在析构 崩溃 析构路径不做异步
CF 对象未 __bridge ARC 不管 CF 内存 泄漏或过度释放 明确 __bridge / CFBridgingRelease
retainCount 判内存 该 API 不可靠、Tagged Pointer 无意义 错误结论 用 Memory Graph

三条反思

  1. weak 不是万能修复。 它只解决「引用环」这一件事。如果你的设计需要「回调时对象必须在」，改成 weak 只会把崩溃变成静默失效——更难查。先想清楚该不该是 weak，再动手。
  2. unowned 是对生命周期的断言，不是性能优化。 用 unowned 等于向编译器和同事声明「我保证它比我活得久」。当你不能拿出证据时，就该用 weak。
  3. ARC 消除了「忘记 release」，但没有消除「所有权设计错误」。 现代 iOS 的内存问题，99% 不是漏写 release，而是谁该持有谁没想清楚。画所有权图比看代码更有效。

  12. 给出一个真实（或可信构造的）内存泄漏故障：现象、用 Memory Graph 建立的证据链、根因与改进方案。
  13. 什么条件下你会放弃引用计数方案，改用其他内存管理策略（如值类型、区域分配、手动管理）？

08 掌握标准

一句话总结：ARC 是「编译期插桩 + 运行时计数表」的协作机制——引用计数优先存在 isa.extra_rc 里，溢出后外挂到分片加锁的 SideTable，归零时 dealloc 依次析构 ivar、移除关联对象、并由 weak_clear_no_lock 把所有 weak 指针置 nil；它换来确定性的释放时机，代价是循环引用必须由人用 weak / unowned 显式打破。

掌握标准：

  • 60 分：能说清 ARC 与 GC 的区别；能列出 strong / weak / unowned / copy 的语义与适用场景；能识别 delegate、闭包、Timer 三类典型循环引用并给出修法。
  • 80 分：能讲清 isa.extra_rc + SideTable 两级存储与溢出规则；能画出 dealloc 的完整步骤并指出 weak 置 nil 的时机；能解释 objc_storeStrong 的顺序原因与 TLS 返回值优化；能用 Memory Graph 与单元测试定位真实泄漏。
  • 100 分：能分析 ARC 相比 GC 的取舍与苹果的六项补救优化；能对任意模块画出所有权图并证明其无环；能论证 weak 与 unowned 的选择依据，并指出「用 weak 掩盖生命周期设计问题」的危害；能把「所有权是显式设计决策」落成团队可执行的规范。
