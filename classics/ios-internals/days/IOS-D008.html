IOS-D008

Category：方法扩展与加载机制

动态系统 · 2026-08-17 · Category / category_t / attachCategories / attachLists / 类扩展 Extension / load / initialize / -ObjC
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准参考资料

Category 让你不必改动一个类、不必创建子类，就能给它加上方法。它的全部秘密在于：编译期生成 category_t 存进 Mach-O，镜像加载时 runtime 用 attachLists 把 category 的方法列表**插到原类方法列表的前面**——所以「覆盖」从来不是替换，而是查找顺序上的抢先。同一套限制也解释了为什么 Category 加不了 ivar：class_rw_t 里可以被 attach 的只有 methods / properties / protocols 三个二维数组，ivars 不在其中。

01 背景与 API

要解决的问题

想给一个已经存在的类加方法，而这个类：

  • 是系统类（NSString、UIView），你没有源码；
  • 是三方库的类，改了下次升级就没了；
  • 是自己写的类，但已经几千行，想按职责拆成多个文件。

子类化能解决前两者，但代价是类型变了：NSString 的方法不能对你的子类生效，工厂方法返回的仍是原类。

Category 的答案是：不创建新类型，直接往现有类上追加方法。

三种「扩展」的区别

这是本课第一个必须分清的概念：

维度 Category 分类 Extension 类扩展 Subclass 子类
决议时机 运行时（attach） 编译期（合并进主类） 编译期
文件形态 独立 .h / .m 必须在类的 .m 中 独立 .h / .m
能否加 ivar ❌ ✅ ✅
能否加方法 ✅ ✅ ✅
是否产生新类型 ❌ ❌ ✅
必须有源码 ❌ ✅ ❌
典型用途 给系统类加方法、拆分大类 私有属性/方法的声明 需要新的类型身份

Extension 常被误称为「匿名 Category」，但二者完全不同：Extension 在编译期就把 ivar 和方法布局合并进主类，是类的一部分。

基本语法

// NSString+XYAdd.h
@interface NSString (XYAdd)
- (NSString *)xy_md5;
+ (BOOL)xy_isValidEmail:(NSString *)email;
@end

// NSString+XYAdd.m
@implementation NSString (XYAdd)
- (NSString *)xy_md5 { /* ... */ }
+ (BOOL)xy_isValidEmail:(NSString *)email { /* ... */ }
@end

括号里的名字是 Category 名，一个类可以有多个 Category。

能加什么，不能加什么

能力 支持 说明
实例方法 ✅ 最常用
类方法 ✅ 加到元类上
协议 ✅ 会被 attach 到类的 protocol list
属性（@property） ⚠️ 只生成方法声明，不合成 ivar、不生成存取方法
实例变量 ivar ❌ 根本原因见 03 节
重写已有方法 ⚠️ 技术上可行，但后果不可控，不该做（详见 Day 10）

底层数据结构

编译后，每个 Category 变成一个 category_t，存进 Mach-O 的 __DATA,__objc_catlist 段：

struct category_t {
    const char                    *name;                 // 分类名，如 "XYAdd"
    classref_t                     cls;                  // 目标类
    method_list_t                 *instanceMethods;      // 实例方法列表
    method_list_t                 *classMethods;         // 类方法列表
    protocol_list_t               *protocols;
    property_list_t               *instanceProperties;
    property_list_t               *_classProperties;
    uint32_t                       size;                 // sizeof(结构体本身)
};

注意：里面没有 ivar 列表。这不是遗漏，是设计（详见 Day 9）。

02 运行机制

一、从 Mach-O 到方法表的完整链路

关键点：类与 Category 不一定同时加载（比如 Category 在未加载的 bundle 里）。runtime 用一张 unattachedCategories 哈希表兜住这种情况，等类 realize 时再补。

二、attachLists：所谓「覆盖」的真相

attachLists 的作用是往二维数组里插入新的 list：

void list_array_tt<Element, List, Ptr>::attachLists(List* const * addedLists, uint32_t addedCount) {
    uint32_t oldCount = array()->count;
    uint32_t newCount = oldCount + addedCount;
    setArray((array_t *)realloc(array(), array_t::byteSize(newCount)));
    array()->count = newCount;

    // 把旧列表整体后移 addedCount 位
    memmove(array()->lists + addedCount,
            array()->lists,
            oldCount * sizeof(array()->lists[0]));

    // 把新列表放到前面，且**逆序**拷贝
    memcpy(array()->lists,
           addedLists,
           addedCount * sizeof(array()->lists[0]));
    // addedLists 本身是倒序传入的（最后编译的在前）
}

结果：Category 的方法列表排在主类方法列表之前。

attach 前
  method_array_t = [ 主类方法列表 ]

attach 后（一个 Category）
  method_array_t = [ Category列表 , 主类方法列表 ]
                      ↑ 先看这里

消息查找（objc_msgSend → lookUpImpOrForward → findMethodInSortedMethodList）是从前向后遍历的，因此 Category 的方法会先被命中。

这就是「Category 覆盖原类方法」的全部真相：不是替换，是查找顺序上的抢先。主类的方法仍然完整存在于方法列表中。

由此得到三个推论：

  1. 多个 Category 有同名方法时，后编译的那个在数组更前面 → 生效；
  2. 在 Category 里调 [self 同名方法]，找到的仍是 Category 版本（不是主类的）；
  3. super 救不了你——[super foo] 找的是父类的实现，不是主类被「挡住」的那个实现。

三、+load 与 +initialize

维度 +load +initialize
调用时机 main 之前，镜像加载时 第一次给类发消息前（懒加载）
调用方式 直接取函数 IMP 调用，不走消息发送 走 objc_msgSend（_class_initialize）
父类 runtime 保证父类先于子类 父类先于子类，且子类未实现时会再调父类一次
Category 之间 按编译顺序 Category 的 initialize 会覆盖主类的（最后编译者生效）
线程安全 主线程，单线程环境 runtime 加锁保护
是否需要 super 不需要也不该写 [super load] 一般不需要
典型用途 方法交换、类注册表（Day 10） 静态数据一次初始化

+load 的完整顺序

① dyld 完成镜像链接
② 所有类（含系统类）的 +load        ← 父类先于子类
③ 所有 Category 的 +load            ← 按编译顺序，全部在类之后
④ main()

注意第 ③ 步：所有类的 +load 都先于所有 Category 的 +load，源码依据──call_load_methods() 先跑完 call_class_loads()，再跑 call_category_loads()。

+load 期间：

  • runtime 已经包了一层 autorelease pool，所以里面产生的临时对象会被清理；
  • 其他类可能尚未初始化完成（尤其是非当前镜像的类），此时做复杂依赖有死锁风险；
  • 因为不走 objc_msgSend，+load 没有自动向上调用父类 +load 的行为，也不会被 Category 覆盖（每个类的 load IMP 被单独调用）。

+initialize 的坑

@implementation Parent
+ (void)initialize { NSLog(@"Parent"); }
@end
@implementation Child   // 未实现 initialize
@end

[Child alloc];   // 输出：Parent → Parent（被调用两次！）

子类未实现时，会沿继承链调用父类的 +initialize，导致父类实现被调用多次。需要防重时加 dispatch_once 或 self == Parent 判断。

四、静态库里的 Category：-ObjC 链接标志

Category 没有独立的符号可被引用：只有类的符号会被 linker 拉进产物，Category 的方法表在单独的目标文件里，linker 认为它「没人引用」就不链接 → 运行时该 Category 从未被 attach → unrecognized selector 崩溃。

解决：在 Other Linker Flags 里加：

flag 作用
-ObjC 把静态库中所有 OC 类和 Category 的目标文件都链接进来
-all_load 强制链接所有目标文件（包括 C/C++，产物更大）
-force_load <path> 只对指定库强制加载（推荐替代 -all_load）

这是组件化/SDK 集成里最高频的故障之一：Debug 跑源码没问题，打成静态库后某个 Category 方法就崩。

03 底层原理

一、根本命题：运行时的方法表是可追加的

一个类的方法存放在 class_rw_t 里，而 methods / properties / protocols 三者的类型都是 list_array_tt——一个二维数组：

struct class_rw_t {
    // 二维：每一维是一个 Category 或主类自己的 list
    method_array_t      methods;
    property_array_t    properties;
    protocol_array_t    protocols;

    Class               firstSubclass;
    Class               nextSiblingClass;
    // ...
};

而实例变量在 class_ro_t（只读） 里：

struct class_ro_t {
    uint32_t         flags;
    uint32_t         instanceStart;
    uint32_t         instanceSize;
    ivar_list_t    * ivars;          // ★ 一维指针，不是数组容器
    method_list_t  * baseMethodList; // 主类自己的方法（编译期确定）
    protocol_list_t* baseProtocols;
    // ...
};

为什么 Category 加不了 ivar，源码级的答案就在这里：

  • methods / properties / protocols 是二维容器，天生支持「再加一个 list」，runtime 有对应的 attachLists 通路；
  • ivars 是 class_ro_t 里的一个裸指针，既在只读结构中，也没有二维容器结构可以追加。

更深一层的原因是内存布局：对象的字节布局（instanceSize、每个 ivar 的偏移）在编译期编码进了 ivarLayout。运行时再追加一个 ivar，意味着所有已存在的同类型实例都要改变布局——而它们散布在堆内存各处，无法迁移。

这就是为什么我们在 Day 9 讲「Associated Object 不改变对象布局」：它绕开的正是这道不可逾越的墙。

二、Category 的方法查找：二维容器的遍历顺序

方法查找时，runtime 遍历的是这个二维数组：

method_array_t.lists
  ├─ [0] CategoryB 的方法列表   ← 最后编译，最先被遍历
  ├─ [1] CategoryA 的方法列表
  └─ [2] 主类的方法列表          ← 最后才轮到

结论：多个 Category 同名时谁生效，取决于编译顺序（Build Phases → Compile Sources 的顺序），而这不是一个可以依赖的契约。 依赖它等于依赖构建配置的偶然排列。

三、为什么说 Category 不该用来「重写」方法

在 Category 里写一个与已有方法同名的方法，runtime 的行为是：

  • 你的实现排在前面被调用；
  • 原来的实现仍然存在，只是排到了后面；
  • 你无法可靠地调用到原实现（super 是指父类，不是主类原实现；遍历方法列表找则依赖顺序）。

后果：

  • 如果系统内部也在某处依赖那个方法的行为，你的版本会静默改变它的语义；
  • 多个 Category 同时这么做，只有一份生效，且不可预测；
  • 排查时崩溃堆栈里看不到 Category 名，只显示目标类名。

正确做法：

目的 该用的手段
给类加新能力 Category（加新方法）
改写已有方法且要保留原实现 Method Swizzling（Day 10）
需要一个新类型 子类

四、Extension 为什么能加 ivar

类扩展在编译期被处理：它的 @property / ivar 直接写入主类的 class_ro_t，成为类定义的一部分。class_ro_t 此时还没有冻结。

Category 走到 attachCategories 时，类的布局早已确定并可能有活跃实例，所以在完全不同的时间点上，能做的事就更少。

五、Swift extension 的对照

OC Category Swift extension
加方法 ✅ ✅
加存储属性 ❌ ❌
决议时机 运行时 attach 编译期（跨模块也是编译期可解析）
同名冲突 运行时静默抢先 编译期报错（invalid redeclaration）

Swift extension 在编译期就能发现 OC Category 要到运行时才发现的重名冲突——这是 Swift 在这件事上明显更安全的地方。

04 设计与取舍

一、Apple 为什么提供 Category

约束：需要给无法修改源码的类加方法；需要把一个巨型类按职责分文件。

候选 问题
子类化 类型变了：NSString 的工厂方法仍返回 NSString，你必须改所有调用点
改源码 系统类做不到；自己的大类拆不开
组合工具类 失去 self.xxx 的调用语法，可读性下降
Category（运行时 attach） 不产生新类型、不要求源码、语法自然 → 被选中

换来什么：

  • 无需源码即可扩展系统类；
  • 把几千行的类按业务分文件，降低单文件复杂度；
  • 调用语法自然（[str xy_md5]）；
  • 不引入新的类型，无需修改既有调用点。

付出什么：

  • 同名冲突无法可靠裁决，依赖编译顺序；
  • 不能加状态（ivar），有状态扩展要另想办法；
  • 静态库场景需要 -ObjC，否则静默失效；
  • +load 会被拖进启动关键路径；
  • 可调试性差：崩溃堆栈与 class_copyMethodList 都不区分 Category 来源。

二、Apple 的取舍

Category 只开放「能安全追加」的三样东西（methods / properties / protocols），不给 ivar。这不是保守，是因为：

ivar 会改变对象布局，而对象布局必须是编译期常量。

于是苹果把「加状态」这件事交给了另一个机制（Associated Object，Day 9），并为此付出了性能与可发现性的代价——这是一次明确的职责切分：Category 负责行为，关联对象负责状态。

三、方案选型

需求 推荐 理由
给系统类加工具方法 Category 唯一自然的方式
拆分自己的大类 Category 降低单文件规模
类内部的私有方法/属性声明 Extension 编译期合并，能加 ivar
需要新的类型身份 子类 Category 不改变类型
需要干干净净的存储 子类或独立模型 ivar 才是正规做法
已有方法要改写且保留原实现 Method Swizzling（Day 10） Category 覆盖不可控
有状态的系统类扩展 Category + 关联对象（Day 9） 或 外部 Map 后者更可调试

四、架构定位

  • 单一所有者：一个 Category 文件只属于一个模块/一个人，避免多人往同一个 Category 里塞东西；
  • 统一命名前缀：xy_ 是不可省略的纪律，不是风格偏好；
  • Category 只加新方法，不改已有行为；
  • 避免在 +load 里做事（详见 05 节替代方案）。

五、与相邻知识的连接

  • Associated Object（Day 9）：Category 加不了 ivar 的直接后果，二者成对出现。
  • Method Swizzling（Day 10）：Category 不能可靠改写已有方法，需要改写时走交换；而 +load 是 swizzling 最常用的执行时机。
  • Runtime / 类结构（Day 4）：class_rw_t / class_ro_t / method_array_t 的二维结构是 Category 能生效的前提。
  • ARC（Day 2）：+load 期间的 autorelease pool、以及 objc_msgSend 查找顺序决定了消息最终落在哪里。

05 工程实战

一、命名前缀：唯一必须的纪律

@interface UIView (XYLayout)
// ✅ 推荐
- (void)xy_pinToEdgesOfView:(UIView *)view;
// ❌ 禁止：无前缀，与任何人（含系统私有方法）都可能撞
- (void)pinToEdgesOfView:(UIView *)view;
@end

理由不仅是三方库冲突——系统框架自己也有未公开的 Category 和私有方法。撞上私有方法时，你的实现会在某些系统版本上替换掉系统内部依赖的行为。

二、单一所有者

❌ 反例：所有人往 NSString+Common.m 里塞
   ├── 用户模块：userId 解析
   ├── 支付模块：金额格式化
   └── 埋点模块：事件名转义
   → 冲突频发，改动互相影响，无法定位谁的责任

✅ 正例：按模块拆分
   NSString+UserAuth.m
   NSString+Payment.m
   NSString+Tracking.m
   → 每个文件一个所有者，冲突面大幅缩小

三、有状态扩展：优先独立对象

Category 想要状态时有三个选项，按优先级：

方案 适用 评价
独立的管理者对象（如 XYBadgeManager） 状态可以被归类管理 ✅ 首选：可发现、可测试、可调试
外部 Map（NSMapTable / 字典） 需要按对象索引一堆数据 ✅ 可枚举、可调试
Associated Object（Day 9） 状态与单个对象强绑定、量小、访问不频繁 ⚠️ 最后手段：隐式、无类型检查 
// ✅ 首选
[XYBadgeManager setBadge:@"new" forView:self.view];

// ⚠️ 最后手段
objc_setAssociatedObject(self, @selector(xy_badge), badge, OBJC_ASSOCIATION_COPY_NONATOMIC);

四、不要用 +load 做注册

+load 在 main 之前执行，每写一个就给启动时间加一笔，而且它带来的隐式的、不可控的执行时机非常难排查。

替代方案：显式注册表 + 惰性初始化

// 集中注册（App 启动时显式调用一次，时机可控、可度量）
@implementation XYModuleRegistry
+ (void)registerAllModules {
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        [XYUserModule new];
        [XYPayModule new];
    });
}
@end

对比：

+load 注册 显式注册
时机 main 之前，不可控 你调用的那一行
可度量 ❌ 藏在 dyld 阶段 ✅ 可用 signpost 打点
依赖顺序 靠编译顺序 代码里写清楚
移除的影响 悄悄消失 编译错误或显式改动

如果必须用 +load（比如 Method Swizzling 需要在类被使用之前完成），要遵守：里面只做最小动作，绝不做网络、磁盘、加锁等待等重活（详见 Day 10）。

五、验证 Category 是否真的生效

静态库的 Category 经常「悄悄没附上」，必须能自己验证：

// 1. 运行时检查方法是否存在
XCTAssertTrue([NSString instancesRespondToSelector:@selector(xy_md5)]);

// 2. 打印一个类的全部方法，确认 Category 方法在列表中
unsigned int count = 0;
Method *list = class_copyMethodList([NSString class], &count);
NSMutableArray *names = [NSMutableArray array];
for (unsigned int i = 0; i < count; i++) {
    [names addObject:NSStringFromSelector(method_getName(list[i]))];
}
free(list);
NSLog(@"%@", [names componentsJoinedByString:@", "]);

// 3. Mach-O 层面确认 Category 被链接进产物（被打成静态库时尤其适用）
// $ nm -m YourApp | grep objc_catlist
// $ otool -o YourApp | grep -A2 category

检查清单：

现象 优先怀疑
Category 方法 unrecognized selector 静态库缺 -ObjC；文件未加入 Target Membership
方法行为与预期不符 多个 Category 同名，顺序不确定
Debug 好 Release 崩 Release 的链接优化丢掉了 Category
只在部分机型/系统版本异常 撞上了系统私有方法

六、工程护栏

  1. 方法名一律加模块前缀，无例外；
  2. Category 只加新方法，不写与主类同名的方法；
  3. 一个 Category 文件一个所有者；
  4. 不用 +load 做业务注册；
  5. 静态库集成后，用 nm/otool 验证 __objc_catlist 里有你的 Category；
  6. CI 加一条检查：扫描所有 (CategoryName)，报出重名 selector。

+load 做重活 在 main 之前执行 启动变慢、难以度量 改显式注册
+load 内依赖其他类 其他类可能未初始化 死锁或读到不完整状态 load 里只做最小动作
+load 里写 [super load] load 不走消息发送 误以为继承了行为 不写
+initialize 被多次调用 子类未实现会调父类 初始化逻辑重复执行 dispatch_once 或 self == Cls 判断
多个 Category 拆分过细 方法被分散 调试时找不到实现 单一所有者 + 合理粒度
崩溃堆栈看不到 Category 符号只记录类名 排查方向不明 靠方法名前缀反查
Category 方法与协议方法同名 全局 SEL 唯一 意外实现了别人的协议 命名检查

三条反思

  1. Category 的「覆盖」从来不是替换，这是理解它一切怪异行为的钥匙。 因为原实现还在数组后面，所以「多个 Category 谁生效」取决于编译顺序这种非契约的东西；因为 super 找的是父类而不是主类原实现，所以你无法像重写那样「先做自己的事再调 super」。一旦理解它是顺序插入而不是替换，很多坑就能自己推出来。
  2. 不能加 ivar 不是功能缺失，是刻意切分。 Category 负责行为、关联对象负责状态——苹果把两件事拆成两个机制，是为了守住「对象布局必须是编译期常量」这条底线。选哪个，取决于你要加的是方法还是数据。用 Category 加状态，等于要求它突破自己的设计前提。
  3. +load 的隐式性是它的致命问题。 它把「什么时候初始化」交给了 ld 和编译顺序，而不是代码里的某一行。这在单人开发时不痛，在几十个模块、上百个 Category 的工程里，会造成启动时间神秘增长、依赖顺序不可推理、删掉一个文件引发连锁失效。凡是能被显式调用替代的注册表，都不该用 +load。

  1. Category、Extension（类扩展）和 Subclass 有什么区别？Extension 为什么常被误称为「匿名 Category」？

08 掌握标准

一句话总结：Category 编译成 category_t 存进 Mach-O 的 __objc_catlist，镜像加载时 attachCategories 用 attachLists 把它的方法列表 memmove 到原列表之前，消息查找从前向后遍历，于是 Category「抢先」命中——所谓覆盖是查找顺序，不是替换；而 class_rw_t 中只有 methods / properties / protocols 是二维可追加容器，ivars 却在只读的 class_ro_t 里是个裸指针，这从源码层面解释了 Category 为何加不了实例变量。

掌握标准：

  • 60 分：能分清 Category / Extension / Subclass 的差异；能写出带前缀的 Category；知道 Category 不能加 ivar、@property 不合成；知道静态库要加 -ObjC。
  • 80 分：能画出从 category_t 到 attachLists 的完整链路并解释方法列表的二维数组结构；能从该结构推出「多 Category 同名依赖编译顺序」和「super 不指向主类原实现」；能说清 +load 与 +initialize 的时机、顺序与调用次数差异。
  • 100 分：能从 class_rw_t / class_ro_t 的结构差异给出「不能加 ivar」的源码级论证，并将其与 Day 9 的关联对象连成完整因果；能论证为何 Category 不该用于改写已有方法、何种情况应改用 swizzling；能设计出替代 +load 的显式注册方案并说明它带来的可度量性收益；能把「前缀 + 单一所有者 + 只加新方法」落成团队可执行且可被 CI 检查的规范。
