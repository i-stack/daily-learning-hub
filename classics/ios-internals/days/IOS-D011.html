IOS-D011

Message Forwarding：消息转发完整链路

动态系统 · 2026-08-20 · Message Forwarding / 消息转发 / resolveInstanceMethod / forwardingTargetForSelector / methodSignatureForSelector / forwardInvocation / NSInvocation / NSProxy / Aspects
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准参考资料

消息转发是 objc_msgSend 查找失败后的兜底链路：先给一次动态补方法的机会，再给一次转交给别人的机会，最后才用 NSInvocation 完整转发。本课打通三阶段的触发条件、能力边界与性能代价，说明它在多播代理、AOP 与崩溃防护中的角色，以及为什么「吞掉未知消息」通常是错的选择。

01 背景与 API

要解决的问题

unrecognized selector sent to instance 0x... 是 iOS 最常见的崩溃之一。它的含义是：消息查找走完本类、走完所有父类，仍然没有找到 SEL 对应的 IMP。

在直接崩溃之前，runtime 给了对象三次自救机会：

  1. 能不能现在补一个方法实现？（动态方法解析）
  2. 能不能交给别的对象处理？（快速转发）
  3. 能不能让我自己决定怎么处理这条消息？（完整转发）

都不处理，才调用 doesNotRecognizeSelector: 抛异常。

三阶段 API

阶段 API 类型 能做什么
① 动态方法解析 +resolveInstanceMethod: <br> +resolveClassMethod: 类方法 用 class_addMethod 现场加一个 IMP
② 快速转发 -forwardingTargetForSelector: 实例方法 返回一个能处理该 SEL 的对象
③ 完整转发 -methodSignatureForSelector: <br> -forwardInvocation: 实例方法 拿到 NSInvocation，改 target / 改参数 / 改返回值 / 多播
兜底 -doesNotRecognizeSelector: 实例方法 抛异常（不要自己调）

NSInvocation 是什么

NSInvocation 把一次消息调用对象化：

NSInvocation *inv = invocation;
[inv getArgument:&arg atIndex:2];   // 0=self, 1=_cmd, 2 起是真实参数
[inv setArgument:&arg atIndex:2];
[inv invoke];
[inv invokeWithTarget:otherObject];
id ret = nil;
[inv getReturnValue:&ret];          // 注意：返回的是 unsafe unretained

底层入口

查找失败后，runtime 把 IMP 替换成转发入口：

  • _objc_msgForward_impcache（汇编缓存入口）
  • _objc_msgForward（C 入口，旧架构还有 _objc_msgForward_stret 用于结构体返回）
  • 随后进入 CoreFoundation 的私有函数 ___forwarding_prep_0 → ___forwarding___，由它依次调用上述三个阶段。

一个最小例子

// 阶段 ②：把不认识的消息转给内部对象
- (id)forwardingTargetForSelector:(SEL)sel {
    if ([_realWorker respondsToSelector:sel]) {
        return _realWorker;
    }
    return [super forwardingTargetForSelector:sel];
}

02 运行机制

一、完整链路

flowchart TD
  A["objc_msgSend 查找失败"] --> B["IMP = _objc_msgForward_impcache"]
  B --> C["___forwarding___ 进入转发"]
  C --> D{"阶段一：resolveInstanceMethod:"}
  D -- "class_addMethod 成功" --> D1["标记已解析，回到查找流程重试"]
  D1 --> D2["命中新增 IMP，正常执行"]
  D -- 未添加 --> E{"阶段二：forwardingTargetForSelector:"}
  E -- "返回非 nil 对象" --> E1["消息原样重发给该对象"]
  E1 --> E2["objc_msgSend"]
  E -- 返回 nil --> F{"阶段三：methodSignatureForSelector:"}
  F -- 返回 nil --> G["doesNotRecognizeSelector: 抛异常"]
  F -- "返回 NSMethodSignature" --> H["构造 NSInvocation"]
  H --> I["forwardInvocation:"]
  I --> J{"是否调用 invoke / invokeWithTarget:"}
  J -- 是 --> K["执行目标实现，可改参数与返回值"]
  J -- 否 --> L["消息被静默丢弃"]

二、阶段一：动态方法解析

+ (BOOL)resolveInstanceMethod:(SEL)sel {
    if (sel == @selector(dynamicMethod)) {
        IMP imp = imp_implementationWithBlock(^(id self, ...) {
            NSLog(@"动态补上的实现");
        });
        class_addMethod(self, sel, imp, "v@:");   // 加在本类上
        return YES;
    }
    return [super resolveInstanceMethod:sel];
}

要点：

  • 这是类方法（+），因为要在类上加方法；
  • 类方法未找到时走 +resolveClassMethod:，此时要加到元类上；
  • runtime 会重新走一遍完整查找（retry），所以新增的 IMP 会被找到并回填缓存；
  • 每个 SEL 只解析一次：解析失败后会置 triedResolver 标记，不再重复调用；
  • 返回 YES / NO 其实不影响结果——runtime 只看方法有没有真的被加进去。

典型用途：@dynamic 属性的存取方法（Core Data 的 NSManagedObject 就是这个机制）、按需生成方法。

三、阶段二：快速转发

- (id)forwardingTargetForSelector:(SEL)sel {
    if ([_worker respondsToSelector:sel]) return _worker;
    return [super forwardingTargetForSelector:sel];   // 返回 nil 进入阶段三
}
  • 返回一个对象 → 消息被原样重发给该对象，等价于 objc_msgSend(target, sel, ...)；
  • 不能修改参数、不能改返回值、不能多播；
  • 成本最低——只多一次消息发送；
  • 这是实现「代理 / 装饰器 / 多继承模拟」最划算的一层。

四、阶段三：完整转发

- (NSMethodSignature *)methodSignatureForSelector:(SEL)sel {
    NSMethodSignature *sig = [super methodSignatureForSelector:sel];
    if (!sig) sig = [_worker methodSignatureForSelector:sel];
    return sig;   // 返回 nil 则直接 doesNotRecognizeSelector:
}

- (void)forwardInvocation:(NSInvocation *)invocation {
    if ([_worker respondsToSelector:invocation.selector]) {
        [invocation invokeWithTarget:_worker];    // 转交
    } else {
        [super forwardInvocation:invocation];     // 默认实现会调 doesNotRecognizeSelector:
    }
}
  • methodSignatureForSelector: 返回 nil → 直接崩溃，连 forwardInvocation: 都不会调；
  • 有了签名，runtime 才能构造 NSInvocation（它需要知道参数个数、类型、返回值类型）；
  • forwardInvocation: 的 NSObject 默认实现就是调用 doesNotRecognizeSelector:——所以「只实现 forwardInvocation: 而忘了 invoke」等于吞掉消息。

五、各阶段能力对比

能力 ① 动态解析 ② 快速转发 ③ 完整转发
修改参数 否 否 是
修改返回值 否 否 是
多播给多个对象 否 否 是
作用范围 类级（所有实例） 实例级 实例级
触发次数 每 SEL 一次 每次调用 每次调用
相对成本 一次（之后走缓存） ~1 次额外消息 1~2 个数量级

03 底层原理

一、根本命题：把「找不到」变成一次可编程的机会

静态语言里，调用不存在的方法 = 编译错误。Objective-C 把它变成运行时的一段可编程流程：查找失败不是终点，而是进入转发流程的起点。

这带来两个本质能力：

  1. 存在性可以被伪造：一个对象可以不实现某方法，仍然「能响应」它（阶段一现加、阶段二转交）。
  2. 调用可以被重放：NSInvocation 把一次调用变成数据，于是可以延迟执行、改参数、多播、甚至跨进程/跨语言（热修方案正是靠这个）。

二、查找与转发的衔接点

关键点在于：转发不是一个独立的 API，而是「查找失败时填进缓存的那个 IMP」。

lookUpImpOrForward 在确认找不到后：

imp = _objc_msgForward_impcache;
log_and_fill_cache(cls, sel, imp, receiver);   // 注意：会把转发入口也缓存起来

两个重要推论：

  • 转发入口会被缓存，所以同一个未实现 SEL 第二次调用不会再走慢速查找；
  • 也因为被缓存，阶段一只有第一次有机会执行——它加上方法后，缓存里已经是转发入口了……实际上 runtime 在 resolve 成功后会清掉这条转发缓存并重试，所以第一次调用会正常命中新方法。

三、为什么需要 methodSignature

NSInvocation 必须知道参数的个数、类型、大小才能在栈/寄存器上正确摆放参数。这些信息全部来自 NSMethodSignature，也就是 Type Encoding。

签名错误的后果不是「转发失败」，而是ABI 不匹配导致的栈破坏：

场景 后果
返回值类型写错（如 void 当成 id） 返回值寄存器被错误解读 → 野指针
参数个数写少 目标方法读到垃圾寄存器
结构体返回未用正确编码 sret 隐藏参数错位 → 崩溃

这正是「转发比 swizzling 危险」的地方：swizzling 要求你自己写对签名，转发允许你在运行时撒谎。

四、Aspects 的原理：把转发当成 AOP 的织入点

Aspects 这类 block 型 hook 库的做法：

flowchart LR
  A["原方法 SEL"] -- "method_setImplementation" --> B["IMP 指向 _objc_msgForward"]
  B --> C["调用该 SEL 时直接进入转发"]
  C --> D["hook 过的 forwardInvocation:"]
  D --> E["按 SEL 取出 aspect 链"]
  E --> F["依次执行 before / 原 IMP / after"]
  1. 把目标 SEL 的 IMP 改成 _objc_msgForward；
  2. swizzle forwardInvocation:；
  3. 在自己的 forwardInvocation: 里按 SEL 查表，取出原始 IMP 与注册的 block，按 before / instead / after 顺序执行；
  4. 用 NSInvocation 调用原始 IMP。

推论：

  • 这类方案必须依赖消息转发，所以性能远低于直接 swizzling（Day 10）；
  • 与其他同样 hook forwardInvocation: 的库（如 ReactiveCocoa 的早期版本）互相覆盖，必然冲突；
  • 好处是可以用 block 写切面，且能拿到 NSInvocation 改参数。

五、Swift 的限制

纯 Swift 类型没有消息转发——它连 objc_msgSend 都不走。只有：

  • 继承 NSObject 的类，且方法是 @objc 暴露的，才可能进入转发；
  • struct / enum 完全不支持。

六、可变参数的死角

NSInvocation 无法可靠转发可变参数方法（如 +[NSString stringWithFormat:]）——C 的可变参数 ABI 无法在运行时重建参数列表。遇到这类方法，转发链路要么崩溃、要么参数错乱。

04 设计与取舍

一、Apple 为什么分三阶段

一句话：能力递增，成本也递增。

阶段 苹果给的定位 为什么放在这个位置
① 动态解析 「这个类的所有实例都需要这个方法」 结果进方法列表、进缓存，成本只付一次，最划算
② 快速转发 「这个实例把消息交给别人」 只需一次额外消息发送，覆盖最常见需求（代理/装饰器）
③ 完整转发 「这条消息要被当作数据处理」 成本最高，但能力也最强（改参、改返回值、多播）

这个分层的设计意图很明确：让 90% 的需求停在前两阶段，只有真正的元编程需求才付出 NSInvocation 的代价。

二、换来什么

  • unrecognized selector 崩溃可以被兜底与观测；
  • 无需继承即可实现代理、装饰器、多继承模拟；
  • NSInvocation 让「一次调用」变成可传递的数据，支撑了多播代理、AOP、热修、Mock 测试；
  • 与 Core Data 的 @dynamic、KVO、Category 共享同一套键/签名约定。

三、付出什么

  • 性能：阶段三要构造 NSMethodSignature + NSInvocation，比直接调用慢 1~2 个数量级；
  • 错误被推迟：吞掉未知消息后，错误从「立刻崩溃」变成「某个下游状态不对」，排查成本陡增；
  • 可推理性：静态分析看不到转发，调用关系在源码里是断的；
  • ABI 风险：签名写错的后果是栈破坏，不是抛异常。

四、架构判断

用途 建议
代理 / 装饰器 / 多继承模拟 推荐，优先用阶段二
多播代理（一处调用通知多个 observer） 可用阶段三，但要考虑改用显式的事件数组
AOP 切面 优先 Method Swizzling（Day 10）；需要改参数才用转发型库
崩溃防护（吞掉 unrecognized selector） 不推荐，见「06 常见坑」
热修（JSPatch 类） 苹果明确限制，有审核风险

五、与相邻知识的连接

  • Runtime（Day 4）：本课是 objc_msgSend 查找链路的最后一个分支。
  • NSProxy（Day 12）：NSProxy 是「天生为转发而生」的抽象类，它连 methodSignatureForSelector: 都要求你自己实现。
  • Method Swizzling（Day 10）：Aspects 用转发做 hook，与直接换 IMP 的方案形成对比。
  • KVO（Day 6）：都依赖 runtime 的动态性，但 KVO 改 isa、转发改 IMP。

05 工程实战

一、实验：记录每个阶段的触发顺序

@implementation Target

+ (BOOL)resolveInstanceMethod:(SEL)sel {
    NSLog(@"① resolveInstanceMethod: %@", NSStringFromSelector(sel));
    return [super resolveInstanceMethod:sel];
}

- (id)forwardingTargetForSelector:(SEL)sel {
    NSLog(@"② forwardingTargetForSelector: %@", NSStringFromSelector(sel));
    return [super forwardingTargetForSelector:sel];   // nil → 进阶段三
}

- (NSMethodSignature *)methodSignatureForSelector:(SEL)sel {
    NSLog(@"③ methodSignatureForSelector: %@", NSStringFromSelector(sel));
    return [NSMethodSignature signatureWithObjCTypes:"v@:"];  // 必须与真实签名一致
}

- (void)forwardInvocation:(NSInvocation *)invocation {
    NSLog(@"④ forwardInvocation: %@", NSStringFromSelector(invocation.selector));
}

@end

对一个未实现的 foo 发消息，控制台应依次出现 ①②③④；把 ③ 改成返回 nil，则 ④ 不出现并直接崩溃——这是验证「签名决定能否进入完整转发」的最小实验。

二、场景一：多播代理

- (NSMethodSignature *)methodSignatureForSelector:(SEL)sel {
    for (id target in self.targets) {
        NSMethodSignature *sig = [target methodSignatureForSelector:sel];
        if (sig) return sig;
    }
    return [super methodSignatureForSelector:sel];
}

- (void)forwardInvocation:(NSInvocation *)invocation {
    for (id target in self.targets) {
        if ([target respondsToSelector:invocation.selector]) {
            [invocation invokeWithTarget:target];   // 同一个 invocation 可重复 invoke
        }
    }
}

注意：多播时若多个 target 都写返回值，只有最后一次 getReturnValue 的结果有意义，需明确约定。

三、场景二：代理与装饰器（优先用阶段二）

- (id)forwardingTargetForSelector:(SEL)sel {
    // 只对约定的协议方法转发，其余交给 super，避免吞掉意外消息
    if (protocol_getMethodDescription(@protocol(MyProto), sel, NO, YES).name != NULL) {
        return _impl;
    }
    return [super forwardingTargetForSelector:sel];
}

四、场景三：崩溃防护——以及为什么不推荐

// 常见但有害的写法
- (NSMethodSignature *)methodSignatureForSelector:(SEL)sel {
    return [NSMethodSignature signatureWithObjCTypes:"v@:"];  // 对所有未知消息都给签名
}
- (void)forwardInvocation:(NSInvocation *)invocation {
    NSLog(@"吞掉 %@", NSStringFromSelector(invocation.selector));  // 什么都不做
}

问题：

  1. 调用方以为方法执行了，实际什么都没发生——错误从崩溃变成错误的数据；
  2. 若方法本该有返回值，调用方拿到的是未初始化的栈/寄存器值；
  3. 所有类都挂上这个分类后，真正的编程错误全被掩盖，问题在几步之后以完全不相干的形式暴露。

如果一定要做，至少满足：

  • 只在线上开启，Debug 期必须崩溃；
  • 上报完整信息（类名、SEL、调用栈），并设熔断（同一 SEL 超阈值即停止）；
  • 只保护明确白名单内的系统类/第三方类，绝不给自己的业务类兜底。

五、ABI 一致性检查清单

检查项 说明
返回值类型 methodSignature 的返回值编码必须与真实方法一致
参数个数与顺序 从 index 2 开始是真实参数
结构体返回 大结构体走隐藏的 sret 指针，编码必须正确
可变参数 无法可靠转发，应直接禁止
对象返回值内存语义 getReturnValue: 取到的是 unretained，需自己 retain

六、调试技巧

  • 崩溃时先看日志里的完整 SEL 与 receiver 真实类（object_getClass）；
  • 下符号断点 ___forwarding___ 可观察三阶段的实际执行；
  • 用 class_respondsToSelector 与 methodSignatureForSelector: 判断对象是否「真的」能处理；
  • 检查是否被 KVO 改写 isa、或被 Aspect 类库 hook 了 forwardInvocation:。

06 常见坑与反思

高频坑位表

坑 成因 症状 规避
forwardingTargetForSelector: 返回 self 消息又发回自己 死循环直到栈溢出 必须排除自己；返回前判断 target != self
只实现 forwardInvocation: 不 invoke 默认实现才是 doesNotRecognizeSelector: 消息被静默吞掉 明确调用 invoke / invokeWithTarget:，否则交 super
methodSignatureForSelector: 返回错误签名 编码与实际方法不符 栈破坏、野指针、随机崩溃 从真实 target 取签名，不要手写
返回 self 造成循环（阶段三） invokeWithTarget:self 死循环 同上
吞掉未知消息 全类名目兜底 编程错误变成数据错误，排查成本陡增 见上一节防护前提
respondsToSelector: 判断为 NO 默认实现不触发转发 明明「能响应」却被判否 若需表达转发能力，显式重写 respondsToSelector:
resolveInstanceMethod: 只调一次 resolve 后 retry 并缓存 第二次进来不再解析 需要持久能力就真的 class_addMethod
类方法走了实例方法的解析 类方法在元类 hook 无效 用 +resolveClassMethod:，加到 object_getClass(cls)
可变参数转发 C 可变参数 ABI 无法重建 参数错乱 / 崩溃 禁止转发这类方法
与 Aspects / RAC 冲突 都 hook forwardInvocation: 一方的切面静默失效 全项目只用一种转发型 hook 库
性能 NSInvocation 构造开销大 高频调用掉帧 高频路径用阶段二或直接调用

三条反思

  1. 返回 self 会循环，吞掉未知消息会把编程错误推迟成数据错误。 前者立刻暴露，后者潜伏到生产——后者的危害大得多。
  2. 转发让「调用」变成了数据，也就让控制流离开了源码。 用之前先问：这个需求能不能用协议、显式事件或组合来解决？
  3. 签名是转发的 ABI 契约。 swizzling 的签名由编译器检查，转发的签名由你在运行时提供——编译器帮不上忙的地方，就是最容易出事的地方。

07 知识验收

  1. 按顺序列出消息转发的三个阶段，各自的 API 是类方法还是实例方法？每个阶段分别能做什么、不能做什么？
  2. 画出从 objc_msgSend 查找失败到 doesNotRecognizeSelector: 的完整链路，标出每个判断节点的分支条件。
  3. methodSignatureForSelector: 返回 nil 会发生什么？返回一个错误的签名又会发生什么？为什么后者更危险？
  4. 为什么 resolveInstanceMethod: 每个 SEL 只会被调用一次？runtime 在这一步之后做了什么？
  5. 类方法找不到时应该实现哪个方法？实现要加到哪个类上？
  6. forwardInvocation: 的 NSObject 默认实现做了什么？「实现了它但消息还是丢了」通常是什么原因？
  7. respondsToSelector: 会触发消息转发吗？如果一个对象靠转发响应方法，如何让外界正确判断它的能力？
  8. Aspects 这类 block 型 hook 库是怎么利用消息转发的？它相比直接 Method Swizzling 有哪些取舍？
  9. 为什么 NSInvocation 无法可靠转发可变参数方法？还有哪些签名场景容易出问题？
  10. 线上崩溃防护用转发吞掉 unrecognized selector，为什么通常被认为是有害的？如果必须做，需要哪些前提？
  11. 给出一个真实（或可信构造的）故障：现象、证据链（用到哪些 runtime 或 lldb 手段）、根因与改进方案。
  12. 什么条件下你会选择协议 / 显式事件 / 组合，而不是消息转发？

08 掌握标准

一句话总结：消息转发是查找失败后的三级兜底——先 resolveInstanceMethod: 现场补方法（类级、只一次），再 forwardingTargetForSelector: 原样转交给别的对象（最快、不能改参数），最后 methodSignatureForSelector: + forwardInvocation: 用 NSInvocation 完整接管（最慢、可改参改返回值可多播）；签名返回 nil 则直接 doesNotRecognizeSelector:。

掌握标准：

  • 60 分：能按顺序说出三阶段的 API 与能力边界；能解释为什么 methodSignatureForSelector: 返回 nil 就不再进入 forwardInvocation:；知道 forwardInvocation: 默认实现是 doesNotRecognizeSelector:。
  • 80 分：能独立写出「记录三阶段触发顺序」的最小实验；能实现多播代理与装饰器；能定位「消息被吞」「返回 self 死循环」「签名不匹配导致随机崩溃」三类故障。
  • 100 分：能讲清转发入口如何被填进 cache_t、动态解析为何只执行一次；能解释 Aspects 的转发型 hook 原理及其与 Method Swizzling 的取舍；能论证为什么「吞掉未知消息」是有害的，并给出把转发收敛在基础设施边界的架构方案。
