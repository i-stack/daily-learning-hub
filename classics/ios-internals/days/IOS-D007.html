AutoreleasePool：延迟释放与内存峰值

内存管理 · 2026-08-16 · AutoreleasePool / AutoreleasePoolPage / pop / 哨兵对象 POOL_BOUNDARY / RunLoop / 内存峰值 / TLS 优化 / objc_autoreleasePoolPush
01 背景与 API02 运行机制03 底层原理04 设计与取舍05 工程实战06 常见坑与反思07 知识验收08 掌握标准参考资料

AutoreleasePool 是一套「延迟释放」机制：把对象暂时挂进线程私有的 AutoreleasePoolPage 双向链表，池 pop 时统一发 release。它不是 GC，也不回收循环引用，它唯一的作用是把「一次性产生的大量临时对象」的释放时机提前到你能控制的位置，从而压平内存峰值。理解它的关键在三件事：page 的栈结构与哨兵对象、它与 RunLoop / Thread / Task 的绑定关系，以及与它配套的 TLS 返回值优化。

01 背景与 API

要解决的问题

ARC 管不了一种对象：你创建但不持有的对象。

+ (instancetype)userWithName:(NSString *)name {
    User *u = [[User alloc] init];   // 持有
    return u;                        // 返回，但调用方还没来得及持有
}

此时 u 这一强引用即将出作用域。如果这里直接 release，对象在调用方拿到之前就死了；如果不 release，就泄漏。

AutoreleasePool 给出的答案是：先 release 一次到 pool 里，pool 稍后再补一次 release。 于是对象能活到「当前这一次事件处理结束」，足够调用方接手。

对应的 API

写法 版本 说明
@autoreleasepool { ... } 推荐（LLVM 3.0+） 编译期为 objc_autoreleasePoolPush / Pop，作用域清晰
NSAutoreleasePool *p = [NSAutoreleasePool new]; ... [p drain]; MRC 遗留 已被 @autoreleasepool 取代，ARC 下不可用 
@autoreleasepool {
    for (int i = 0; i < 100000; i++) {
        id obj = [self makeBigObject];   // 进入池
    }
}   // 作用域结束 → pop → 全部 release

Swift 对应：

func run() {
    autoreleasepool {
        for _ in 0..<100000 { _ = makeBigObject() }
    }
}

三个必须分清的概念

概念 是什么 什么时候释放
栈上对象 局部变量，编译器插入 release 出作用域
autorelease 对象 进了 pool pool pop 时
被强引用持有的对象 被强引用 强引用消失时（Day 2）

AutoreleasePool 不是 GC。 它不扫描、不追踪、不回收<｜hy_place▁holder▁no▁813｜>ycle，只是把 release 延后到某个点统一执行。

编译器做了什么

@autoreleasepool {} 会被翻译成：

void *ctx = objc_autoreleasePoolPush();
// ... 你的代码 ...
objc_autoreleasePoolPop(ctx);

它不是 OC 对象，是一对 C 函数调用。

02 运行机制

一、AutoreleasePoolPage：线程私有的栈

池不是对象，是由 AutoreleasePoolPage 组成的双向链表，每个 page 是一块虚拟内存页：

每个 page 的大小是 4096 字节（虚拟内存页），其中：

  • 前 56 字节是成员变量（AutoreleasePoolPageData）；
  • 剩下的空间用来从低地址向高地址压入对象指针，像一个栈；
  • next 指向下一个可写入位置。

page 之间通过 parent / child 指针连成双向链表。一个 page 满了就 child = new Page()。

每个线程有自己的 page 链表（存在 TLS 里），互不干扰。

二、push：压一个哨兵

objc_autoreleasePoolPush()
  ↓
取当前线程的 hotPage（TLS 里存的最新 page）
  ↓
写入 POOL_BOUNDARY（哨兵对象，值为 nil，仅占一个指针宽度）
  ↓
返回这个哨兵的**地址**作为 token

哨兵是分层的标记。 嵌套多个 @autoreleasepool 时，栈里就有多个哨兵，pop 时用地址判断停在哪个。

低地址 ────────────────────────────► 高地址
[BOUNDARY][a][b][BOUNDARY][c][d][BOUNDARY][e]
   ↑外层token      ↑内层token      ↑最新

三、autorelease：把对象指针压栈

objc_autorelease(obj)
  ↓
取当前 hotPage
  ↓
page 未满 → *next++ = obj
  ↓
page 已满 → 找/新建 child page，再压入

注意：压入的是对象地址，不是对象本身。 对象早在 autorelease 之前就分配好了。

四、pop：释放到哨兵为止

objc_autoreleasePoolPop(token)
  ↓
① 找到 token 所在的 page
② 从 page 的栈顶（next）向前遍历，对每个地址发送一次 release
   —— 遇到哨兵就停止
③ 把 next 移回该哨兵位置
④ 清理不再需要的 child page
⑤ 更新 hotPage

关键语义：pop 会对区间内每个对象发送一次 release ——注意是 release，不是 release + 置 nil。对象是否真的释放取决于它当前的引用计数（可能还有其他强引用）。

五、池什么时候被 pop

| 场景 | 谁负责 pop | | --- | --- | --- | | 主线程 RunLoop | 系统在每轮 RunLoop 的特定时机压/弹：进入时 push，休眠前 pop + push，退出时 pop（详见 03 节） | | @autoreleasepool {} | 编译器在作用域进出处配对调用 | | 子线程 | 不会自动 pop——如果没有自己的 pool，临时对象会一直堆积 | | dispatch_queue | 每条 GCD 队列的线程自带一个 pool（系统创建线程时已经包好），但具体何时 pop 没有保证 | | main() | UIApplicationMain 之外的 @autoreleasepool 包住整个 main |

子线程最重要的事实：主线程因为有 RunLoop，autorelease 对象最多活到下一次 RunLoop 循环；而没有 RunLoop 的子线程，如果你不自己建池，对象会一直堆积到线程结束。

03 底层原理

一、根本命题：把「释放时机」从一个不可控点挪到一个可控点

为什么需要延迟释放？因为返回值的所有权转移有一个时间差。

+ (User *)userWithName:(NSString *)name {
    User *u = [[User alloc] init];
    return u;    // u 的强引用即将出作用域，但调用方还没持有
}

User *u = [User userWithName:@"a"];   // 调用方在这里才持有

ARC 的解法是把这个对象扔进 pool：让它在当前这次调用链走完之后才被 release。这样调用方一定有足够时间 retain。

这个「当前这次调用链结束」的粒度，在 iOS 主线程上就是一次 RunLoop 循环——这是 AutoreleasePool 与 RunLoop 强耦合的根本原因。

二、栈结构决定了三个性质

page 是一个从低地址向高地址增长的栈，这个数据结构直接决定了：

  1. 自动释放是严格逆序的：后压入的对象先 release；
  2. 嵌套 pool 天然成立：哨兵分层，pop 到哪层取决于 token 地址；
  3. 代价极小：一次 autorelease 就是一次指针写入，比 malloc/free、比维护引用计数便宜得多。

所以「autorelease 很贵」是误解。贵的是对象迟迟不释放导致的内存峰值，不是 autorelease 本身。

三、TLS 返回值优化：为什么很多对象根本不进池

这是理解现代 ARC 性能的关键（Day 2 已铺垫，这里完整展开）：

被调方 objc_autoreleaseReturnValue(obj)
   ├── 检查调用方接下来要执行的指令（用返回值地址在 TLS 里查）
   ├── 如果紧跟的是 objc_retainAutoreleasedReturnValue
   │     → 什么也不做，直接返回 obj（计数保持 +1 传给调用方）
   └── 否则
         → 走正常路径：objc_autorelease(obj)，进 pool

调用方 objc_retainAutoreleasedReturnValue(obj)
   ├── 检查 TLS 里记录的这个返回状态
   ├── 如果已标记为「已直接传递」 → 直接返回 obj，不做 retain
   └── 否则 → 正常 objc_retain

结果：[[User alloc] init]、[User new]、[User userWithName:] 这类常见写法，对象和 obj 完全不进 autorelease pool。

依赖条件：编译器必须在调用方插了 objc_retainAutoreleasedReturnValue 才能触发。这意味着——

写法 是否触发优化
User *u = [User userWithName:@"a"]; ✅
User *u = ???; 返回值后面立刻被 retain 取决于编译器是否插入该调用
返回值被赋给 _unsafe_unretained / weak ❌（不 retain，仍会进 pool）
block 捕获 + ARC 优化插入 retain 通常 ✅

实践结论：不要为了「避免 autorelease」写出扭曲的代码。 现代 ARC 已经把绝大多数返回值路径优化掉了；真正需要你处理的是循环内产生的大量临时对象。

四、内存峰值：真正需要 @autoreleasepool 的场景

// ❌ 峰值 = 10000 个 UIImage 同时存活
for i in 0..<10000 {
    let img = UIImage(contentsOfFile: path(i))
    process(img)
}

// ✅ 每轮结束就释放，峰值 = 1 个 UIImage
for i in 0..<10000 {
    autoreleasepool {
        let img = UIImage(contentsOfFile: path(i))
        process(img)
    }
}

三种典型场景：

场景 为什么堆临时对象
批量图片解码 / 缩略图生成 每张图的 bitmap 是几 MB 的临时对象
大批量数据序列化 / 解析（JSON、CSV、Core Data 导入） 每个 record 一个 ObjC/Swift 对象
后台长任务（导出文件、迁移数据库） 没有 RunLoop 兜底，堆积到线程结束

注意粒度：池放在循环内，不是循环外。循环外加一圈等于没加（峰值不变）。

五、AutoreleasePool 不能做什么

误解 事实
「pool 能回收内存」 它只是发送 release；对象是否释放取决于引用计数
「pool 能解决循环引用」 完全不能，环里的对象计数永不归零（Day 2）
「pool 替代 ARC」 它是 ARC 的补充，处理「返回但不持有」的所有权转移
「把对象丢进 pool 就安全了」 恰恰相反，它延长了对象寿命
「子线程不用管」 子线程没有 RunLoop 兜底，最需要管

04 设计与取舍

一、Apple 为什么需要这套机制

约束：返回值的所有权转移存在时间差；同时希望 -method 返回对象这类写法（而非 +alloc 系列）保持便利。

候选 问题
让调用方负责 release（MRC 的 copy/new 规则） 心智负担重，漏即泄漏
延迟到某个全局 GC 时机 放弃确定性释放（Day 2 的取舍）
per-thread 的释放池 + 明确的 pop 点 既保持确定性，又能处理返回值 → 被选中

换来什么：

  • 返回值的所有权语义成立（[User userWithName:] 这种写法才可能存在）；
  • 延迟释放的成本压到极限：一次指针写入；
  • 与 RunLoop 天然契合，主线程无需开发者操心；
  • 给开发者一个手动控制内存峰值的手段。

付出什么：

  • 释放时机变得间接：对象实际寿命取决于 pool 何时 pop，而不是作用域；
  • 子线程没有兜底，忘记建池就堆积；
  • 内存峰值不可控，需要开发者主动插 pool；
  • 调试困难：Instruments 里看到对象「还活着」，但其实只是还没 pop。

二、Apple 的补救

成本 优化
返回值反复入池 TLS 快速路径（跳过 pool）
主线程不知何时清理 RunLoop 自动压/弹
page 遍历开销 哨兵分层 + 逆序释放（缓存友好、向栈底收缩）
线程隔离 page 链表存 TLS，无需加锁

三、RunLoop 与 Pool 的三个时机

主线程（更准确说是每个 RunLoop）在系统层面做三件事：

时机 动作
进入 RunLoop（kCFRunLoopEntry） objc_autoreleasePoolPush()
休眠前（kCFRunLoopBeforeWaiting） objc_autoreleasePoolPop() → 再 Push()
退出（kCFRunLoopExit） objc_autoreleasePoolPop()

所以主线程上一次事件（一次点击、一次网络回调）里产生的 autorelease 对象，最多活到这次 RunLoop 循环结束，不会跨越 RunLoop 周期堆积。

四、方案选型

场景 该怎么做
普通业务代码 什么都不做，交给 RunLoop
循环里创建大量临时对象 循环内套 autoreleasepool
后台长任务（无 RunLoop） 整个任务外层 + 循环内层
主线程 UI 刷新 一般不必；若一次处理成百上千个 view 才考虑
Swift Concurrency Task 每个 Task 有独立的栈，长时间循环仍需自己做池
需要严格的生命周期 别依赖 pool，用显式的所有者（Day 2）

五、架构定位

内存峰值的责任人永远是写循环的那个人。 系统只能保证「一次事件结束清一次」，无法知道你在一帧里创建了一万个对象。所以：

  • 图片处理、数据导入这类模块，默认就要有向在循环里加池的意识；
  • 后台线程入口固定包一层 pool；
  • 峰值要用 Instruments 度量，不要凭感觉加。

六、与相邻知识的连接

  • ARC（Day 2）：TLS 返回值优化是现代 ARC 性能的基石；objc_storeStrong 与 pool 处理的是两种不同时机。
  • RunLoop（Day 22）：主线程 pool 的三个 pop 时机全部挂在 RunLoop 观察者上。
  • GCD（Day 14）：GCD 线程的 autorelease pool 由 libdispatch 管理，pop 时机无保证。
  • Block（Day 3）：@autoreleasepool 与 Block 一样，本质都是编译器把一段语法翻译成一对 runtime 函数调用。

05 工程实战

一、标准写法

func exportThumbs(from urls: [URL]) throws {
    for url in urls {
        autoreleasepool {
            let img = UIImage(contentsOfFile: url.path)
            let thumb = img?.resized(to: CGSize(width: 120, height: 120))
            try savePNG(thumb, to: url)
        }   // ← 每轮结束，bitmap 立即释放
    }
}

三条纪律：

  1. 池在循环内，不是循环外；
  2. 每轮的工作量要适中——如果单轮就占几百 MB，把任务再切细；
  3. 嵌套是允许的，内层先生效。

二、后台长任务必须自建池

DispatchQueue.global(qos: .utility).async {
    autoreleasepool {          // ← 外层：整个任务的兜底
        for batch in batches {
            autoreleasepool {  // ← 内层：控制峰值
                process(batch)
            }
        }
    }
}

即使 GCD 的线程自带 pool，pop 时机没有保证——可能整个 block 结束才弹，也可能更久。所以重活一律自己加。

三、Swift 与 OC 混编时注意

语言 语法
Swift autoreleasepool { }
Objective-C @autoreleasepool { }
C 函数（无 OC 语法） objc_autoreleasePoolPush() / Pop()

Swift 的 autoreleasepool 与 Foundation 对象的桥接依赖这个机制——例如 String、Data 桥接到 NSString / NSData 时产生的临时对象同样会进池。

四、用 Instruments 对比峰值

标准流程：

  1. Allocations 模板运行 App；
  2. 勾选 Record reference counts（需要深入到 release 时才用）；
  3. 用 Mark Generation 打点：操作前点一次（Generation A），操作后再点（Generation B）；
  4. 看 Generation B 的 Persistent bytes ——持续存活的内存；
  5. 对比加池前后的曲线：
指标 不加池 循环内加池
峰值（Peak, high water mark） 数百 MB，可能触发内存警告 / OOM 下降到接近基线
持久内存（Persistent） 通常不变 通常不变
耗时 略快（对象复用延迟） 略慢（频繁 release）

判断标准：看 Allocations 的锯齿是否变平。 加池后应该出现密集的小锯齿，而不是一路爬升到峰值后才回落。

也可用 memoryReport：

func memoryFootprintMB() -> Double? { /* task_vm_info，Debug 打点 */ }

五、验证 pool 行为的三个实验

实验 做法 预期
① autorelease 对象出了 pool 就死 autoreleasepool { __weak id w = obj; } 后打印 w 出作用域为 nil
② 主线程 autorelease 跨到下一次 RunLoop 在 pool 外创建 autorelease 对象，dispatch_after 一帧后检查 已释放
③ 子线程不建池会堆积 开一个 Thread，循环创建 autorelease 对象，观察内存 内存持续上涨到线程结束

六、工程清单

场景 是否加池
UIViewController 生命周期代码 ❌
一次处理几十张缩略图 ✅
遍历 Core Data 上十万条记录做迁移 ✅
后台导出 CSV / ZIP ✅

06 常见坑与反思

高频坑位表

坑 成因 症状 规避
循环外加池 作用域包错位置 峰值完全没降 池必须在循环体内
子线程不建池 无 RunLoop 兜底 内存持续上涨，长任务 OOM 后台任务入口包一层
误以为池能解决循环引用 概念混淆 泄漏依旧 用 weak / weak proxy（Day 2、Day 12）
误以为对象出作用域就释放 autorelease 由 pool 决定 「对象怎么还活着」 看 pool 边界，不是作用域
在 pool 外持有 __autoreleasing 参数 逃逸到外层 使用已释放对象 明确 __autoreleasing 的生命周期
过度加池 每几行一个 release 过于频繁，性能反而降 只在有实测峰值的热点加
GCD 线程假设会及时 pop libdispatch 不保证时机 临时对象寿命不可控 重活自己加
在 pool pop 后访问其中的对象 已被 release 野指针崩溃 不要把 autorelease 对象存到外层
主线程上处理千级对象 一次 RunLoop 太长 内存尖峰 + 掉帧 分批 + 加池 + 异步
Debug 时被 RunLoop 掩盖 主线程自动清理 问题只在后台暴露 后台任务单独测
NSAutoreleasePool 用于 ARC MRC 遗留 API 编译错误 只用 @autoreleasepool
用 drain 代替 release 概念过时的 API 行为差异 现代写法不需要

三条反思

  1. AutoreleasePool 解决的是「峰值」，不是「泄漏」。 它只把 release 的时间点往后挪再集中执行，不产生任何额外的回收能力。遇到对象不释放，先去看引用计数和所有权图（Day 2），而不是到处加 @autoreleasepool——那只会让你更难看清真相。
  2. 「延迟释放」这个词本身就藏着风险：对象比你想的活得久。 池内的对象在 pop 之前一直占着内存，而且在 Instruments 里表现为「还活着」。很多人因此误判为泄漏，跑去查循环引用；同样也有人在子线程里等着 Main RunLoop 兜底，结果发现根本没有 RunLoop。
  3. 真正该写 @autoreleasepool 的地方很少，但每一处都很关键。 有了 TLS 返回值优化，日常代码里 99% 的 autorelease 根本不会发生池操作。所以不要为了「优化」到处加池，也不要因此忽视那 1%——批量图片、批量序列化、常驻后台线程，这三处的池不是优化，是能不能正常运行的问题。

08 掌握标准

一句话总结：AutoreleasePool 是由 AutoreleasePoolPage（4096 字节、双向链表、线程私有于 TLS）组成的指针栈，objc_autoreleasePoolPush 压入 POOL_BOUNDARY 哨兵、objc_autorelease 把对象地址压栈、objc_autoreleasePoolPop(token) 逆序发送 release 直到哨兵为止；主线程由 RunLoop 在 Entry / BeforeWaiting / Exit 三个时机自动压弹，子线程没有这个兜底必须自建——它延迟释放、把内存峰值压平，但不提供任何额外的回收能力。

掌握标准：

  • 60 分：能用 @autoreleasepool 包住循环内的临时对象；知道 AutoreleasePool 不是 GC、不能解决循环引用；知道主线程靠 RunLoop 清理、子线程要自己建池。
  • 80 分：能描述 AutoreleasePoolPage 的结构与 push / pop 流程并解释哨兵的分层作用；能说出 RunLoop 三个清理时机；能解释 TLS 返回值优化及其退化条件；能用 Allocations + Mark Generation 度量峰值差异。
  • 100 分：能从 page 的栈结构推出「自动释放严格逆序」「嵌套天然成立」「autorelease 本身几乎零开销」三条性质；能论证内存峰值的真正成因是延迟释放而非 autorelease 昂贵；能区分 内存峰值问题与泄漏问题，给出不同的排查路径；能在图片处理、数据迁移、常驻线程三类场景做出正确的加池粒度决策，并说明过度加池的代价。
